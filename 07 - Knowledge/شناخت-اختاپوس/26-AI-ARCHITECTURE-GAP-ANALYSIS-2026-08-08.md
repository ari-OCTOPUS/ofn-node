## بخشِ سوم — ۱۵ اشتباهِ معماری (هرکدام: توضیح + دلیل + راهِ فیکس + اولویت)

> ترتیب بر اساسِ شدت. هرکدام با **شاهدِ واقعی** (نه فرض) آورده شده.

### 🔴 ۱. نقضِ «قانونِ اتصال» — لایه‌ها می‌نویسند، نمی‌خوانند
**توضیح:** اصلِ بنیادینِ سیستم (در `ARCHITECTURE-LAYERS`) می‌گوید «هر لایه باید
لایهٔ زیرِ خودش را بخواند، وگرنه فقط دارد دفتر پر می‌کند.» ولی در عمل، تقریباً هر
ماژول write-only است: BCM وزن‌ها را می‌سازد ولی هیچ تصمیمی آن‌ها را نمی‌خواند؛
Hebbian هم‌خانواده‌سازی می‌کند ولی مصرف‌کننده‌ای نیست؛ consolidation بدونِ dedup
290+ سیکل با ۳ بینشِ تکراری ساخته است.
**دلیل ریشه‌ای:** ماژول‌ها به‌صورتِ موازی، بدونِ آگاهی از هم ساخته شده‌اند
(الگوی «دوبار ساخته» — `debate_loop` و `governor` tier-router).
**راهِ فیکس:** یک «reader map» رسم کن — برای هر producer مشخص کن چه decision-
consumerی باید بخواندش. سپس consumerها را یکی‌یکی وصل کن، با تست. این یک کارِ
نقشه‌برداری است قبلِ کدنویسی.
**اولویت:** 🔴 CRITICAL — این خودِ بیماری است.

### 🔴 ۲. Sensor-rich، Actuator-poor
**توضیح:** ۵ منبعِ زنده (BCM×۲، self-model، C6، vault_bridge) دادهٔ غنی تولید
می‌کنند ولی هیچ اکچوئیتوری آن‌ها را مصرف نمی‌کند. سیستم حس می‌کند ولی عمل نمی‌کند.
**شاهد:** effect-shadow ۱۵٬۸۳۸ ردیف `learned_pressure` محاسبه کرد، ۰ بار `applied=true`.
**راهِ فیکس:** یک «effector registry» بساز — هر حس باید به یک اکشنِ ممکن (حتی اگر
propose-only) نگاشت شود. حس بدونِ مسیرِ اکشن، نویز است.
**اولویت:** 🔴 CRITICAL

### 🔴 ۳. `smallest_fix` خوانده نمی‌شود
**توضیح:** دقیق‌ترین خروجیِ تصمیمِ سیستم («یک afferent/scorer به پروژهٔ mining اضافه
کن») روی ۱۸ سیکل محاسبه می‌شود ولی **هیچ ماژولی آن را نمی‌خواند**. به‌عنوانِ تشخیص
به مالک می‌رسد، ولی هرگز به نسخه/اجرا تبدیل نمی‌شود.
**دلیل:** خروجی تولید شده ولی به `self_patch` / `mission_runner` وصل نیست.
**راهِ فیکس:** یک consumer برای `smallest_fix` بساز که آن را به‌صورتِ proposal به
`action_graph` می‌فرستد (پشتِ approval، propose-only).
**اولویت:** 🔴 HIGH — این دقیقاً همان «بی‌فایده به نظر می‌رسد» است: سیستم می‌فهمد
چه مشکلی هست ولی هیچ‌وقت فیکسش نمی‌کند.

### 🔴 ۴. بدونِ جمع‌کنندهٔ control-plane واحد
**توضیح:** هیچ پنجره‌ای نیست که «پروسه‌ها + صف‌ها + بودجه + validatorها + Git +
خطاها» را با هم نشان دهد. هر کارتِ تلگرامی منبعِ خودش را جدا می‌خواند.
**شاهد:** `CONTROL-PLANE-PLAN` پیشنهادِ `snapshot()` داده ولی ساخته نشده.
**راهِ فیکس:** تابعِ `control_plane.snapshot()` (read-only، پشتِ فلگ) بساز که همهٔ
حالتِ سیستم را در یک JSON برگرداند. این پایهٔ وب‌اپ است (بخشِ چهارم).
**اولویت:** 🔴 CRITICAL — پیش‌نیازِ هر وب‌اپِ کنترلی.

### 🟠 ۵. ۱۲۸ درِ تاریک (dark gate) از ۳۲۶ فلگ
**توضیح:** ۱۲۸ فلگ partial، ۱۳۵ live-on، ۶۰ ماژولِ یتیم از ۴۹۴. ۲۱۷ نمادِ مرده.
۱۵۸ فایلِ state یتیم.
**دلیل:** ماه‌ها افزودنی‌بودن بدونِ هرس.
**راهِ فیکس:** یک گزارشِ «flag health» بساز: هر فلگ را با «آیا کد می‌خواندش؟ آیا
armed است؟ آخرین بار کِی استفاده شد؟» نشان بده. سپس هرسِ دسته‌جمعی با رأیِ مالک.
**اولویت:** 🟠 HIGH

### 🟠 ۶. خستگیِ تأیید (Approval fatigue)
**توضیح:** دادهٔ Anthropic: ۹۳٪ approvalها rubber-stamp است. اختاپوس همین را دارد —
doctor-pulse ۶ روز منتظرِ رأیِ مالک ماند.
**راهِ فیکس:** (۱) تأییدهای تکراری را batch کن (یک کارت برای ۵ مورد مشابه)؛ (۲)
«confidence-based routing» — کارهایی که سیستم با اطمینانِ بالا درست می‌کند را خودکار
کن (پشتِ آستانه، با log)؛ (۳) auto-decay برای تصمیماتِ کهنه.
**اولویت:** 🟠 HIGH — مستقیماً تجربهٔ «بی‌فایده» را می‌سازد.

### 🟠 ۷. بدونِ سندباکسِ OS-level
**توضیح:** کد بدونِ ایزولاسیونِ container اجرا می‌شود. آخرین خطِ دفاع = کلیکِ مالک.
Anthropic از Bank Vault (sandbox شده) استفاده می‌کند.
**راهِ فیکس:** Firecracker MicroVM پیشنهک شده ولی ساخته نشده. به‌عنوانِ فازِ بعد.
**اولویت:** 🟠 HIGH (برای code_autonomy/self_patch)

### 🟠 ۸. kill switch بدونِ شرایط
**توضیح:** DeepMind توصیه می‌کند شرایطِ ازپیش‌تعریف‌شده (sigma>1، budget>80٪،
pain>0.7) برای توقفِ خودکار. اختاپوس فقط STOP-ORGANISMِ واکنشی دارد.
**راهِ فیکس:** یک «kill conditions» تنظیم‌پذیر در وب‌اپ بساز که مالک آستانه‌ها را
تنظیم کند و سیستم خودکار توقف کند.
**اولویت:** 🟠 HIGH

### 🟡 ۹. `improvement_rate` خودارجاعی
**توضیح:** این معیار ۴۵.۷٪ بود یعنی «به آینه نگاه کردم و پیشرفت دیدم.» `HONEST_OUTCOMES=1`
آن را صفر می‌کند ولی نسخهٔ صادق‌اش هنوز ساخته نشده.
**راهِ فیکس:** improvement_rate باید از **خروجیِ واقعیِارجاع‌شده** (این فیکس باعث شد
تست X سبز شود) بخواند، نه از خود-ارزیابیِ مدل.
**اولویت:** 🟡 MEDIUM

### 🟡 ۱۰. consolidation بدونِ dedup
**توضیح:** 290+ سیکل، ۳ بینشِ تکراری. append-only، بدونِ retract.
**راهِ فیکس:** یک مرحلهٔ dedup (شباهتِ معنایی) به consolidation اضافه کن + retract
برای بینش‌های نقض‌شده.
**اولویت:** 🟡 MEDIUM

### 🟡 ۱۱. `improve._deep_synth` دفترِ خودش را نمی‌خواند
**توضیح:** سنتزکننده، خروجی‌های قبلیِ خودش را نمی‌بیند، پس همان چیز را دوباره
پیشنهاد می‌دهد.
**راهِ فیکس:** قبلِ سنتز، آخرین N خروجی را بخوان و «قبلاً پیشنهاد دادم» را فیلتر کن.
**اولویت:** 🟡 MEDIUM

### 🟡 ۱۲. `effect-shadow.applied` همیشه False
**توضیح:** فیلدِ `applied` در `wiring.py:1730` هاردکد False است — شکافِ observability
(نه باگ). ۱۵٬۸۳۸ ردیف جمع شده ولی نمی‌دانیم کدام اعمال شد.
**راهِ فیکس:** وقتی `learned_pressure_capped` واقعاً باعثِ throttle/halt شد، `applied=True`
ثبت کن.
**اولویت:** 🟡 MEDIUM

### 🟡 ۱۳. بدونِ idempotency تأیید
**توضیح:** محافظتی در برابرِ اجرای تأییدِ منقضی/تکراری نیست.
**راهِ فیکس:** هر approval یک nonce + TTL بگیر؛ dispatch_callback تکراری را رد کن.
**اولویت:** 🟡 MEDIUM

### 🟢 ۱۴. دو ایجنت روی درختِ زنده هم‌زمان
**توضیح:** ۰۸-۰۷ مشاهده شد — ممیزیِ امنیتی و اسکنِ موازی هردو `app.js`/`live/server.py`
را روی `F:\backup` مستقیماً ویرایش کردند (دقیقاً الگوی WORKLOCK).
**راهِ فیکس:** کارِ همزمان همیشه در worktree باشد، نه در درختِ زنده.
**اولویت:** 🟢 LOW (فرهنگی/روند)

### 🟢 ۱۵. الگوی «دوبار ساخته»
**توضیح:** `debate_loop.py`، `governor.py` tier-router، `drawdown_guard` تکراری بدونِ
آگاهی از هم ساخته شده‌اند.
**راهِ فیکس:** قبلِ ساختِ ماژولِ نو، جستجو کن (capability_registry).
**اولویت:** 🟢 LOW (فرهنگی)

## بخشِ چهارم — طراحیِ وب‌اپ: تب‌های کنترلِ چندبعدی

> مالک خواست: «چه تبی در وب‌اپ باید اضافه کنیم که بتونیم همه اینارو در سطح‌بندی و
> ابعادِ مختلف عملی کنترل کنیم.» طراحی زیر ۹ تب را تعریف می‌کند که هرکدام یک **بُعد**
> از کنترل را پوشش می‌دهد. همهٔ read-only در ابتدا؛ write پشتِ approval.

### معماریِ فنی (پایه)
- **پایه:** `control_plane.snapshot()` — تابعی read-only که همهٔ حالتِ سیستم را در یک
  JSON برمی‌گرداند (پیش‌نیازِ اشتباهِ #۴). بدونِ این، وب‌اپ داده ندارد.
- **auth:** همان دیوارِ HMAC ِ موجود (`miniapp_gateway.validate_init_data`) — صاحب‌تنها.
- **read/write تفکیک:** تمامِ تب‌ها اول read-only؛ هر write-only پشتِ `approval_store`
  (کارتِ تأیید در تلگرام).

### ۹ تبِ پیشنهادی (هرکدام یک بُعد)

| # | تب | بُعدِ کنترل | داده | اکشن‌های ممکن (write) |
|---|---|---|---|---|
| ۱ | **نقشهٔ ارگانیسم** (Organism Map) | «زنده‌ست؟ کدام پاها؟» | beat، frozen، halted، legs (live/dead)، ۶ پا با وضعیت | restart leg (پشتِ approval) |
| ۲ | **فلگ‌ها** (Flags) | «چه چیزی armed است؟» | همهٔ ۲۳۴ فلگ با وضعیتِ (armed/partial/dark)، گروه‌بندیِ WIRE/TG/CORTEX | toggle flag (پشتِ رأیِ مالک) |
| ۳ | **بودجه و مغز** (Budget & Brain) | «چقدر خرج کردیم؟» | spent_today/month، fugu_quota (60/60)، سهمیهٔ باقی‌مانده، local vs paid tier، per-leg cost | raise cap (موقت)؛ switch tier |
| ۴ | **حافظه و یادگیری** (Memory) | «چه آموخته؟» | BCM وزن‌ها، Hebbian، consolidation بینش‌ها، latent vector، self-model نسخه، smallest_fix | retract یک بینشِ غلط |
| ۵ | **تصمیم و تأیید** (Approvals) | «چه انتظارِ رأی است؟» | صفِ approval با confidence، verdicts کهنه، نرخِ rubber-stamp | approve/reject/defer (batch) |
| ۶ | **خطای کشتار** (Kill Switch) | «توقفِ اضطراری» | شرایطِ kill (sigma/budget/pain)، STOP-ORGANISM وضعیت، FREEZE.flag | set kill conditions؛ HALT؛ RESUME |
| ۷ | **سلامتِ سیستم** (Health) | «چه چیزی خراب است؟» | flag health (۱۲۸ dark)، orphan modules، dead symbols، validatorها، Git status | trigger cleanup؛ run validator |
| ۸ | **گفتگو و آگاهی** (Cognition) | «چه می‌داند؟ چه فکری می‌کند؟» | فکرِ فعلیِ cortex، self-knowledge نسخه، mirror-history اخیر، owner corrections، consolidation graph (نمایشِ گرافیکی) | inject correction؛ set effort level |
| ۹ | **پاها و کسب‌وکار** (Legs) | «کدام پا چه می‌کند؟» | per-leg: lead pipeline، consent_gate، outbound queue، SMTP status، revenue per leg | approve outbound؛ toggle consent |

### چرا این ۹ تب؟ (نقشه‌برداری به ۱۵ اشتباه)

| اشتباه | کدام تب آن را کنترل/نمایش می‌دهد |
|---|---|
| #۱ قانون اتصال | تب ۴ (Memory) + تب ۸ (Cognition) — reader map را نشان می‌دهد |
| #۲ sensor-rich/actuator-poor | تب ۴ — effector registry |
| #۳ smallest_fix خوانده نمی‌شود | تب ۴ — این فیلد را prominent نشان بده |
| #۴ بدونِ collector | **همهٔ تب‌ها** — `snapshot()` پایهٔ همه است |
| #۵ ۱۲۸ dark gate | تب ۲ (Flags) + تب ۷ (Health) |
| #۶ خستگیِ تأیید | تب ۵ (Approvals) — batch + confidence |
| #۷ سندباکس | تب ۶ (Kill) + تب ۷ (Health) — نشانگر sandbox status |
| #۸ kill conditions | **تب ۶ (Kill)** — تنظیمِ آستانه‌ها |
| #۹ improvement_rate | تب ۸ — نسخهٔ صادق |
| #۱۰ consolidation dedup | تب ۴ — نشانگر تکرار |
| #۱۱ deep_synth خود-خوان | تب ۸ — تاریخچهٔ proposal |
| #۱۲ effect-shadow applied | تب ۴ — درصدِ applied واقعی |
| #۱۳ idempotency | تب ۵ — nonce/TTL |
| #۱۴/۱۵ فرهنگی | تب ۷ — نشانگر worklock/risk |

### ترتیبِ ساختِ پیشنهادی (priority)
1. **`snapshot()`** (پایه — بدونِ این چیزی برای نشان‌دادن نیست) — اشتباهِ #۴
2. **تب ۱ Organism** + **تب ۶ Kill** (امنیتِ بنیادین — مالک باید بتواند ببیند/بکشد)
3. **تب ۳ Budget** + **تب ۲ Flags** (کنترلِ عملیاتی روزانه)
4. **تب ۵ Approvals** (رفعِ خستگیِ تأیید)
5. **تب ۴ Memory** + **تب ۸ Cognition** (پاسخ به «چه می‌داند»)
