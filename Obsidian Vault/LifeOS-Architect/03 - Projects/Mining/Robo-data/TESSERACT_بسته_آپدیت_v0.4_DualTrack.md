# بستهٔ دادهٔ آپدیت پروژهٔ TESSERACT-Miner (نسخهٔ ۰.۳ ← ۰.۴ «Dual-Track»)

> **این فایل چیست؟** ادامهٔ بستهٔ آپدیت v0.3. یک **محور دوم موازی** به معماری اضافه می‌کند: یک سبد (track) جداگانه که فقط کوین‌های PQCِ جوان (≤۹۰ روز) را شکار و انباشت می‌کند، در کنار track عمومی Frontier موجود. این یک ساختار **barbell در سطح استخراج** است: نه یک سیگنال کوچک، بلکه یک دومینِ تخصیص مستقل با بودجهٔ هش‌ریت خودش.
>
> **این یک «ادغام دو فلسفه» نیست.** سند کوانتومی یک تز انباشت بلندمدت روی پروژه‌های جاافتاده تبلیغ می‌کرد که با قانون ≤۹۰ روز در تضاد بود. این فایل به‌جای آن، **ارزش مفهومی PQC (آینده‌نگری امنیتی) را در قالب یک track مستقل که همچنان تابع قانون ۹۰ روز است** پیاده می‌کند.
>
> **زمینهٔ سخت‌افزار/استراتژی (تغییر نده):** اپراتور سیدنی، برق زیر ۰.۰۵ دلار/کیلووات‌ساعت، ناوگان Orange Pi 5/RK3588 + ESP32. هدف: فقط کوین‌های Frontier ≤۹۰ روز. اولویت: حداکثر انباشت کوین با ریسک بالا.
>
> **مهر راستی‌آزمایی:** فکت‌های PQC و رگولاتوری تا **۲۱ مه ۲۰۲۶** راستی‌آزمایی شده‌اند.

---

## بخش ۰ — دو حقیقت فنی که قبل از هر چیز باید جا بیفتند

این دو نکته از سند کوانتومی استخراج و اصلاح شده‌اند:

**حقیقت ۱ — کوانتوم استخراج را تهدید نمی‌کند، امضا را تهدید می‌کند.**
الگوریتم شور فقط ECDSA (لایهٔ امضا/کیف‌پول) را می‌شکند. الگوریتم‌های استخراجِ هش (RandomX, YescryptR32 و …) فقط با گروور یک speedup درجه‌دو می‌گیرند که عملاً نشکستنی است. **نتیجه:** «مقاومت کوانتومی» ویژگی **معماری امنیتی کوین** است، نه ویژگی الگوریتم استخراج. PQC هرگز یک قید روی `algorithm_classifier` نیست — یک معیار انتخاب کوین برای track دوم است.

**حقیقت ۲ — PQC جاافتاده ≠ هدف TESSERACT.**
- **Abelian (ABEL):** lattice-based معتبر (Dilithium/Kyber)، اما از ۲۰۲۲ فعال = چهارساله = نقض قانون ۱. ضمناً privacy coin با فشار delisting (ریسک exit شدید).
- **QRL:** قبلاً در استراتژی خودت به‌خاطر سختی بالا رد شده. وارد نکن.
- **Lattice (LAT):** نام مبهم؛ اسکات باید وجود و سن واقعی‌اش را تأیید کند.

این کوین‌ها **هدف track دوم نیستند** — فقط **الگوی مرجع** هستند (نشان می‌دهند یک معماری PQC خوب چه شکلی است) تا اسکات بتواند فورک‌ها/لانچ‌های جوانِ ≤۹۰ روزه‌ای که از همان خانواده پیروی می‌کنند را تشخیص دهد.

## بخش ۱ — معماری دو-track (هستهٔ آپدیت v0.4)

```
                    ┌─────────────────────────────────────┐
                    │   بودجهٔ کل هش‌ریت  H_total (KH/s)    │
                    └───────────────┬─────────────────────┘
                                    │  تقسیم با سقف کانفیگ‌پذیر
                ┌───────────────────┴───────────────────┐
                ▼                                       ▼
    ┌───────────────────────┐               ┌───────────────────────┐
    │  TRACK A — General     │               │  TRACK B — PQC          │
    │  Frontier Hunter       │               │  (سبد موازی جدید)       │
    │                        │               │                        │
    │  • همهٔ کوین‌های ≤۹۰ روز │               │  • فقط کوین‌های ≤۹۰ روز  │
    │  • منطق فعلی TESSERACT │               │    با pqc_signal >= کف   │
    │  • سهم: 1 - PQC_BUDGET │               │  • سهم: PQC_TRACK_BUDGET │
    └───────────────────────┘               └───────────────────────┘
```

**قاعدهٔ تقسیم بودجه (مهم‌ترین تصمیم این نسخه):**

```python
PQC_TRACK_BUDGET = 0.25     # حداکثر ۲۵٪ از کل هش‌ریت به track دوم
                            # (barbell: ۷۵٪ شکار عمومی / ۲۵٪ شرط آینده‌نگر PQC)

H_track_A = H_total * (1 - PQC_TRACK_BUDGET)   # شکار عمومی
H_track_B = H_total * PQC_TRACK_BUDGET         # سبد PQC

# هر track به‌طور مستقل Kelly-on-hashrate خودش را اجرا می‌کند (بخش ۲).
# دو track سر منابع نمی‌جنگند — بودجه از پیش تقسیم شده.
```

چرا سقف ۲۵٪؟ این همان منطق barbell است که در استراتژی سرمایه‌گذاری‌ات داری (۸۰/۲۰ ایمن/فرانتیر). track دوم یک **شرط آینده‌نگر با ریسک بالاتر** است؛ نباید بتواند بیش از یک‌چهارم ناوگان را ببلعد. کانفیگ‌پذیر است — اگر روایت کوانتومی شتاب گرفت، می‌توانی بالاتر ببری.

## بخش ۲ — Kelly مستقل برای هر track

هر track بودجهٔ هش‌ریت خودش را با همان فرمول Kelly از v0.3 تخصیص می‌دهد، اما **جدا**:

```
# Track A:
allocate_kelly(candidates_general, budget=H_track_A)

# Track B:
allocate_kelly(candidates_pqc, budget=H_track_B)
  # candidates_pqc = کوین‌هایی که هم ≤۹۰ روزند و هم pqc_signal.score >= PQC_TRACK_THRESHOLD

# قواعد مشترک هر دو track:
#   - fractional Kelly = 0.25
#   - سقف ۲۰٪ روی هر کوین (نسبت به بودجهٔ همان track، نه H_total)
#   - اگر لبهٔ همهٔ کاندیداهای یک track منفی بود -> آن track بیکار می‌ماند
#     و بودجه‌اش به track دیگر قرض داده نمی‌شود (مرزبندی سفت برای جلوگیری از drift)
```

**نکتهٔ ضدشکنندگی:** اگر track B هیچ کاندید معتبری نداشت (هیچ کوین PQCِ جوانی موجود نبود)، بودجه‌اش **بیکار می‌ماند**، به track A منتقل نمی‌شود. این عمدی است — جلوگیری از اینکه ربات به بهانهٔ «استفادهٔ بهینه» مرز barbell را آرام‌آرام پاک کند. اگر می‌خواهی در نبودِ کاندید PQC بودجه به track A برگردد، باید صریحاً `PQC_BUDGET_REALLOCATE=True` بگذاری (پیش‌فرض False).

## بخش ۳ — سیگنال PQC (معیار ورود به track B)

```
pqc_signal(coin) -> { score: float[0,1], is_pqc: bool, family: str, reasons: list[str] }

تشخیص (از ریپوی واقعی کوین، نه از بازاریابی):
  family ∈ {dilithium, kyber, falcon, sphincs, generic_lattice, hash_based, none}

امتیازدهی:
  dilithium | kyber | falcon (NIST-standardized)    -> 0.9–1.0
  sphincs (hash-based, NIST alt)                     -> 0.7
  generic_lattice (پیاده‌سازی واقعی غیراستاندارد)     -> 0.5
  ادعای بدون کد قابل‌تأیید                             -> 0.0  + reason="unverified_marketing_claim"
  none (کوین کلاسیک ECDSA)                            -> 0.0

PQC_TRACK_THRESHOLD = 0.5    # کف ورود به سبد track B
                             # (یعنی حداقل یک پیادهٔ lattice واقعی، نه فقط ادعا)
```

**هشدار سفت‌شده:** برچسب «quantum-resistant» در سایت کوین به‌تنهایی score=0 می‌گیرد. اسکات باید scheme امضا را از کد/مستندات فنی استخراج کند. این مهم‌ترین فیلتر ضد-buzzword است — بسیاری کوین‌ها PQC را فقط برای بازاریابی ادعا می‌کنند.

## بخش ۴ — تنش PQC + privacy (تعامل با regulatory_score)

بسیاری کوین‌های PQC هم‌زمان privacy coin هستند (مثل Abelian). این دو محور جدا می‌نشینند و خنثی نمی‌شوند:

```
if coin in track_B and coin.is_privacy:
    survival       <- PQC مثبت (کوین در track B هست چون PQC دارد)
    exit_liquidity <- privacy منفی (ریسک delisting صرافی)

# نتیجه: یک کوین می‌تواند هم‌زمان survival بالا و exit_liquidity پایین داشته باشد.
# Exit Manager (v0.3) این را از قبل مدل می‌کند: privacy coinها فقط
# exit_liquidity پایین‌تر می‌گیرند، که روی regulatory_score اثر دارد نه روی استخراج.
```

این یعنی حتی در track B، یک کوین PQC+privacy ممکن است به‌خاطر exit ضعیف، رتبهٔ Kelly پایینی بگیرد. درست است — survival بالا تضمین نقدسازی نیست.

## بخش ۵ — به‌روزرسانی config (دلتای v0.4 روی v0.3)

```python
# اضافه به config.py:
PQC_TRACK_BUDGET        = 0.25     # سهم هش‌ریت track دوم (barbell cap)
PQC_TRACK_THRESHOLD     = 0.5      # کف امتیاز PQC برای ورود به track B
PQC_NIST_FAMILIES       = ("dilithium", "kyber", "falcon")
PQC_REQUIRE_CODE_PROOF  = True     # ادعای بازاریابی بدون کد = score 0
PQC_BUDGET_REALLOCATE   = False    # بودجهٔ بلااستفادهٔ track B به track A منتقل نشود
# قانون ۹۰ روز در هر دو track بدون استثنا اعمال می‌شود.
```

**قواعد غیرقابل‌مذاکرهٔ افزوده (۱۱ و ۱۲):**

۱۱. track B تابع تمام قواعد track A است (۹۰ روز، fractional Kelly 0.25، سقف ۲۰٪ هر کوین، idle در لبهٔ منفی). PQC هیچ قاعده‌ای را دور نمی‌زند؛ فقط یک سبد جداست با معیار ورود اضافی.
۱۲. مرز بودجهٔ دو track سفت است. بودجهٔ بلااستفادهٔ یک track به دیگری منتقل نمی‌شود مگر با فلگ صریح. **برچسب «quantum-resistant» بدون کد قابل‌تأیید، ورود به track B را نمی‌دهد.**

## بخش ۶ — قراردادهای ماژول (دلتای v0.4)

| فایل | دلتای v0.4 |
|---|---|
| `config.py` | ثابت‌های PQC track بخش ۵ + قواعد ۱۱/۱۲. |
| `scout_agent.py` | خروجی `signature_scheme` و `is_privacy` از ریپو (نه بازاریابی). برچسب‌گذاری کاندیداها به track A یا B. |
| `pqc_classifier` (جدید) | تابع `pqc_signal()` بخش ۳. مستقل از `algorithm_classifier`. |
| `algorithm_classifier.py` | **بدون تغییر.** PQC اینجا وارد نمی‌شود (بخش ۰، حقیقت ۱). |
| `regulatory_score` | تنش PQC+privacy بخش ۴ (boost survival، penalty exit، بدون خنثی‌سازی). |
| `exit_manager.py` | بدون تغییر نسبت به v0.3. |
| `tesseract_orchestrator.py` | **بازنویسی اصلی:** تقسیم H_total به دو بودجه؛ اجرای دو Kelly مستقل؛ مرزبندی سفت بودجه؛ ادغام دو خروجی تخصیص در یک device_plan نهایی. |
| `infra_monitor.py` | بدون تغییر منطقی؛ اما داشبورد Grafana باید تخصیص track A در برابر track B را جدا نشان دهد. |

## خلاصهٔ یک‌خطی استراتژی v0.4

> TESSERACT حالا یک ساختار barbell در سطح استخراج دارد: ۷۵٪ ناوگان روی شکار عمومی کوین‌های Frontier ≤۹۰ روزه (track A)، و ۲۵٪ روی یک سبد موازیِ آینده‌نگر از کوین‌های جوانِ دارای معماری امنیتی PQCِ واقعی و کداثبات‌شده (track B). هر دو track تابع همان قواعد سفت‌اند؛ مرز بودجه نشت نمی‌کند؛ و هیچ برچسب بازاریابی‌ای جای کدِ تأییدشده را نمی‌گیرد.
