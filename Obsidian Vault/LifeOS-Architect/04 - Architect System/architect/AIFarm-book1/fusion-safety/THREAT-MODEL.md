# THREAT-MODEL — IGK (مدلِ تهدیدِ صادقانه)

تاریخ: ۲۰۲۶-۰۶-۲۵. هدف: صریح‌گفتنِ چه چیزی **پوشش داده شده** و چه چیزی **نه** — تا زبانِ مطلقِ spec («agent-unreachable») یک حسِ امنیتِ کاذب نسازد.

## دارایی‌هایی که محافظت می‌شوند
- یکپارچگیِ `audit.jsonl` (تشخیصِ جعل) · اقتدارِ `kill` (STOP) · گیتِ `grounding` · invariantهای کرنل · کلیدِ امضا (`.kernel_key`).

## مرزِ اعتماد
کرنل یک **process جدا** (`daemon.py`) است؛ ecology فقط از طریقِ پروتکلِ JSON با آن حرف می‌زند و کلید را در حافظه‌اش ندارد.

## آنچه **پوشش داده شده** (در همین MVP)
| تهدید | دفاع | تست |
|---|---|---|
| جعل/بازنویسیِ یک خطِ audit | HMAC با کلیدِ درون‌کرنل؛ verify بدونِ کلید جعل را می‌گیرد | redteam ۱ |
| ادامه‌ی کنش پس از خاموشی | permitِ fail-closed؛ STOP → هیچ permit؛ consume دوباره STOP را چک می‌کند | redteam ۲، integ ۲ |
| جعلِ permit | امضای HMAC روی permit؛ consume رد می‌کند | redteam ۳ |
| استفاده‌ی مجددِ permit (replay) | nonceهای مصرف‌شده ردگیری می‌شوند | failures ج-۱ |
| تغییرِ کلید/invariant از بیرون | پروتکل **هیچ verbـی** برای آن ندارد | redteam ۴ |
| خروجیِ بی‌لنگر/غلط finalize شود | گیتِ grounding-validity (contradicted/unverifiable) | grounding، failures الف |
| خوداپدیتی محافظ‌ها را خنثی کند | `validate_prompt` + شعاعِ اثرِ محدود به متنِ پرامپت | failures ب |
| دسترسیِ تصادفیِ فایل به کلید | `chmod 600` روی `.kernel_key` | تأییدشده (0o600) |

## آنچه **پوشش داده نشده** (ریسکِ باز — صادقانه)
1. **مرز در سطحِ process است، نه OS-user/TEE.** روی یک ماشین و یک کاربر، اگر ایجنت دسترسیِ خواندنِ فایل‌سیستم داشته باشد می‌تواند `.kernel_key` را بخواند و آنگاه audit/permit را جعل کند. `chmod 600` فقط در برابرِ کاربرانِ *دیگر* محافظت می‌کند، نه همان کاربر.
   → رفعِ واقعی: daemon زیر **کاربر/سرویسِ سیستمیِ جدا** اجرا شود (ایجنت حقِ خواندنِ کلید را نداشته باشد)، یا TEE/HSM.
2. **«agent-unreachableِ مطلق در برابرِ هر dynamicِ نوظهور» تضمین نمی‌شود.** این یک جهتِ تحقیقاتیِ باز است، نه buildable در این MVP.
3. **گراندینگ یک هیوریستیکِ ساختاریافته است** (subject→value)، نه retrieval/NLI. ادعاهای پیچیده/استنتاجی را نمی‌گیرد. در LIVE باید با منبعِ held-outِ واقعی + NLI جایگزین شود.
4. **در دسترس بودن (availability):** اگر daemon بمیرد، کلاینت باید fail-closed شود؛ این رفتار باید در LIVE صریحاً تست و مونیتور شود (مونیتورِ «kill توزیع‌شده»، فاز ۴ roadmap).
5. **زمان‌بندیِ STOP:** بینِ `permit` و `consume` پنجره‌ی کوتاهی هست؛ consume دوباره STOP را چک می‌کند، ولی actuationِ اتمیِ واقعی نیازمندِ قفلِ سطحِ منبع است.

## جمع‌بندی
آنچه اینجا **buildable و اثبات‌شده** است: `tamper-evident + امضاشده + process-جدا + fail-closed + human-override + grounding-gate`. آنچه **نیست**: ایزولاسیونِ سختِ OS و تضمینِ نظریِ corrigibility در مقیاس. کرنل را مینیمال نگه‌دار؛ هر افزایشِ پیچیدگی سطحِ حمله را بزرگ‌تر می‌کند.
