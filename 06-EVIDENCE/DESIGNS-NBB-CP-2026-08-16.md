# طراحی‌های کوتاه — NBB-V2/V3/V4 + قرارداد OFN (V5)

## NBB-V2 — داشبورد با گیت تپ مالک (رأی: نوشتن با تپ مالک)

**جای کد:** داشبورد فعلی NBB-CP (کشف شد؟) → `03 - Projects/NBB-Control-Plane/` · لایهٔ اجرا: فقط مسیرهای امنِ موجود (stop از طریق مکانیزم‌های فعلی).

```
داشبورد (فقط‌خواندنی + دکمهٔ عمل) → proposal به صفِ تپ → مالک در خود داشبورد تپ می‌کند
  → تأیید در لاگ (همان rigour تصمیمات NBB-CP) → اجرا از مسیر امنِ موجود → رسید
```

**گیت‌ها:** (۱) عمل فقط از فهرست سفید (stop-leg · reject-proposal · freeze-budget) (۲) تپ مالک با نشست/توکن کوتاه‌عمر (۳) هر تپ در ledger با id یکتا (ضدِ بازپخش — درس شورا V4).
**تست:** ۳ تست نو — تپ بدون مالک رد · بازپخش callback_id رد · اثر واقعی فقط از مسیر امن.
**ریسک/مرز:** نوشتن فقط بعد از تأییدِ این طراحی؛ INV-ها دست‌نخورده.

## NBB-V3 — آداپتور ترکیبی (رأی: پایهٔ مشترک + per-leg)

```
nbb_cp/adapters/legs/
  base.py      — LegAdapter (هویت پا، heartbeat، سقف بودجه، submit-to-NBB-CP، status)
  registry.py  — ثبت پاها + گارد نام‌یکتا (درس C-014: رجیستریِ مالکِ کارها)
  legs/
    ziman.py   — کلاس کوچک per-leg: فقط رفتار خاص (مثل transform کارت‌ها)
    lead_painting.py · accounting.py · mining.py · crypto_etoro.py · project_f.py — اسکلت‌های ثبت
```

**قرارداد base:** `heartbeat(ts) -> status` · `propose(action) -> proposal_id` · `budget_cap` per-leg · هیچ اجرایی در base — فقط پیشنهاد/وضعیت (propose-only تا رأی V4).
**تست:** ۴ تست — ثبت نام‌یکتا · heartbeat انقضایافته → stale · پیشنهاد بدون NBB-CP approval ثبت می‌شود ولی اجرا نمی‌شود · سقف بودجه per-leg.
**توجه OFN (V5):** این آداپتورها «محلی» هستند؛ پاهای واقعی روی Orange Pi از طریق لینک راه‌دور (قرارداد زیر) وصل می‌شوند — آداپتور محلی = پروکسیِ لینک.

## NBB-V4 — API با گیت امضای Ed25519 مالک (رأی: باز با امضا)

**کلیدها:** تأیید فقط با کلید عمومی `_ops/owner-signing/` (موجود) — کلید خصوصی `~/.octopus-signing/` فقط دست مالک (هرگز لمس/خوانده نشود؛ امضا = عملیات دستی مالک یا ابزارِ فقط-مالک).

```
درخواست API → بدنهٔ کنونیکال (JSON sort_keys) → امضای مالک (خارج از سرویس)
  → سرویس: verify با کلید عمومی + anti-replay (nonce/انقضا) → اجرای عمل از مسیر امن → رسید امضا؟
```

**قواعد:** (۱) فقط افعال فهرست‌سفید (dry-run/status/stop-با-تأیید-دوباره) (۲) nonce یک‌بارمصرف + انقضای ۶۰s (درس V4 شورا: action-bound, expiry) (۳) لاگ کامل. **تا ممیزی D1: بدون افعال اجراییِ برگشت‌ناپذیر** (هم‌راستا با رأی NO-GO — نسخهٔ محدود).
**تست:** ۵ تست — امضای نامعتبر رد · nonce بازپخش رد · انقضا رد · بدنهٔ دستکاری‌شده رد · رسید ثبت.
**ابزار امضا برای مالک:** `scripts/sign_api_request.py` (ورودی: بدنه → خروجی: امضا؛ فقط روی ماشین مالک اجرا می‌شود).

## V5 — قرارداد لینک راه‌دور OFN (پاسخ مالک: پاها روی Orange Pi، همیشه در ارتباط)

```
OCTOPUS (این ماشین)  ←── لینک همیشه-برقرار ──→  Orange Pi (OFN — پاهای بیرونی)
   NBB-CP/آداپتورها                                   Accounting · Lead-نقاشی · Mining ·
                                                       Crypto-eToro · Ziman · Project-F
قرارداد پیشنهادی v0 (طراحی، نه ساخت):
  - transport: HTTPS محلی/شبکهٔ خانگی + TLS (مقصد allowlist — درس allowlist رصدخانه)
  - heartbeat: هر ۳۰s از هر پا (الگوی doctor-link cursor — pos-based, idempotent)
  - رویداد: پاکت امضاشده (seq + leg + type + payload-hash + ts) — الگوی قرارداد کنونیکال شورا (15 فیلد)
  - صف: outbox در هر طرف + cursor (الگوی tg-outbox — بدون از دست رفتن)
  - گیت: NBB-CP فقط propose/status از طریق لینک؛ اجرا روی برد با تأیید (V2/V4)
  - سلامت: اگر heartbeat > ۹۰s → کارت هشدار در داشبورد (همیشه-در-ارتباط = رصدی)
اولین پا: تابع آمادگی برد (OFN کدام پاها را دارد؟ دسترسی ما به برد نداریم — TEST-COUNT: unverified)
  → قدم بعدی: لیست پاهای روی برد از مالک/برد، سپس ساخت پاکت/heartbeat برای همان پا.
```

## گیت رفتن به کد
هر سه طراحی (V2/V3/V4) بعد از تأیید شما به کد + تست (≥171 سبز) تبدیل می‌شوند. V5 با لیست پاهای روی برد شروع می‌شود.
