## خلاصه اجرایی

زیمن از این گزارش کنار گذاشته شده و به‌صورت مستقل پیگیری می‌شود؛ این گزارش صرفاً روی **چت یکپارچه اختاپوس** (owner-chat / octopus-unified-chat) و فناوری‌های کانکتوری که در `[TECHNOLOGY ADMISSION GATE]` پروژه فهرست شده‌اند تمرکز دارد. مهم‌ترین یافته: **پروتکل MCP در نسخه 2026-07-28 یک تغییر بنیادین کرده** — از یک پروتکل دوطرفه و stateful به یک پروتکل کاملاً stateless تبدیل شده است؛ این مستقیماً روی تصمیم فاز O-T0 پروژه (ممیزی MCP به‌عنوان adapter نه authority) اثر می‌گذارد. در کنار آن، شواهد تازه دربارهٔ SSE در برابر WebSocket، Qdrant در برابر Chroma، Temporal در برابر DBOS، و OpenTelemetry GenAI conventions جمع‌آوری شد که مستقیماً به بندهای ۱ تا ۹ گیت پذیرش فناوری مگاپرامپت شما نگاشت می‌شود.[1][2][3]

## تحول پروتکل MCP — مهم‌ترین تغییر برای owner_recall و Tool Registry

نسخهٔ ۲۰۲۶-۰۷-۲۸ پروتکل MCP، هندشیک `initialize/initialized` و هدر `Mcp-Session-Id` را کاملاً حذف کرده است؛ هر درخواست اکنون مستقل و خوداظهار است و نسخهٔ پروتکل، هویت کلاینت و قابلیت‌ها را در `_meta` حمل می‌کند. دو هدر جدید اجباری — `Mcp-Method` و `Mcp-Name` — به gatewayها اجازه می‌دهند بدون باز کردن بدنهٔ درخواست، مسیریابی و احراز هویت را روی سطح هدر HTTP انجام دهند؛ این دقیقاً همان چیزی است که PolicyGate پروژهٔ شما برای کنترل authority نیاز دارد. لایهٔ HTTP+SSE قدیمی و همچنین Roots/Sampling/Logging به‌طور رسمی منسوخ شده‌اند با یک بازهٔ گذار حداقل ۱۲ ماهه. Cloudflare هم تأیید کرده که این تغییر باعث می‌شود سرورهای MCP بتوانند بدون هیچ زیرساخت stateful، حتی صرفاً در یک Worker، اجرا شوند که هزینهٔ عملیاتی را به شدت پایین می‌آورد.[2][4][3]

برای اختاپوس این یعنی: طبق قانون بند ۹ گیت پذیرش («MCP فقط interface adapter است؛ authority جدید ایجاد نمی‌کند»)، اکنون با نسخهٔ stateless دیگر نیازی به نگهداری session state در لایهٔ Tool Registry نیست و پیاده‌سازی command-trust برای Pi ساده‌تر می‌شود، چون هر دستور به‌طور مستقل قابل امضا و اعتبارسنجی است بدون وابستگی به یک نشست باز.[4][1]

## SSE در برابر WebSocket — تأیید مسیر فعلی مگاپرامپت

داده‌های تازهٔ ۲۰۲۶ به‌طور قاطع تأیید می‌کنند که SSE پروتکل پیش‌فرض صنعت برای استریم پاسخ‌های هوش مصنوعی است — OpenAI، Anthropic و گوگل همگی از آن استفاده می‌کنند و حدود ۹۰٪ موارد استریم AI (چت‌بات، RAG، ابزار-agent) را پوشش می‌دهد. توصیهٔ عملی چندین منبع مستقل یکسان است: با SSE شروع کن، فقط برای سناریوهای دوطرفهٔ واقعی (صدا با قطع‌کردن هم‌زمان، تأیید انسانی مکرر و آنی) به WebSocket برو.[5][6][7]

| معیار | SSE | WebSocket |
|---|---|---|
| جهت | فقط سرور به کلاینت | دوطرفه [8] |
| پیچیدگی زیرساخت | کمتر، روی HTTP معمولی | بیشتر، نیازمند مدیریت اتصال پایدار [5] |
| مناسب برای | چت متنی، پیشرفت اجرا، داشبورد زنده [6] | صدا با interrupt، تعامل گام‌به‌گام مکرر [5] |
| توصیه برای Chat Box اختاپوس | مسیر پیش‌فرض (`GET /api/runs/{run_id}/events`) [1] | فقط اگر بعداً voice/HITL آنی لازم شود |

این یافته مستقیماً فاز O-E4 مگاپرامپت شما (SSE Event Streaming با endpoint `GET /api/runs/{run_id}/events`) را تأیید می‌کند؛ ادامهٔ همان مسیر بدون مهاجرت به WebSocket توصیهٔ درست است.[7][1]

## Qdrant در برابر Chroma — برای Vault و owner_recall

بنچمارک‌های مستقل ۲۰۲۶ نشان می‌دهند Chroma برای حجم زیر ۱۰۰ هزار بردار (حالت embedded، بدون پیکربندی) گزینهٔ مناسبی است، اما در بیش از یک میلیون بردار Qdrant با تأخیر p95 حدود ۱۸ میلی‌ثانیه و Recall@۵ حدود ۹۸.۲٪ عملکرد بهتری می‌دهد. یک بنچمارک دیگر نشان داد Qdrant تنها ۴۱ QPS در ۹۹٪ recall روی ۵۰ میلیون بردار می‌دهد در حالی که pgvectorscale به ۴۷۱ QPS می‌رسد — یعنی حتی Qdrant هم در مقیاس خیلی بزرگ رقیب دارد. نکتهٔ کلیدی مشترک همهٔ منابع: recall بیشتر به تنظیم پارامترهای ایندکس (`ef`، `M`) و کیفیت chunking بستگی دارد تا برند دیتابیس.[9][10][11]

طبق بند ۶ گیت پذیرش فناوری («migration قبل از benchmark ممنوع»)، توصیه این است: تا زمانی که Vault شما به بیش از چند صدهزار fact نرسیده، Chroma فعلی کافی است و مهاجرت به Qdrant باید فقط پس از اندازه‌گیری واقعی Recall@K و p95 روی corpus خودتان تصمیم‌گیری شود، نه پیش از آن.[12][1]

## Temporal در برابر DBOS — برای Run Store و durability

مقایسهٔ عمیق ۲۰۲۶ نشان می‌دهد DBOS یک کتابخانه است که مستقیماً در Postgres موجود شما ادغام می‌شود و state گردش‌کار را در همان تراکنش دیتابیس کسب‌وکار ذخیره می‌کند، بدون سرویس جداگانه؛ Temporal یک خوشهٔ کامل مجزا (Frontend، History، Matching) با پایگاه دادهٔ تاریخچهٔ جدا نیاز دارد. یک آزمایش عملی نشان داد افزودن durable execution به یک پایپلاین ۱۱۰ خطی با DBOS فقط ۷ خط تغییر نیاز داشت، در حالی که با Temporal بیش از ۱۰۰ خط تغییر و بازطراحی به سه سرویس مجزا لازم بود.[13][14][15]

توصیهٔ صریح منابع: DBOS برای تیم‌های کوچک (زیر ۵ مهندس) با یک سرویس Postgres-محور مناسب‌تر است؛ Temporal وقتی ارزش خود را نشان می‌دهد که چند سرویس گردش‌کار-محور مستقل دارید یا به تحمل‌پذیری چندمستأجری/چندمنطقه‌ای نیاز دارید. برای Run Store اختاپوس (فاز O-E2 مگاپرامپت)، این یعنی به‌جای هر دو گزینهٔ سنگین، همان توصیهٔ مگاپرامپت («ابتدا adapter داخلی کوچک، سرویس خارجی نه») با DBOS-style استفاده از دیتابیس موجود هم‌راستاست؛ Temporal را باید DEFER کرد مگر اینکه fan-out واقعی به سرویس‌های خارجی چندگانه اثبات شود.[16][1][13]

## OpenTelemetry GenAI Semantic Conventions — برای Truth Layer و Verifier

قراردادهای معنایی GenAI اوپن‌تلمتری اکنون سه نوع span استاندارد تعریف می‌کنند: `invoke_agent` برای سطح agent، spanهای فراخوانی مدل با ویژگی‌هایی مثل `gen_ai.system`، `gen_ai.usage.input_tokens`، و `gen_ai.response.finish_reasons`، و spanهای `execute_tool` برای هر فراخوانی ابزار. نکتهٔ حیاتی برای اصل «Cite before claim» پروژهٔ شما: محتوای prompt/completion به‌عنوان **span event** جدا از attributeها ثبت می‌شود تا قابل فیلتر حریم خصوصی باشد، و به‌طور پیش‌فرض هیچ محتوایی capture نمی‌شود مگر صراحتاً فعال شود. این قراردادها هنوز در حالت beta هستند و برخی attributeها آزمایشی باقی می‌مانند.[17][18][19]

طبق بند ۸ گیت پذیرش («ابتدا instrumentation API موجود را پیدا کن؛ collector سنگین فقط بعد از نیاز عملی»)، توصیه این است: به‌جای نصب یک backend کامل مثل Aspire Dashboard یا Jaeger، ابتدا فقط spanهای حداقلی مطابق این قرارداد را به رویداد تایپ‌شدهٔ موجود خودتان (`RUN_CREATED`، `MODEL_STARTED`، ...) نگاشت کنید؛ چون event schema فعلی شما (`[TYPED EVENT CONTRACT]`) تقریباً هم‌ساختار با این استاندارد است، فقط افزودن یک mapping لایه کافی است نه جایگزینی کامل.[18][1]

## NATS JetStream در برابر Kafka — برای Event Bus داخلی

مقایسهٔ فنی نشان می‌دهد NATS به زبان Go و با باینری کمتر از ۱۵ مگابایت، بدون نیاز به Zookeeper/KRaft، پیچیدگی پیکربندی بسیار کمتری نسبت به Kafka دارد؛ هر دو تضمین «حداقل یک‌بار» و «دقیقاً یک‌بار» را در JetStream پشتیبانی می‌کنند. توصیهٔ عملی جامعه: اگر فقط یک صف پیام معمولی نیاز دارید، JetStream کافی است؛ Kafka برای حجم بسیار بالا و پردازش پیچیدهٔ داده برتری دارد.[20][21][22][23]

طبق بند ۴ گیت پذیرش شما («فقط اگر چند process/consumer مستقل یا replay/durable ack لازم است؛ در غیر این صورت DEFER»)، از آنجا که رویدادهای اختاپوس فعلاً درون‌فرایندی و با حجم داخلی هستند، توصیه DEFER هر دو (NATS و Kafka) است تا زمانی که مصرف‌کنندگان واقعاً مستقل و چندفرایندی شوند.[23][1]

|---|---|---|

| SSE | استاندارد صنعت برای ۹۰٪ سناریوهای استریم AI [7] | ADOPT (مسیر فعلی فاز O-E4 درست است) |

| Qdrant | بهتر فقط در >۱M بردار؛ Chroma برای حجم کوچک کافی [10][12] | DEFER؛ benchmark روی corpus واقعی قبل از migration |

## ریز تا درشت — پیشنهادات کامل برای واقعی‌سازی اختاپوس

**زیرساخت فوری (این هفته):**

- MCP adapter موجود را برای سازگاری با هدرهای جدید `Mcp-Method`/`Mcp-Name` بازبینی کنید تا gateway بتواند مسیریابی سطح هدر انجام دهد، بدون باز کردن body.[4]
- endpoint `GET /api/runs/{run_id}/events` را طبق فاز O-E4 با SSE پیاده‌سازی کنید؛ heartbeat و resume-after-sequence را طبق مگاپرامپت خودتان تست کنید.[1][7]
- یک لایهٔ نگاشت کوچک بسازید که رویدادهای تایپ‌شدهٔ فعلی (`MODEL_STARTED`, `MODEL_FINISHED`) را به attributeهای `gen_ai.*` نگاشت کند، بدون نصب backend سنگین.[18]

**میان‌مدت (این ماه):**

- برای Run Store، یک TRIAL کوچک DBOS-style روی Postgres موجود اجرا کنید و آن را با معیارهای بند O-T0 (append/read ordering، concurrent append، corrupt fail-closed) بسنجید، قبل از هر تصمیم دربارهٔ Temporal.[15][1]
- baseline واقعی Chroma را روی Vault فعلی (نه دادهٔ synthetic) اندازه بگیرید: Recall@K، p95 retrieval، اندازهٔ corpus؛ فقط اگر شکست خورد Qdrant را TRIAL کنید.[12][1]
- Equation Explainer و Architecture Explainer را طبق فازهای Q و R مگاپرامپت وصل کنید؛ این‌ها مستقل از تصمیم‌های فناوری بالا هستند و می‌توانند موازی پیش بروند.[1]

**بلندمدت (وقتی مقیاس واقعی رسید):**

- اگر تعداد consumerهای مستقل رویداد از ۱ فراتر رفت (مثلاً observatory + hypothesis-engine همزمان مصرف‌کننده شدند)، آن‌وقت NATS JetStream را TRIAL کنید، نه زودتر.[23][1]
- برای Pi/سنسورها: بعد از رسیدن soak به حالت پایدار (نه DEGRADED)، command-trust را با امضای بدون-session سازگار با MCP جدید هم‌راستا کنید تا هر دستور مستقل قابل اعتبارسنجی باشد.[2][1]
- e-stop فیزیکی را قبل از فعال‌سازی هرگونه PWM بخرید و نصب کنید — این پیش‌نیاز سخت‌افزاری مستقل از هر تصمیم نرم‌افزاری بالاست.[1]

**اصل راهنما برای همهٔ گام‌ها:** طبق گیت پذیرش فناوری خودتان، هیچ فناوری جدیدی بدون Technology Decision Record (مشکل اندازه‌گیری‌شده + راه‌حل موجود ناکافی اثبات‌شده + trial با threshold + rollback تست‌شده) نصب نشود؛ این گزارش فقط شواهد بیرونی تازه را فراهم کرد، تصمیم نهایی هر مورد باید طبق پروتکل STOP/TDR خودتان با رأی مالک ثبت شود.[1]
