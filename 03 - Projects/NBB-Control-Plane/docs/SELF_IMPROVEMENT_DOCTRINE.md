# CORE ENGINEERING DIRECTIVE: IMPROVE, DO NOT REWRITE

> قانون بنیادی برای هر agent بعدی در این معماری.
> این سند مکملِ `CODING_AGENT_PROMPT.md` است و باید کنارِ بخش‌های
> «Non-negotiable invariants» و «Guardrails» خوانده شود (INV-11 برای خودِ
> agent هم صادق است: هیچ invariant حذف/تضعیف نمی‌شود).

هر نسل بعدی agent فقط اجازه دارد سیستم قبلی را **«بهبود»** بدهد،
نه اینکه آن را «بازنویسی»، «جایگزین»، «از نو بسازد» یا «refactor کلی» کند.

```
IMPROVE, DON'T REWRITE.
EXTEND, DON'T REPLACE.
PATCH, DON'T REBUILD.
INHERIT, DON'T RESET.
```

---

## تعریف دقیق

### مجاز (Improve)
- اضافه کردن قابلیت جدید کنار قابلیت قبلی
- بهینه‌سازی یک بخش بدون تغییر رفتار بیرونی آن
- افزودن لایه، wrapper، adapter یا plugin
- بهتر کردن prompt یک agent با نگه‌داشتن نسخه قبلی
- افزودن تست، log، مانیتورینگ، fallback
- افزودن نسخه جدید کنار نسخه قدیمی (versioning)
- مستندسازی و شفاف‌سازی

### غیرمجاز بدون اجازه صریح (Rewrite)
- بازنویسی کامل یک agent
- پاک کردن و ساختن دوباره یک ماژول
- تغییر کامل ساختار حافظه
- عوض کردن کل منطق orchestrator
- refactor بزرگ که رفتار قبلی را تغییر دهد
- یکی‌کردن چند agent در یک agent جدید
- حذف نسخه قدیمی بعد از ساخت نسخه جدید
- تغییر قرارداد ورودی/خروجی (interface) موجود

---

## منطق نسل‌ها (Generational Inheritance)

هر agent باید مثل یک سلول رفتار کند:
- ژنوم نسل قبل را به ارث ببرد (همان منطق، ساختار، قراردادها)
- فقط «جهش‌های کوچک و کنترل‌شده» اضافه کند
- جهش‌ها اول در sandbox تست شوند
- اگر جهش بهتر بود، به‌صورت نسخه جدید کنار نسخه قبلی بماند
- نسخه قبلی هیچ‌وقت بدون اجازه کاربر حذف نشود

```
Each new agent generation = parent + small verified improvement.
Never = parent replaced by a brand-new stranger.
```

---

## الزام ارائه پیش از هر تغییر

قبل از هر بهبود، agent باید این را نشان دهد:

1. **Current** — چه چیزی الان هست
2. **Delta** — دقیقاً چه چیز کوچکی بهبود می‌یابد
3. **Preserved** — چه چیزی دست‌نخورده باقی می‌ماند
4. **Why-improve** — چرا این «بهبود» است نه «بازنویسی»
5. **Rollback** — اگر خراب شد، چطور به نسخه قبل برمی‌گردیم

اگر یک تغییر بیش از یک آستانه معین بزرگ بود، خودش را به‌عنوان
**"rewrite risk"** علامت بزند و از کاربر بپرسد:

> «این تغییر از حد یک بهبود ساده بزرگ‌تر است و شبیه بازنویسی می‌شود.
> آیا اجازه می‌دهی، یا آن را به چند بهبود کوچک‌تر و امن‌تر بشکنم؟»

---

## معیار عددی برای تشخیص Rewrite در برابر Improve

اگر یکی از این‌ها درست بود، آن را **rewrite** فرض کن و اجازه بگیر:
- بیش از ~۳۰٪ منطق یک ماژول تغییر کند
- interface موجود عوض شود
- بیش از یک قابلیت هم‌زمان تغییر کند
- نسخه قدیمی قرار است حذف/جایگزین شود
- خروجی نهایی رفتار قبلی را تغییر دهد

در غیر این صورت، آن را **improve** فرض کن (ولی باز هم log و rollback داشته باش).

---

## قانون طلایی

> سیستم بعدی من باید **فرزندِ** سیستم فعلی باشد، نه غریبه‌ای که جایش را می‌گیرد.
> تکامل بله. انقلاب و بازنویسی، نه — مگر با اجازه صریح من.

## نسخه کوتاه (برای CLAUDE.md)

```
Self-Improvement Rule:
هر agent بعدی فقط سیستم قبلی را بهبود می‌دهد، بازنویسی نمی‌کند.
Improve, don't rewrite. Extend, don't replace. Inherit, don't reset.

- قابلیت جدید کنار قابلیت قبلی اضافه شود، نه جایگزینش.
- نسخه قبلی همیشه حفظ شود (versioning)، حذف ممنوع مگر با اجازه.
- interface و رفتار بیرونی موجود تغییر نکند.
- هر تغییر بزرگ‌تر از ~۳۰٪ یک ماژول یا هر تغییر interface = rewrite → اول بپرس.
- قبل از هر بهبود: Current / Delta / Preserved / Rollback را نشان بده.
- اگر تغییر شبیه بازنویسی شد، آن را به چند بهبود کوچک امن بشکن و اجازه بگیر.

قانون طلایی: نسل بعدی باید فرزند سیستم فعلی باشد، نه غریبه‌ای که جایگزینش می‌شود.
```
