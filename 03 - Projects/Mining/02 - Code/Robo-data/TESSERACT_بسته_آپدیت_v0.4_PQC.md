# بستهٔ دادهٔ آپدیت پروژهٔ TESSERACT-Miner (نسخهٔ ۰.۳ ← ۰.۴ «PQC-Aware»)

> **این فایل چیست؟** ادامهٔ بستهٔ آپدیت قبلی (v0.3). یک لایهٔ جدید اضافه می‌کند: **آگاهی از رمزنگاری پساکوانتومی (PQC) به‌عنوان سیگنال بقا**. این لایه از سند «معادلات کوانتومی» استخراج شده، اما **عمداً تز هستهٔ TESSERACT (فقط کوین‌های ≤۹۰ روز، استخراج با Orange Pi) را دست‌نخورده نگه می‌دارد**.
>
> این یک «ترکیب» به‌معنای ادغام دو فلسفه نیست. سند کوانتومی یک فلسفهٔ انباشت بلندمدت (افق ۵–۷ ساله) روی پروژه‌های جاافتاده تبلیغ می‌کرد که با تز TESSERACT در تضاد است. کاری که این فایل می‌کند: **فقط لایهٔ ارزشمند آن سند (PQC به‌عنوان سیگنال آینده‌نگری) را برمی‌دارد و به اسکلت TESSERACT تزریق می‌کند**، با وزن متوسط — نه آنقدر کم که بی‌اثر شود، نه آنقدر زیاد که قانون ≤۹۰ روز را بکشد.
>
> **زمینهٔ سخت‌افزار/استراتژی (تغییر نده):** اپراتور سیدنی، برق زیر ۰.۰۵ دلار/کیلووات‌ساعت، ناوگان Orange Pi 5/RK3588 + ESP32. هدف: فقط کوین‌های Frontier ≤۹۰ روز. اولویت: حداکثر انباشت کوین با ریسک بالا.
>
> **مهر راستی‌آزمایی:** فکت‌های PQC و رگولاتوری زیر تا **۲۱ مه ۲۰۲۶** راستی‌آزمایی شده‌اند.

## بخش ۰ — دو حقیقت فنی که قبل از هر چیز باید جا بیفتند

این دو نکته از سند کوانتومی **استخراج و اصلاح** شده‌اند، چون سند آن‌ها را مبهم/غلط ارائه کرده بود:

**حقیقت ۱ — کوانتوم استخراج (mining) را تهدید نمی‌کند، امضا را تهدید می‌کند.**
الگوریتم شور فقط رمزنگاری منحنی بیضوی (ECDSA — لایهٔ امضا/کیف‌پول) را می‌شکند. الگوریتم‌های استخراجِ هش (SHA-256, RandomX, YescryptR32 و …) فقط با الگوریتم گروور یک speedup درجه‌دو می‌گیرند که عملاً نشکستنی است (امنیت ۲۵۶ بیت → ~۱۲۸ بیت مؤثر). **نتیجه برای ربات:** «مقاومت کوانتومی» یک ویژگی **لایهٔ امضای کوین** است، نه یک ویژگی الگوریتم استخراج. تو نمی‌توانی با Orange Pi «مقاومت کوانتومی استخراج کنی». این یعنی PQC هرگز نباید یک قید روی `algorithm_classifier` باشد — فقط یک سیگنال روی **معماری امنیتی خودِ کوین** در Survival Filter.

**حقیقت ۲ — PQC جاافتاده ≠ هدف TESSERACT.**
پروژه‌های شاخص PQC که سند نام می‌برد، با تز ≤۹۰ روز ناسازگارند:
- **Abelian (ABEL):** پروژهٔ معتبر lattice-based (CRYSTALS-Dilithium/Kyber)، اما **از ۲۰۲۲ فعال** = چهارساله = نقض قانون ۱. ضمناً **privacy coin** است و با فشار delisting صرافی‌ها مواجه (ریسک exit-liquidity شدید).
- **QRL:** قبلاً در استراتژی خودت **به‌خاطر سختی بالا رد شده بود**. وارد نکن.
- **Lattice (LAT):** نام مبهم؛ قبل از هر ارجاع، اسکات باید وجود و سن واقعی‌اش را تأیید کند.

**نتیجه:** این کوین‌های نام‌برده **هدف استخراج نیستند**. آن‌ها فقط **الگوی مرجع** هستند — یعنی نشان می‌دهند یک معماری PQC «خوب» چه شکلی است (lattice-based، NIST-aligned مثل Dilithium/Kyber)، تا اسکات بتواند کوین‌های **جوانِ ≤۹۰ روزه‌ای** که از همین الگو پیروی می‌کنند را تشخیص دهد.

## بخش ۱ — لایهٔ جدید: سیگنال PQC در Survival Filter

این هستهٔ آپدیت v0.4 است. یک تابع جدید اضافه می‌شود که خروجی‌اش به‌عنوان یک ضرب‌کنندهٔ متوسط وارد `survival_probability` می‌شود.

```
pqc_signal(coin) -> { score: float[0,1], is_pqc: bool, family: str, reasons: list[str] }

تشخیص (از ریپوی واقعی کوین، نه از بازاریابی):
  - آیا لایهٔ امضا/کیف‌پول از خانوادهٔ lattice-based است؟
    family ∈ {dilithium, kyber, falcon, sphincs, generic_lattice, hash_based, none}
  - آیا با استانداردهای NIST PQC هم‌راستاست؟ (CRYSTALS-Dilithium/Kyber = بالاترین اعتماد)
  - هشدار: ادعای صرفِ «quantum-resistant» در سایت کوین = score=0 تا وقتی کد تأیید شود.
    (بسیاری کوین‌ها این را به‌عنوان buzzword بازاریابی می‌کنند بدون پیاده‌سازی واقعی.)

امتیازدهی:
  dilithium | kyber | falcon (NIST-standardized)   -> 0.9–1.0
  sphincs (hash-based, NIST alt)                    -> 0.7
  generic_lattice (پیاده‌سازی واقعی ولی غیراستاندارد) -> 0.5
  ادعای بدون کد قابل‌تأیید                            -> 0.0  + reason="unverified_marketing_claim"
  none (کوین کلاسیک ECDSA)                           -> 0.0  (نه جریمه، نه پاداش — خنثی)
```

**نحوهٔ تزریق به survival (وزن متوسط — این تنظیم کلیدی است):**

```
# PQC یک محور درجه‌یک نیست. یک تقویت‌کنندهٔ متوسط است.
PQC_TILT_MAX = 0.15        # حداکثر ۱۵٪ تقویت survival — قابل تنظیم در config

survival_adjusted = survival_base * (1 + PQC_TILT_MAX * pqc_signal.score)

# مثال: کوین با survival_base=0.4 و pqc_signal=1.0 (Dilithium واقعی)
#   -> 0.4 * 1.15 = 0.46   (یک هل کوچک اما معنادار، نه یک جهش)
```

چرا وزن متوسط؟ چون PQC یک **روایت آینده** است که هنوز محقق نشده. اگر آن را محور درجه‌یک کنی، ربات کوین‌های PQCِ بی‌کیفیت را فقط به‌خاطر برچسب‌شان شکار می‌کند (دام بازاریابی). اگر صفرش کنی، یک سیگنال بقای واقعی را از دست می‌دهی. ۱۵٪ نقطهٔ تعادل ضدشکنندگی است.

## بخش ۲ — حلقهٔ Watchlist برای PQCِ هنوز-جوان (مدیریت تنش با قانون ۹۰ روز)

این مشکل واقعی را حل می‌کند: بهترین پروژه‌های PQC معمولاً جاافتاده‌اند (نقض ۹۰ روز)، اما تو نمی‌خواهی یک کوین PQCِ امیدوارکنندهٔ ۹۵ روزه را فقط به‌خاطر ۵ روز از دست بدهی.

```
وقتی اسکات یک کوین با pqc_signal.score >= 0.7 پیدا می‌کند اما سنش > 90 روز است:
  -> آن را استخراج نکن (قانون ۱ سفت می‌ماند)
  -> ولی به PQC_WATCHLIST اضافه کن با reason و snapshot
  -> هدف watchlist: شناسایی فورک‌ها / لانچ‌های جدیدِ بعدی که از همان معماری استفاده می‌کنند

# منطق: اگر Abelian چهارساله است و نمی‌توانی استخراجش کنی،
# ولی یک فورک ۳۰ روزهٔ lattice-based از همان خانواده لانچ شد،
# watchlist کمک می‌کند آن را زودتر تشخیص دهی.
```

این تنها نقطه‌ای است که سند کوانتومی واقعاً ارزش افزوده دارد: به اسکات یک **الگوی شناسایی** می‌دهد، نه یک هدف مستقیم.

## بخش ۳ — اثر بر regulatory_score (تعامل با privacy/PQC)

نکتهٔ ظریف: بسیاری کوین‌های PQC هم‌زمان **privacy coin** هستند (مثل Abelian). این یک تنش رگولاتوری ایجاد می‌کند که باید کد بفهمد:

```
# اگر کوین هم PQC و هم privacy باشد:
if pqc_signal.is_pqc and coin.is_privacy:
    pqc_boost = +0.15 (روی survival)        # امتیاز فنی
    reg_penalty = اعمال شود روی exit_liquidity # ریسک delisting صرافی

# این دو خنثی نمی‌شوند — در دو محور جدا می‌نشینند:
#   survival (آیا شبکه دوام می‌آورد؟) <- PQC مثبت
#   exit_liquidity (آیا می‌توانم نقد کنم؟) <- privacy منفی
```

این دقیقاً همان معماری دودفتری/دومحوری است که در v0.3 ساختیم: «دوام شبکه» جدا از «قابلیت نقدسازی» امتیاز می‌خورد. PQC + privacy یک کوین می‌تواند survival بالا و exit پایین داشته باشد هم‌زمان — و این درست است.

## بخش ۴ — به‌روزرسانی config (دلتای v0.4 روی v0.3)

```python
# اضافه به config.py (روی دلتاهای v0.3):
PQC_TILT_MAX            = 0.15      # حداکثر تقویت survival از سیگنال PQC
PQC_WATCHLIST_THRESHOLD = 0.7      # کف امتیاز PQC برای ورود به watchlist
PQC_NIST_FAMILIES       = ("dilithium", "kyber", "falcon")  # بالاترین اعتماد
PQC_REQUIRE_CODE_PROOF  = True     # ادعای بازاریابی بدون کد = score 0
# قانون ۹۰ روز هیچ استثنایی نمی‌گیرد — watchlist جایگزین استثناست.
```

**یازدهمین قاعدهٔ غیرقابل‌مذاکره (افزوده):**

۱۱. سیگنال PQC هرگز نمی‌تواند گیت سن ۹۰ روز را دور بزند یا سقف هش‌ریت ۲۰٪ را بشکند. PQC فقط `survival_probability` را حداکثر ۱۵٪ تقویت می‌کند و یک watchlist تغذیه می‌کند. **برچسب «quantum-resistant» بدون کد قابل‌تأیید، صفر امتیاز می‌گیرد.**
