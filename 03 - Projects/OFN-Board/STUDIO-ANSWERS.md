## ۰) 🔴 اول یک تصحیح — خطا مال من بود

مگاپرامپت نوشته بود «`kernel/photos.py` از قبل نوشته شده و بدون تغییر کار
می‌کند… بخوانش و استفاده کن؛ دوباره ننویس». **وجود نداشت.**

آن ماژول در فضای کاری من ساخته و تست شده بود (۴۰ تست) و هرگز به این برد
منتقل نشد. من توصیفش را نوشتم و بعد باورش کردم.

این دقیقاً درس ۵ و ۸ است، این بار در یک سند به‌جای یک docstring:

> **توصیف، جدا از چیزی که توصیفش می‌کند، بررسی نشد.**

ایجنت درست کار کرد که ایستاد و گزارش داد به‌جای اینکه فرض کند سند درست
است. همان کار را با هر ادعای دیگری در اسناد من بکن.

**اقدام:** فایل `tests/test_photos.py` (۴۰ تست، مستقل از پیاده‌سازی) همراه
این سند می‌آید. آن را روی پیاده‌سازیِ **خودت** اجرا کن، نه روی نسخهٔ من.
اگر رد شد، باگ پیدا شده. اگر سبز شد، دو مسیر مستقل به یک نتیجه رسیده‌اند.

سه موردی که در آن تست‌ها هست و ممکن است نداشته باشی: `bool` به‌عنوان
`position` (چون `True == 1` در پایتون و بی‌صدا می‌شود موقعیت ۱)، رد کردن
`image/svg+xml` (ظرف اسکریپت است — سرو کردنش از origin خودمان XSS ذخیره‌شده
با لباس عکس است)، و اینکه پیشوند `piece-1/` نباید `piece-10/` را بگیرد.

## ۱) واحد پیش‌نویس — تصمیم گرفته شد

مالک گفت: مجموعه‌های مختلف با ژانرهای مختلف، مرحله‌به‌مرحله، و هر پست
می‌تواند یک یا چند عکس باشد. تصمیم مدل‌سازی به من واگذار شد. این است:

```
collection  →  draft  →  media
مجموعه         پست       رسانه (۱ تا N)
```

**`draft` هم واحد رضایت است و هم واحد انتشار.** یک پست، یک تصمیم، یک ردیف
در `draft_subjects`. رسانه‌ها زیرمجموعهٔ آن‌اند و ترتیب دارند.

```sql
collections
  collection_id TEXT PRIMARY KEY,
  label       TEXT NOT NULL,
  genre       TEXT NOT NULL,        -- برچسب آزاد. سیستم تفسیرش نمی‌کند.
  sensitivity TEXT NOT NULL,        -- 'general' | 'restricted'
  created_at  INTEGER NOT NULL

drafts
  draft_id      TEXT PRIMARY KEY,
  collection_id TEXT REFERENCES collections,   -- NULL مجاز: پست بی‌مجموعه
  caption       TEXT,
  status        TEXT NOT NULL,
  scheduled_for INTEGER,
  created_at    INTEGER NOT NULL

draft_media
  draft_id  TEXT NOT NULL REFERENCES drafts,
  position  INTEGER NOT NULL,
  media_ref TEXT NOT NULL,
  PRIMARY KEY (draft_id, position)
```

چرا `draft` و نه `media` واحد رضایت است: سبا دربارهٔ **یک پست** تصمیم
می‌گیرد، نه دربارهٔ تک‌تک فریم‌ها. اگر واحد، رسانه بود، یک پست سه‌عکسی
سه بار همان سؤال را می‌پرسید — و این دقیقاً همان تکثیر تصمیم است که کل
`DESIGN-DIRECTIVE.md` علیه آن است.

### 🔴 و `sensitivity` یک دروازهٔ ماشینی است، نه یک برچسب

```python
# ofn/kernel/advisor_gate.py
def may_send_image(collection, *, consent) -> Verdict:
    """مجموعهٔ restricted هرگز به هیچ API بیرونی نمی‌رود.

    این ساختاری است، نه سیاستی: نه با تنظیم روشن می‌شود، نه با رضایت،
    نه با فلگ. تابع مسیرش را ندارد.
    """
    if collection.sensitivity != "general":
        return Verdict(False, rule="advisor:restricted-never-leaves")
```

دلیلش دو تاست و هر دو کافی‌اند: شرط سرویس تقریباً همهٔ ارائه‌دهنده‌های مدل
این را ممنوع می‌کند، و سپردنش به حافظهٔ آدم یعنی روزی یادش می‌رود.

`sensitivity` پیش‌فرض **`restricted`** است. عمومی شدن یک انتخاب صریح است،
نه حالت پیش‌فرض. با fact غایب، در محتاطانه‌ترین حالت بمان.

## ۲) افراد در تصویر — «فقط خودش»

یک `subject`، یک `release`. ثبتش کن و تمام.

ولی **`draft_subjects` را از روز اول پر کن، حتی وقتی همیشه همان یک نفر
است.** جدولی که همیشه یک مقدار دارد بی‌فایده به نظر می‌رسد — تا روزی که
نفر دوم بیاید. آن روز، اگر جدول باشد یک ردیف اضافه می‌شود؛ اگر نباشد،
تاریخچه‌ای که تا آن روز ساخته شده هیچ‌وقت قابل بازسازی نیست.

`published_containing(subject_id)` باید از همین حالا جواب بدهد.

## ۳) معیار «خوب شد» — ستون خالی پر شد

مالک هر چهار مورد را انتخاب کرد. یعنی:

```
        ورودی انسانی                    مشتق قطعی                خروجی
studio  حس خودش نسبت به تصویر       →  چه چیزی جواب داد     →  «این را دوباره بساز»
        پیام و کامنت دریافتی            در برابر چه            «این ترند با کار تو
        عدد پلتفرم                                              جور است»
        ترند بازار (از بیرون)
```

سه‌تای اول از سباست، چهارمی از تحقیق. **حس خودش را جدی بگیر** — همان چیزی
است که ماشین نمی‌داند و کل معماری روی آن سوار است:

```yaml
post.felt_right:
  label: "این پست چه حسی بهت داد؟"
  hint: "قبل از اینکه هیچ عددی ببینی."
  type: scale        # ۱ تا ۵، بدون برچسب عددی در رابط
  ask_when: after_publish
```

⚠️ **قبل از دیدن عدد پلتفرم بپرس.** اگر بعد از دیدن آمار پرسیده شود، جوابش
دیگر حس او نیست، بازتاب همان عدد است — و آن‌وقت یک ورودی مستقل را از دست
داده‌ایم و خودمان هم نمی‌فهمیم.

### مقایسه‌ای که ارزش دارد

جالب‌ترین خروجی این سیستم جایی است که این چهار سیگنال **با هم مخالف‌اند**:

```
حس بالا · عدد پایین   →  «این را دوست داشتی ولی دیده نشد. زمان انتشار؟»
حس پایین · عدد بالا   →  «این گرفت ولی تو دوستش نداشتی. می‌خواهی بیشتر بسازی؟»
```

هیچ داشبوردی این را نمی‌گوید چون هیچ داشبوردی حس را نمی‌پرسد.

## ۴) تحقیق ترند — الگویش از قبل در همین مخزن هست

مالک خواست: تحقیق لحظه‌ای بازار، پیش‌بینی ترند بعدی، و مقایسهٔ کار خودش با
آن‌ها.

**`ofn/kernel/scout.py` را بخوان.** برای leg ماینینگ نوشته شده ولی شکلش
دقیقاً همین است و بدون تغییر ساختاری قابل استفاده است:

```
Memory جغجغه‌ای    چیزی که سبا رد کرده، هفتهٔ بعد دوباره پیشنهاد نمی‌شود
research_focus()   دستور کار از شکاف‌های اندازه‌گیری‌شده می‌آید، نه از خیال
screen()           غربال سخت به‌شکل dataclass، نه به‌شکل متن در پرامپت
brief()            آنچه قبلاً رد شده همراه سؤال می‌رود تا دوباره کشف نشود
```

هفته‌ای یک بار، پلهٔ `fugu`. `fugu-ultra` فقط اگر آری صریح بخواهد.

### 🔴 و یک قید روی کلمهٔ «پیش‌بینی»

مدلی که وب را می‌گردد می‌تواند بگوید **الان چه چیزی دیده می‌شود** و **از
هفتهٔ پیش چه عوض شده**. نمی‌تواند آینده را بگوید. اگر خروجی را به‌شکل
پیش‌بینی قطعی نشان بدهیم، همان کلاس خطاست که تمام این پروژه علیه آن ساخته
شده: عددی با اطمینان، که منبعش را ندارد.

```
✅ «این هفته سه بار این را دیدم؛ دو هفته پیش صفر بار»
✅ «کار تو در این محور با آنچه بالا می‌آید فاصله دارد»
❌ «ترند بعدی X خواهد بود»
```

هر یافتهٔ ترند باید **تاریخ مشاهده و تعداد مشاهده** را حمل کند. بدون آن،
حرفِ مدل است، نه شاهد.

و: تحقیق ترند **رده‌بندی صفر است** — به بیرون می‌رود ولی چیزی از سبا با خود
نمی‌برد. هیچ تصویری، هیچ نامی، هیچ آماری از او. فقط سؤال دربارهٔ دنیا.
