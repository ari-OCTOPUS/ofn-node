# CH-04 · Telegram Bot Unified

> **Channel type:** Human-in-the-loop (HITL) interface — unified bot bridging `_ops` organism and `4d_system` brain.
> **Status:** ✅ Implemented — code complete, credentials gated

## Purpose

One Telegram bot serves both worlds:
- **4d_system brain** (`ایده‌یاب`) — research daemon, self-evolution, frontier
- **`_ops` organism** — governance, budget, doctor, legs

Eliminates dual-bot confusion and ensures a single owner-verdict surface.

## Architecture

```
Owner (Telegram)
    │
    ▼
telegram_bot_unified.py  ←──  reads from both systems
    │
    ├──► 4d_system/brain/  (daemon, self_code, budget)
    │
    └──► _ops/budget/approval_channel_merge.py
              │
              ├──► TelegramApprovalChannel (base)
              │         └──► Telegram API (long-poll)
              │
              └──► UnifiedApprovalQueue (CH-14)
```

---

## Security

- **Owner-only:** `TELEGRAM_CHAT_ID` hard-gate — any other sender = ignored
- **Token from env only:** `TELEGRAM_BOT_TOKEN` — never hardcoded
- **HTTP stdlib-only:** `urllib` — no external HTTP deps
- **Fail-soft:** per-update try/except — one bad message never crashes bot
- **URL/token never logged**

---

## Callback Flow

```
Owner clicks inline button
    │
    ▼
unified bot parses callback_data
    │
    ├──► "self_code:approve:PID"  →  brain/self_code.approve()
    ├──► "app:approve:EID:token"  →  _ops gate approved
    └──► "rfc:merge:RID:token"   →  doctor RFC merge
    │
    ▼
Result emitted to both event buses
```
