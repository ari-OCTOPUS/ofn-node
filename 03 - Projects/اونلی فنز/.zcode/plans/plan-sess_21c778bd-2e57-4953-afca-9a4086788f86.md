# 🏗 طرح Layer 2 — Fan CRM + Vault + KPI واقعی + Octopus Bridge + FAQ auto

## اصل طراحی: یک «data spine» مشترک

به‌جای ۴ جزیرهٔ جدا، یک **`brain/store.py`** می‌سازم که منبعِ حقیقتِ یکپارچه‌ست:

```
brain/store.py (DataSpine)
   ├── FanDB          → fan_db.json     (segments, tags, last-contact, LTV)
   ├── VaultBank      → vault.json      (content assets, tags, metrics)
   ├── KPIRollup      → kpi.json        (rollup از fan_db + record_kpi)
   └── OctopusState   → octopus.json    (heartbeat, last_tick, sync)

      ▲                ▲                ▲                ▲
      │                │                │                │
  dm_pipeline    acquisition_pipe   /kpi real       langar /octopus
  (FAQ auto)     (vault-aware)     (از rollup)      (bridge)
```

هر چهار قابلیت از همین spine تغذیه می‌شن → یکپارچه، بدون drift، با migration safety.

## 🌊 ترتیب build (۸ مرحله، هر یک self-contained + تست)

### مرحله ۱ — `brain/store.py` (DataSpine پایه) · ~۱ ساعت

- متدهای query/add/update که بقیه استفاده می‌کنن
- **تست:** `tests/test_store.py` (~۱۰ تست)

### مرحله ۲ — Fan CRM + `/fan_*` commands · ~۱ ساعت
- `langar/fan_admin.py`: `/fan_add`, `/fan_list`, `/fan_tag`, `/fan_segment`
- آری می‌تونه fan اضافه کنه (مثلاً بعد از اولین PPV، fan رو ثبت کنه)
- segments خودکار: vip (LTV>$50) / regular / lurker / churned
- **تست:** `tests/test_fan_crm.py` (~۸ تست)

### مرحله ۳ — Vault (content bank) + wire به acquisition · ~۱ ساعت
- `langar/vault_admin.py`: `/vault_add`, `/vault_list`, `/vault_tag`

- اگه vault خالی بود → fallback به هوک‌های امن (backward-compat)
- **تست:** `tests/test_vault.py` (~۸ تست)

### مرحله ۴ — KPI dashboard واقعی (`/kpi` real) · ~۱ ساعت
- غیرفعال کردن `/kpi` به جای حالت غیرفعال قبلی
- `/kpi` حالا از `KPIRollup` می‌خونه: fans, revenue, PPV unlocks, delivery rate, churn
- رندر: اعداد واقعی + trend (هفتهٔ قبل vs این هفته)
- `record_kpi` موجود به store وصل می‌شه
- **تست:** `tests/test_kpi_real.py` (~۶ تست)

### مرحله ۵ — FAQ auto-DM (قابلیت HITL + auto) · ~۱.۵ ساعت
- `brain/faq_engine.py`: pattern matching روی incoming DM
  - "price?" → auto-draft قیمت (HITL)
  - "custom?" → auto-draft توضیح custom (HITL)
  - بقیه → HITL مثل قبل
- قانون: هیچ‌چیز autonomous ارسال نمی‌شه — فقط draft auto-z'd می‌شه، آری هنوز `/dm_ok` لازمه
- این FAQ به معنای «seri‌اول سریع‌تر draft میاد» نه «خودکار ارسال می‌شه»
- **تست:** `tests/test_faq_engine.py` (~۸ تست)

### مرحله ۶ — Octopus bridge (`/octopus` command) · ~۱.۵ ساعت
- `langar/langar_bot.py`: command `/octopus` اضافه می‌شه
- سعی می‌کنه `orchestrator.py` رو import کنه (fail-soft اگه `_ops/` غایب)
- اگه موفق: یک tick advisory اجرا می‌شه، نتایج در `OctopusState` ذخیره
- `/octopus status` → beat, protective, pain, consolidation
- `/octopus tick` → یک tick手动 اجرا
- **نکتهٔ صادقانه:** این bridge فقط اگه `_ops/neural` موجود باشه کار می‌کنه. اگه غایب (که هست)، fallback می‌ده به «octopus heartbeat isolated»
- **تست:** `tests/test_octopus_bridge.py` (~۶ تست)

### مرحله ۷ — اصلاح UI Studio (Saba dead buttons) · ~۳۰ دقیقه

- بر اساس audit: این‌ها executable هستن ولی labels غلطه — اصلاح labels

## ⚠️ صادقانه در مورد محدودیت‌ها

1. **FAQ auto = draft auto-z'd، نه auto-sent.** اگه واقعاً autonomous می‌خوای (مثل Izzy)، این نقض ToS OF هست. من نمی‌سازمش.
2. **Octopus bridge وابسته به `_ops/` است.** اگه اون ماژول‌ها غایب باشن (که audit نشون داد هستن)، bridge به «isolated heartbeat» fallback می‌ده. این صادقانه‌ترین حالته.
3. **با ۵ ساعت/هفته، این ۸ مرحله ۲-۳ هفته build time می‌خواد.** من در یک session پایه‌ها رو می‌سازم، ولی کامل‌سازی iteration بعدی می‌خواد.
