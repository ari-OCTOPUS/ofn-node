# C-AUDIT-C-C

## summary
HARD READ-ONLY crash/idempotency audit of the request->release->settle path in F:\octopus-phase0-isolated\_ops\chrono.py (EffectorGate), the LANGAR append (on_human_judgment), and the two external call sites (approval_channel._do_approve, legs/effector_gate_bridge). Verdict: the candidate CANNOT provide exactly-once and does not yet provide effectively-once, because (1) the durable state model is missing the very fields the proven prototype added (content_hash, idempotency_key, approval binding, expiry) and has NO external-receipt field at all; (2) settle() is a non-atomic read-then-blind-write (TOCTOU) that can double-settle and can overwrite a concurrent kill-refuse; (3) request() mints a fresh uuid every call with no idempotency_key, so any crash-retry creates a DUPLICATE pending effect; (4) the human-judgment path commits to TWO stores (genome ledger, then chrono.db) non-atomically with no restart re-drive, so a crash between them strands the approval; (5) release_gated_effects is the exact unbounded batch-release the prototype DISABLED, re-releasing unrelated/newer pending rows on one human append; (6) sweep only reaps status='pending', so a crash in the release->settle window strands an effect in 'releasable' forever. Achievable target is EFFECTIVELY-ONCE only, and only after porting the prototype's per-effect binding PLUS adding a durable-intent idempotency_key and an external-receipt (external_ref + external_status) recorded BEFORE the final SETTLED, plus a reconciliation sweep over 'releasable'. All claims grounded in file:line below; no production module was imported or executed; live vault F:\backup untouched.

## findings
- **[critical]** CRASH WINDOW (c) is unrecoverable by construction: settle() only flips a local status column and records NO external receipt, and the gated_effect schema has no field to hold one. The prototype added content_hash/idempotency_key/approval binding columns; the candidate table has only effect_id,kind,payload_ref,created_beat,created_ts,release_ref,status. With no external_ref/external_status/idempotency_key column, a crash after the EXTERNAL effect but before local SETTLED cannot be distinguished from 'never sent' on restart -> re-drive either duplicates the send (send-then-settle) or loses it (settle-then-send). Exactly-once is impossible; effectively-once is unreachable without these fields.
  - ev: `_ops/chrono.py:205`
  - port: Port the prototype's additive+idempotent migration (proto lines 48-67) into gated_effect: add idempotency_key TEXT, content_hash TEXT, action_kind TEXT, target_ref TEXT, approval_id TEXT, expires_at INTEGER (proto:25-30) AND additionally external_ref TEXT (provider-side id) + external_status TEXT CHECK(NULL,'submitting','submitted','confirmed','failed') + external_at INTEGER. Persist external_ref+external_status='submitting' in the SAME chrono.db transaction that is written immediately BEFORE calling transport, and flip to 'confirmed' from the provider receipt before status='settled'. Widen the status CHECK to include NEEDS_OWNER_REVIEW/LEGACY_UNBOUND (proto:42).
- **[critical]** settle() is a non-atomic read-then-blind-write (TOCTOU) and is NOT a compare-and-set: it SELECTs status/release_ref (line 443-445) then issues UPDATE ... SET status='settled' WHERE effect_id=? with NO 'AND status=''releasable''' guard and no changes()==1 check (line 449-450). Two concurrent settle() calls both pass the read and both UPDATE (double-settle). Worse, a concurrent force_closed()->refused write (line 439-440) can be silently overwritten back to 'settled', defeating the kill-switch. Contrast release_one which correctly guards 'AND status=''pending''' and checks rowcount==1 (line 419-420).
  - ev: `_ops/chrono.py:449`
  - port: Make settle a CAS in one statement: UPDATE gated_effect SET status='settled' WHERE effect_id=? AND status='releasable' AND external_status='confirmed'; then treat changes()==1 as the ONLY success (mirror release_one lines 419-420). This makes settle idempotent under crash re-drive (second call sees status!='releasable' -> 0 rows -> returns already-settled) and closes the kill-vs-settle race.
- **[high]** request() is NOT idempotent: it mints a fresh uuid on every call (lines 382-383) and INSERTs with no idempotency_key, so any crash/retry of the caller creates a DUPLICATE pending effect for the same real-world intent. The proven prototype dedups by idempotency_key and returns the existing effect_id on replay (proto:70-85). The candidate has no such dedup and no idempotency_key column.
  - ev: `_ops/chrono.py:382`
  - port: Port request_effect's idempotency_key dedup (proto:73-76): require caller-supplied idempotency_key, SELECT existing effect_id first and return it on hit, add a UNIQUE index on idempotency_key. This is the durable-intent key that makes the whole request->release->settle chain safe to re-drive.
- **[high]** CRASH WINDOW (a): on_human_judgment writes to TWO stores non-atomically with no restart re-drive. lg.append(...) commits to the genome ledger (line 514), THEN gate.release_one/release_gated_effects commits to chrono.db (lines 524-527). A crash between the two leaves the approval durably recorded in the ledger while the effect stays 'pending'. Nothing on restart re-reads the ledger to re-apply the release, so the human approval is stranded; the effect is only reaped by sweep_stale_effects after 72h -> 'refused' (lines 454-470). Fail-closed (safe) but not recoverable and not idempotent.
  - ev: `_ops/chrono.py:514`
  - port: Define the reconciliation contract: on startup (and each epoch) scan the ledger for APPROVAL entries whose named effect_id is still 'pending', and re-drive release_one (id-bound, idempotent). Give each ledger approval a stable approval_id and record it in gated_effect.approval_id (proto adds this column, 25-30; anti-replay proto:104,110) so re-drive is single-use and cannot double-release.
- **[high]** release_gated_effects is the exact unbounded batch-release the prototype DELIBERATELY DISABLED (proto:118-120 returns 0). It flips ALL pending rows whose kind is in the money allowlist to 'releasable' on ONE human-append hash, with no effect_id binding, no content_hash, no expiry and no anti-replay (lines 402-405). Two consequences: (i) a single human approval releases UNRELATED and NEWER pending effects that the human never saw; (ii) re-driving the same append after a crash re-releases any pending rows created since -> not idempotent and over-authorizing.
  - ev: `_ops/chrono.py:402`
  - port: Adopt the prototype's stance: route ALL releases through per-effect release_one bound to effect_id+content_hash+action_kind+target_ref+expiry+single-use approval_id (proto release_effect 91-115). Either disable release_gated_effects (proto:118-120) or restrict it to flip AT MOST the single effect_id named in the approval; never 'all pending of kind'.
- **[high]** CRASH WINDOW (b) leaks a stuck intent: sweep_stale_effects only reaps status='pending' (line 462), never 'releasable'. A crash after release commits (line 402/418) but before settle (called separately in approval_channel._do_approve line 785 / _settle_effect line 800) leaves the effect permanently 'releasable' -- never auto-settled, never swept, never refused. If transport had already fired, this row is also invisible to any pending-only reconciliation, so a real external send can sit unaccounted-for indefinitely.
  - ev: `_ops/chrono.py:462`
  - port: Add a reconciliation pass over status='releasable': for each, consult external_status. If 'confirmed' -> complete settle (CAS); if NULL/'submitting' past a timeout -> query provider by idempotency_key/external_ref and either advance or refuse; expire stale releasable rows (bounded like the 72h pending sweep). This is the piece that converts window (b)+(c) from a leak into effectively-once.
- **[medium]** The external call site orders local-settle vs transport such that today no external effect fires (outbound transport NOT_ARMED, bridge lines 156-161; approval_channel settles at line 785/800), but the ordering contract that makes it safe once armed is not written down or enforced anywhere. When transport is armed, 'settle then send' loses on crash and 'send then settle' duplicates on crash; nothing in the bridge records a durable pre-send marker.
  - ev: `_ops/legs/effector_gate_bridge.py:151`
  - port: Mandate the two-phase external contract in the bridge: (1) CAS releasable->'submitting' recording idempotency_key+external attempt in chrono.db and COMMIT; (2) call transport passing idempotency_key so the provider dedups; (3) on receipt, record external_ref+external_status='confirmed' and COMMIT; (4) CAS settle requiring external_status='confirmed'. State plainly in the docstring that this is effectively-once (provider must honor the idempotency key), not exactly-once.
- **[low]** Durability of a single chrono.db commit is adequate but not pinned: ChronoDB sets journal_mode=WAL (line 237) but never sets PRAGMA synchronous, so it relies on the default FULL. That is safe against power loss today, but the real gap is CROSS-store atomicity (genome ledger + chrono.db are separate commits, finding a); intra-DB durability alone does not close windows a/b/c. A future migration flipping synchronous=NORMAL would silently weaken even the single-store guarantee.
  - ev: `_ops/chrono.py:237`
  - port: Explicitly pin PRAGMA synchronous=FULL (or NORMAL with documented power-loss tradeoff) next to the WAL pragma so the durability assumption behind the reconciliation contract is not left to a default, and document that cross-store consistency is provided by ledger-driven re-drive (finding a), not by any single transaction.
