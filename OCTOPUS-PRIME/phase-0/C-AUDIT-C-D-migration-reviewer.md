# C-AUDIT-C-D-migration-reviewer

## summary
Adversarial audit of migrate_up (v1->v2 table-recreate) in F:\octopus-phase0-isolated\OCTOPUS-PRIME\phase-0\test-authority\chrono_migration_prototype.py against the real port target F:\octopus-phase0-isolated\_ops\chrono.py (ChronoDB, journal_mode=WAL, Python 3.13.7). The migration passes 13/13 on a fixture but has real atomicity, idempotency, WAL-backup, and legacy-row defects that will bite when ported verbatim into ChronoDB.__init__. TWO are port-breaking: (1) migrate_up is NOT atomic as the rollback doc claims — executescript() COMMITs the CREATE of gated_effect_new outside the DROP/RENAME transaction, and _V2_TABLE lacks IF NOT EXISTS, so any crash after CREATE permanently wedges re-runs ("table already exists"); (2) the candidate _DDL unconditionally runs `PRAGMA user_version = 1` on EVERY ChronoDB construction (chrono.py:227), which resets the version below the idempotency gate (>=2) and re-triggers migrate_up on the next process — and the re-run's 7-column INSERT...SELECT silently drops ALL v2 binding/approval columns (content_hash, action_kind, approval_id, ...). Plus a WAL backup hazard (shutil.copy2 of a WAL db without checkpoint yields an inconsistent .pre-v2.bak) and unquarantined legacy releasable/settled unbound rows that candidate settle() (chrono.py:443-452) will pass to the world without per-effect binding. Safe port recipe below. HARD READ-ONLY honored; nothing written, no modules imported, F:\backup untouched.

## findings
- **[critical]** migrate_up is NOT atomic. con.executescript(_V2_TABLE) issues an implicit COMMIT before running and executes the CREATE in SQLite autocommit; the subsequent INSERT opens a fresh legacy transaction (Python 3.13.7, LEGACY_TRANSACTION_CONTROL) that covers only DROP/RENAME/UPDATE/user_version. So CREATE TABLE gated_effect_new is committed SEPARATELY and OUTSIDE the atomic block. This directly contradicts CHRONO-MIGRATION-ROLLBACK.md:14-16 ('table-recreate atomic under one transaction/executescript ... SQLite rolls back the half-done migration').
  - ev: `chrono_migration_prototype.py:55`
  - port: Do NOT use executescript for the recreate. Wrap the whole migration in an explicit BEGIN IMMEDIATE ... COMMIT and run each statement (including the single CREATE via con.execute, since _V2_TABLE is one statement) inside that transaction so CREATE+INSERT+DROP+RENAME+UPDATE+user_version commit or roll back as one unit.
- **[critical]** Partial-failure is non-idempotent and self-wedging. _V2_TABLE is 'CREATE TABLE gated_effect_new' with NO 'IF NOT EXISTS'. Combined with the finding above, a crash after the CREATE commit but before final commit leaves gated_effect_new committed+empty while user_version stays <2; re-running migrate_up hits ver<2, calls executescript(_V2_TABLE), and fails with 'table gated_effect_new already exists', permanently blocking migration until a human manually drops the orphan table.
  - ev: `chrono_migration_prototype.py:38`
  - port: Make it re-runnable: 'DROP TABLE IF EXISTS gated_effect_new' at the very start of the migration transaction, or 'CREATE TABLE IF NOT EXISTS'. Prefer an explicit column-existence / user_version double-check so a desynced version cannot corrupt already-migrated data.
- **[critical]** The candidate's own init defeats the idempotency gate. _DDL ends with 'PRAGMA user_version = 1;' (chrono.py:227) and executescript(_DDL) runs on EVERY ChronoDB.__init__ (chrono.py:238). After migrate_up sets user_version=2, the next process constructs ChronoDB and resets it to 1, dropping below migrate_up's gate 'if ver >= 2: return' (chrono_migration_prototype.py:52-54), so migrate_up runs AGAIN. On that re-run gated_effect is already v2, but the INSERT...SELECT copies only the 7 base columns and DROPs the old table, silently destroying every v2 column value (content_hash, action_kind, target_ref, idempotency_key, proposal_id, mission_id, approval_id, approved_by, approved_at, expires_at). This is a data-loss loop that the fixture never exercises (fixture reuses one live connection, never reopens).
  - ev: `chrono.py:227`
  - port: Remove the unconditional 'PRAGMA user_version = 1' from _DDL, or make it set-once ('PRAGMA user_version=1' only when the current value is 0). Bump the _DDL baseline to 2 once v2 ships and gate migrate_up on the real stored value. Never let init lower user_version.
- **[high]** The 7-column INSERT...SELECT is the migration's only copy path and hard-codes the v1 column set. If migrate_up is ever invoked against a table that already carries v2 data (see the user_version reset above, or any manual re-invocation), the extra columns are not selected and are lost after DROP+RENAME. There is no guard that the source table is actually v1.
  - ev: `chrono_migration_prototype.py:56`
  - port: Before recreating, assert the source is v1 (e.g. 'content_hash' NOT in PRAGMA table_info) OR copy dynamically by intersecting source and target columns, so a mis-triggered migration is a no-op instead of a silent column-drop.
- **[high]** WAL backup hazard for rollback. ChronoDB opens PRAGMA journal_mode=WAL (chrono.py:237). The rollback procedure (CHRONO-MIGRATION-ROLLBACK.md:12) prescribes shutil.copy2(chrono.db, chrono.db.pre-v2.bak). Under WAL, committed pages live in the -wal file until checkpoint; copying only the main .db file (as the prototype's shutil.copy2 does, chrono_migration_prototype.py:187) yields a stale/inconsistent backup, so the 'byte-identical restore point' the rollback doc promises does not exist for a WAL database.
  - ev: `chrono_migration_prototype.py:187`
  - port: Back up with a WAL-consistent method: run 'PRAGMA wal_checkpoint(TRUNCATE)' then copy .db, OR use 'VACUUM INTO <bak>' / the sqlite3 online backup API (con.backup()). Copy all three files (.db/.db-wal/.db-shm) if a raw copy is unavoidable. Never copy a WAL .db alone.
- **[high]** Legacy quarantine is incomplete. migrate_up only re-labels status='pending' rows with NULL/empty content_hash as NEEDS_OWNER_REVIEW (chrono_migration_prototype.py:63-64). Legacy rows in status 'releasable' or 'settled' that were batch-released under the OLD money-allowlist carry no content_hash and are left untouched. The candidate's EffectorGate.settle() authorizes purely on status=='releasable' and a non-empty release_ref (chrono.py:443-452) with NO content/action/target binding check, so a legacy unbound 'releasable' row can still be settled into the world post-migration, defeating the whole point of per-effect authorization (C).
  - ev: `chrono.py:445`
  - port: Extend the quarantine UPDATE to cover non-pending unbound rows (e.g. set status='NEEDS_OWNER_REVIEW' or the unused 'LEGACY_UNBOUND' for status='releasable' AND content_hash IS NULL), OR harden candidate settle() to additionally require content_hash/action_kind/target_ref binding before it settles anything.
- **[medium]** No PRAGMA foreign_keys handling and no post-migration integrity check. migrate_up never sets foreign_keys and never runs foreign_key_check. gated_effect currently has no FKs/indexes/triggers and no other table references it in _DDL (chrono.py:205-222), so nothing is lost TODAY — but the SQLite-official table-recreate procedure requires foreign_keys=OFF (set BEFORE the transaction, since the pragma is a no-op inside one) and a foreign_key_check afterward. Porting the recipe without this makes the migration unsafe the moment any index/FK/trigger is added to gated_effect, because DROP TABLE silently drops dependent indexes/triggers and RENAME does not recreate them.
  - ev: `chrono_migration_prototype.py:60`
  - port: Follow SQLite's canonical 12-step ALTER recipe: PRAGMA foreign_keys=OFF before BEGIN, recreate table, recreate any indexes/triggers on the new table, PRAGMA foreign_key_check, COMMIT, then restore PRAGMA foreign_keys. Add an assertion that gated_effect has no dependent objects before relying on the bare DROP/RENAME.
- **[medium]** Concurrency / single-writer serialization is unaddressed for the port. ChronoDB is single-writer via self._lock and only the pacemaker writes (chrono.py:235-245). migrate_up is written for a standalone fixture connection with no locking. If ported into ChronoDB.__init__ or run while start_pacemaker_thread has already started the background writer, the DROP/RENAME (a schema change under WAL) races concurrent writes and can raise 'database is locked' or force SQLITE_SCHEMA re-preparation on the pacemaker connection.
  - ev: `chrono.py:238`
  - port: Run migrate_up during __init__ AFTER executescript(_DDL) creates the v1 baseline but BEFORE any pacemaker thread starts, on the single ChronoDB connection while holding self._lock, and checkpoint the WAL (PRAGMA wal_checkpoint(TRUNCATE)) after commit to bound -wal growth from the full table rewrite (the repo already notes Windows -wal leak needing explicit close in outcome_store.py:73).
- **[low]** Anti-replay set is process-local, not schema. release_effect uses a module-level Python set _used_approvals for single-use enforcement (chrono_migration_prototype.py:88,104,110). This is fine for the fixture but is NOT persisted; after a process restart every previously-used approval_id can be replayed. The migration adds no table for used approvals even though it adds approval_id/approved_at columns.
  - ev: `chrono_migration_prototype.py:88`
  - port: When porting the release contract, persist anti-replay in SQLite (e.g. a UNIQUE approval_id ledger or a used_approvals table) instead of an in-memory set, so single-use survives restarts. Not a migrate_up bug per se but must land with the same migration.
