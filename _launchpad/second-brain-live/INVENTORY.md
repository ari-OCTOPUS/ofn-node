## ۳. پیشنهاد معماری (سؤال سند: یک ربات ادمین یا چند ربات؟)

**یک ربات ادمین واحد (همین control-brain، ارتقایی) + ربات‌های بیزنس جدا برای صاحبان.**
دلیل: (۱) authz چندکاربره و inline و halt از قبل اینجاست — نساختن از نو = قانون طلایی ۱؛ (۲) جدا بودن ربات صاحب هر بیزنس یعنی توکن/دسترسی جدا و ریسک ایزوله؛ (۳) رکن B هر بیزنس پیامش را اول به ربات ادمین می‌فرستد (Approve/Edit/Reject) بعد از ربات خودِ بیزنس برای صاحبش می‌رود — دقیقاً حالت پیش‌فرض سند.
‏polling نگه می‌داریم (کد موجود polling است، لپ‌تاپ پشت NAT است و webhook نیاز به دامنه/SSL دارد — دلیل مکتوب، قانون استانداردها).

## ۴. نقشه‌ی فازها روی واقعیت

- **فاز ۱:** ‏ARCHITECTURE.md + ADR + قرارداد پایتونی دو رکن (`core/contracts.py`: ‏ResearchEngine و OwnerInteraction با متدهای brief() / propose() / feedback()).
- **فاز ۲:** ارتقای ربات ادمین: ‏/status تجمیعی، صف approve با inline، جدول `outbox` و `briefs` در sqlite مشترک (Memory Layer v1) + ‏API Gateway نازک (`core/gateway.py` — یک کلاس با DeepSeek/Tavily/Telegram، ‏cache و rate-limit).
- **فاز ۳:** پیاده‌سازی رکن A+B برای زیمان (الگو) → تعمیم به نقاشی و حسابداری. تحقیق زمان‌بندی‌شده = همان الگوی scheduler موجودِ نقاشی. بازخورد مفید/بی‌فایده = دو دکمه زیر هر بریف در ربات ادمین → جدول `feedback`.
- **فاز ۴:** مغز تکاولی طبق دیزاین ratified خود vault (propose-only، branch جدا، CHANGELOG، rollback).
- **فاز ۵:** تست مسیرهای حیاتی + README غیرفنی.

## ۵. سؤال‌های فاز ۰ (قانون طلایی ۳ — بدون جواب این‌ها فاز ۱ شروع نمی‌شود)

1. **صاحبان بیزنس‌ها با چه کانالی؟** فقط تلگرام کافی است (مامان/زیمان هم تلگرام دارد؟) یا واتساپ/ایمیل هم لازم است؟
2. **سه بیزنس رسمی = زیمان + نقاشی + حسابداری؟** و Project-F به‌عنوان چهارمی با قواعد خاص خودش (رکن B فقط صبا) بماند؟
3. **بودجه‌ی ماهانه‌ی LLM رکن A:** تحقیق زمان‌بندی‌شده با DeepSeek خیلی ارزان است (~۱-۳ دلار/ماه برای ۳ بیزنس روزی یک تحقیق) — سقف چقدر باشد؟ Fugu فقط escalation بماند؟
4. **فرکانس تحقیق رکن A:** روزی یک‌بار برای هر بیزنس کافی است یا هفتگی؟
