# محورِ ب — بیدارکردنِ مغز (زمینه‌های ۱۰–۱۸)

## B10 — مسیرِ گفتگو مرده — chat_room پیش از ask_brain/mirror کلمه‌ها را می‌رباید · P1 · ۲h
**وضع:** برای متنِ آزادِ غیر-`/`، center اول `_chat_room` را صدا می‌زند (`center.py:869-872`) و فقط اگر None برگرداند به `_handle_ask` می‌رود؛ هر دو سطحِ LLM آن‌جایند: mirror (`center.py:1149`) و ask_brain (else-شاخهٔ `:1259-1268`). جدولِ کلیدواژهٔ chat_room عریض است (heart=«کند»، brain=«نظرت»، self=«خودت/کی هستی») → تقریباً هر جملهٔ گفتگویی کلیدواژه می‌خورد → به فرمانِ کارمند بازپخش → non-None → ask_brain/mirror هرگز اجرا نمی‌شود.
**شکاف:** سه لایه: (دیسک) هر سه فلگ =1؛ (env) بریف drift صفر می‌گوید → chat_room=1 زنده؛ (رفتار) هر سه دفتر از ۰۷-۲۷ یخ‌زده (`ask-brain.jsonl` آخرین ۲۰:۱۰). **نکتهٔ صداقت:** یخ‌زدگی از ۰۷-۲۷ شروع شد، *قبل* از arm شدنِ chat_room در ۰۷-۲۸ — پس chat_room علتِ اولیه نیست، ولی از ۰۷-۲۸ مانعِ بازیابیِ هر متنِ کلیدواژه‌دار است. تفکیکِ «رباییده شد» از «مالک نپرسید» ناممکن است چون center هیچ لاگِ per-message ِ مسیریابی ندارد.
**پیشنهاد:** دو کار: (الف) گاردِ اتاقِ آینه در `_chat_room` (پچ پایین)؛ (ب) یک **دفترِ تصمیمِ dispatch** — برای هر متنِ آزاد رکورد `{ts, topic, len, route}` که route یکی از chat-room:<cmd>|mirror|mission|intent|ask_brain:<ok|reason>|ask_unknown است. این تنها راهِ تفکیکِ سه لایه است.
**گارد:** پیامِ کلیدواژه‌دار داخلِ تاپیکِ mirror بده و assert کن به mirror_room می‌رسد. **جهش:** حذفِ خطِ `if room=="mirror": return None` → «خودت چطوری؟» به /reveal می‌رود، قرمز.
**پچِ پیشنهادی (`_chat_room`):**
```
         room = self._topic_key(msg) or ""
+        # اتاقِ آینه قرارداد دارد: هر پیامِ مستقیم به لایهٔ خودشناسی. بدونِ این گارد،
+        # «خودت چطوری؟» به کلیدواژهٔ self می‌خورد و به /reveal بازپخش می‌شود.
+        if room == "mirror":
+            return None
         hit = _cr.classify(text, room=room)
```
**کلاس/هزینه/پیش‌نیاز:** P1 · ۲h · restart center (پروسه ۱۸:۵۵ بوت شده)؛ فلگ‌ها همین حالا armed.

## B11 — مغزِ گران روی مُهرِ ساعتیِ governor می‌سوزد، نه روی هدفِ ماه · P2 · ۶h
**وضع:** `FUGU_DAILY_CALL_CAP=60`؛ امروز used_total=36 (primary=30، secondary=6؛ ~۲۴ استفاده‌نشده). از ۳۰ فراخوانِ primary: ~۲۲ الگویِ ثابتِ governor (tokens_in=5629 → chars_out ~۱۸۰ = مُهرِ تخصیصِ JSON)، ۴ deep_think، ۲ تقریباً خالی (chars_out=3/5). governor هر epoch با tier=primary پین است (`governor_epoch.py:439-440`).

**پیشنهاد:** (۱) مُهرِ ساعتی را از مغزِ گران بردار — یا با فلگِ تازه فقط وقتی هشِ snapshotِ تلمتری مادّتاً عوض شد فراخوان بزن (آزادسازیِ ~۲۰/روز)، یا نقش را به secondary/GLM ببر. (۲) سهمیهٔ آزاد را به deep_thinkِ سمتِ business بده. **گارد:** دو epoch با snapshotِ بایت‌به‌بایت یکسان باید دقیقاً **یک** فراخوانِ paid تولید کنند. **جهش:** حذفِ هش-گیت → دو فراخوان برای snapshotِ یکسان.
**کلاس/هزینه/پیش‌نیاز:** P2 · ۶h · رأیِ مالک برای تغییرِ مسیرِ داغِ governor + تصمیمِ VQ-ACCT-PARK.

## B12 — لایهٔ تداعی unreachable است چون تنه (OCTOPUS_WIRE_NEURAL) خاموش است · P1 · ۰h کد (فقط آرم)
**وضع:** سه‌محوره. (فلگ) `OCTOPUS_WIRE_NEURAL/CONSOLIDATION/BCM/SPARSE` **غایب = خاموش**، ولی `HEBBIAN_RICH/BCM_FEED/LATENT_PERSIST/NEURAL_EFFECT_SHADOW` روشن. (reachability) `make_neural_stack` با NEURAL خاموش `None` برمی‌گرداند (`wiring.py:1171-1172`) → `_neural_stack=None` → `neural_beat` بلافاصله None (هیچ hebbian.observe/decay) و `consolidation_beat` با گاردِ `_neural_stack is not None` رد می‌شود. کلِ hebbian/consolidation/latent/BCM از هر چهار entrypointِ زنده unreachable. **تأییدِ زنده ۰۷-۲۹: NEURAL هنوز غایب از flags.cmd.**
**شکاف:** سه فلگِ روشنِ downstream همه داخلِ کدِ گیت‌شده با تنهٔ خاموش‌اند → صفر اثر (دقیقاً تلهٔ mining_os: مسلح ولی گیتِ بالادست خاموش). NEURAL/CONSOLIDATION در ARMING-ORDER **نیستند** — پس این غیبت «staged-عمدی» نیست، صرفاً خاموش است.
**پیشنهاد:** پاسخِ ریشه‌ای: لایهٔ تداعی «هرگز اجرا نشد» چون سوییچِ اصلی خاموش است، نه چون کد ناقص است. **هیچ کدِ جدیدی لازم نیست** — فقط مسلح‌سازیِ owner-gated (B12-revive).
**گارد:** اگر در هر یک از چهار `flags-loaded-*.json` کلیدِ NEURAL ظاهر شود یا `flag('OCTOPUS_WIRE_NEURAL')` True برگردد، حکم قرمز. تا آن CONFIRMED.
**کلاس/هزینه/پیش‌نیاز:** P1 · ۰h کد · رأیِ مالک + restart (B12-revive).

### B12-revive — نقشهٔ کمینهٔ زنده‌کردن (ترتیبِ مسلح‌سازی) · P1 · ۰٫۲۵h
همهٔ قطعات ساخته و سیم‌کشی‌شده. ترتیبِ کمینه (هر گام برگشت‌پذیر با حذفِ خط + restart):
```
 set OCTOPUS_WIRE_NEURAL=1          # stack ساخته می‌شود؛ hebbian شروع به decay/observe
 set OCTOPUS_WIRE_CONSOLIDATION=1   # هر ~۱۲h latent می‌سازد؛ LATENT_PERSIST برش می‌گرداند
 set CHRONO_CONSOLIDATION_EVERY_N_BEATS=60   # اختیاری — بازخوردِ سریع‌تر همان روز
 set OCTOPUS_WIRE_BCM=1             # اختیاری — هرسِ ایندکسِ بازیابی (فراموشی)
```
۱و۲ اجباری و به‌ترتیب (بدونِ NEURAL اصلاً `_neural_stack` ساخته نمی‌شود). **چه ببینی که کار کرد:** در `neural/consolidation.json` ردیف‌های تازه با `latent_vector != null` + `similar_keys` غیرخالی؛ در `state/latent-vectors.json` کلیدهای cycle > 540. اگر NEURAL روشن شد ولی latent رشد نکرد → منبع خالی است نه فلگ.

### B12-state-depth — عمقِ واقعی: از ۵۳۹ سیکل فقط ۳ بردار دارند · P2 · ۰h
`neural/consolidation.json` = ۵۳۹ ردیف ولی فقط **۳** با `latent_vector != null` (سیکل ۵۳۷/۵۳۸/۵۳۹)؛ `latent-vectors.json` = فقط ۱۰ بردار (سیکل ۵۳۶–۵۴۰). کلِ «حافظهٔ بازیابی‌پذیر» یک پنجرهٔ ۵-سیکلهٔ انتهایی است، نه ۵۳۹ سیکل انباشته. یعنی لایهٔ تداعی نه «هرگز» بلکه **پراکنده و ناپایدار** اجرا شده — ۵ سیکل در ~۱۹ روز. معیارِ موفقیتِ B12-revive: نسبتِ ردیف‌های دارای latent باید از 3/539 بالا برود و reach_max از ۲ فراتر.

### B12-writers — نویسندگانِ غیرِ steady روی state زنده · UNKNOWN · ۰h
`sweep.py` (pid 26212، خارج از مخزن، احتمالاً اسکریپتِ جلسهٔ موازی) هم‌اکنون `hebbian.json` را به `[]` بازنویسی می‌کند؛ و نوشتِ سه‌گانهٔ ۲۰:۳۴ (consolidation+latent+bcm، mtime یکسان) فقط از مسیرِ latent+bcm ممکن است ولی هیچ پروسهٔ سنکشن‌شده فلگش را ندارد → کاندیدا: رانِ `run_all`/probeِ گذرا با ORG_ROOT روی درختِ زنده. **درس:** قبل از هر حکمِ «تداعی زنده شد»، منبعِ نوشت را با فلگِ پروسهٔ organism تأیید کن، نه صرفاً وجودِ ردیفِ تازه.

## B13 — حافظه یک لاگِ سنجه است نه انبارِ دانش · P2 · ۳h
**وضع:** ۵۳۹ ردیف، ۶۱۸ نمونهٔ جمله، **۲۶** جملهٔ یکتا. توزیع: «آگاهیِ میانگین: 0.02»×181 (۲۹٪)، top4=۶۶٪. علتِ ساختاری: `_verify_source` فقط ۴ نوع می‌پذیرد (acquisition/doctor_archive/school/calibration) و `run()` برای هر منبع یک جملهٔ **تمپلیتی** می‌سازد.
**شکاف:** این «دانش» نیست؛ سریِ زمانیِ یک متریک به‌شکلِ جمله. هیچ محتوای بازمصرف‌پذیر (تصمیم، علت، درسِ RFC، رأی) نیست، چون منابعِ غنی (calibration/RFC) با اینکه encoder دارند (`neural/encoders.py`) به consolidation تغذیه نمی‌شوند.
**پیشنهاد:** verdictهای واقعی (calibration) و RFCهای دکتر را به‌عنوان منبع تغذیه کن — هر سیکل یک واحدِ دانشِ قابلِ encode، نه یک عدد (پیش‌نیاز: B12-revive).
**گارد:** اگر بعد از افزودنِ منابع شمارِ جملاتِ یکتا زیرِ ~۳۰ بماند و همه الگوی «X: <عدد>» داشته باشند، تغذیه اثر نکرده.
**کلاس/هزینه/پیش‌نیاز:** P2 · ۳h · B12-revive.

### B13-write-only-retrieval — بازیابی write-only است: هیچ مصرف‌کنندهٔ decision-time بردار را query نمی‌کند · P1 · ۴h
**وضع:** کشفِ نحوی: تنها فراخوان‌های `latent_space.similar()/.nearest()` در کلِ `_ops` (غیرتست) داخلِ `_enrich_with_latent` (`wiring.py:1505`) و `_apply_bcm` (`:1527`) هستند — هر دو در **مسیرِ نوشت**. nearest فقط در لحظهٔ نوشتن و نسبت به سیکلی که همین‌الان نوشته شد صدا زده می‌شود (خود-ارجاعی). تنها خوانندهٔ `similar_keys` یعنی `recall_reach` یک **متریک** است و فقط در تست import شده.
**شکاف:** هیچ نقطهٔ تصمیمی نمی‌پرسد «کدام سیکلِ گذشته به وضعیتِ فعلیِ من شبیه است؟» قبل از عمل. این دقیقاً چیزی است که لاگ را از حافظه جدا می‌کند: نوشتن هست، فراخوانی برای یادآوری نیست. حتی با B12-revive این شکاف باقی می‌ماند — **علتِ ساختاریِ «نمی‌تواند به یاد بیاورد».**
**پیشنهاد:** یک read-path اضافه کن: در یک decision beat بردارِ وضعیتِ فعلی را بساز و `latent_space.similar(vec)` را بزن، نتیجه را shadow-log کن (propose-only، پشتِ فلگِ تازه، صفر اثر بر تصمیم).
**گارد:** اگر grepِ `\.similar\(` خارج از write-path و tests صفر بماند، حکمِ write-only پابرجاست. **جهش (سبزکننده):** افزودنِ یک caller در مسیرِ decision.
**کلاس/هزینه/پیش‌نیاز:** P1 · ۴h · B12-revive (تا latent_space پر باشد).

## B14 — deep_think به تصمیم می‌رسد و کارت را تحویل می‌دهد، ولی تصمیم به اجرا بسته نمی‌شود · P1 · ۸h
**وضع:** `OCTOPUS_WIRE_DEEP_THINK=1`، `SLOTS=4`؛ امروز هر ۴ بازه اجرا، ok، **delivered=true**؛ کارتِ RFC با دکمهٔ آره/نه (`deep_think.py:367-373`). محتوا تصمیم‌شکل است: هر جلسه یک حرکتِ مشخص + شرطِ ابطال و صریحاً به جلسه‌های قبلی ارجاع می‌دهد (`_previously_said`).
**شکاف:** دو نقص: (۱) حرکت‌ها یا کنشِ مالک‌اند («به لیدِ زنده تلفن بزن») یا پشتِ کانالِ خاموش‌اند — اندام هیچ effectorِ اجراکننده ندارد؛ کارت فقط ثبت/تأیید می‌کند. (۲) هر دو جلسهٔ topic=self **همان علتِ ریشه‌ای** را بازکشف کرده‌اند: «مکانیزمِ حافظه/نوشتن وصل نیست» — مغزِ گران روزانه یک بلوکِ شناخته‌شده را دوباره می‌خرد چون فیکسش اتفاق نمی‌افتد. هیچ ledgerِ outcome ثبت نمی‌کند مالک روی کارت چه کرد.
**پیشنهاد:** (۱) dedup روی **علتِ ریشه‌ای/موضوع** نه فقط متن: اگر یک finding N روز تکرار شد، به‌جای کارتِ چهارم یک escalationِ متفاوت بده. (۲) رأیِ کارت را به outcome-ledger بنویس. (۳) topicِ self را به فرضیهٔ واقعیِ صفِ C6 تبدیل کن (`OCTOPUS_C6_UNKNOWN_ROOTCAUSE`).
**گارد:** دو جلسهٔ هم‌موضوع با finding یکسان باید کارتِ دوم را سرکوب و escalation بزنند. **جهش:** حذفِ dedup-on-rootcause → دو کارتِ یکسان.
**کلاس/هزینه/پیش‌نیاز:** P1 · ۸h · آرمِ `OCTOPUS_C6_UNKNOWN_ROOTCAUSE` برای بند ۳.

**شکاف:** «فقط ۳ نوبت» شکستِ ثبت نیست، کمبودِ **رسیدن** است: (۱) مالک باید داخلِ تاپیکِ mirror باشد؛ (۲) از ۰۷-۲۸ chat_room هر جملهٔ کلیدواژه‌دار را می‌رباید (B10) و واژگانِ خودشناسی دقیقاً کلیدواژهٔ self‌اند؛ (۳) `record_correction` **قبل از** موفقیتِ جواب صدا می‌شود (`mirror_room.py:217-220` vs `:235`) → نوبتِ شکسته هم یک تصحیحِ ماندگارِ نویزی می‌گذارد.
**پیشنهاد:** گاردِ B10 بزرگ‌ترین اهرم است. علاوه‌بر آن: (الف) `record_correction` را به **بعد از** جوابِ موفق ببر؛ (ب) دکمهٔ صریحِ «✍️ این اشتباه است» به‌جای هیوریستیکِ `_CORRECTION_RX`.
**گارد:** نوبتی که ask_fn شکست می‌دهد نباید سطری به owner-corrections اضافه کند. **جهش:** برگرداندنِ record_correction به قبل از ask_fn → سطرِ نویز.
**کلاس/هزینه/پیش‌نیاز:** P2 · ۱h · هم‌بسته با B10 (گاردِ mirror اول) + restart.

## B17 — ۳۵ بازماندهٔ مناظره فقط در md می‌نشینند؛ کلِ مسیرِ کارت پشتِ فلگِ عمداً-staged · P2 · ۴h
**وضع:** `OCTOPUS_WIRE_DEBATE=1` و `DEBATE_LOCAL=1` → مناظره هر epoch با مغزِ محلیِ $0 می‌دود. `OCTOPUS_WIRE_DEBATE_VERDICT` **غایب = خاموش** (فلگِ ۴ ARMING-ORDER، عمداً staged). `SURVIVORS-QUEUE.md` حالا **۳۵** ورودی دارد؛ `survivors-pending.jsonl` وجود ندارد.
**شکاف:** همان یک فلگ هم **نویسنده** را می‌بندد (`_publish_survivor` فقط با `_verdict_on()`) هم **خواننده** را (`ingest_debate_survivors` فقط با `_debate_on()`). بازمانده‌ها فقط به md می‌روند، هیچ‌کدام کارتِ آره/نهِ تلگرام نمی‌شوند. **این «مرده» نیست؛ خاموشِ عمدی است.** هشدارِ ثانویه: چون DEBATE_LOCAL با qwen 1.5B محتوا می‌سازد، بازمانده‌ها کیفیتِ کم دارند («رگرسیون خطی به‌جای شبکهٔ عصبی») — مسلح‌کردنِ کورکورانه مالک را با کارتِ کم‌ارزش غرق می‌کند.
**پیشنهاد:** اگر مالک بخواهد (رأیِ او): `DEBATE_VERDICT` را آرم + restart organism و center. ولی **قبلش** کیفیت را بالا ببر — یا topicها را به هدف (لید/درآمد) وصل کن، یا گیتِ کیفیت روی بازمانده بگذار. نیمهٔ بازِ ARMING-ORDER: ایدهٔ architect-killed هنوز می‌تواند دوباره صف شود — این نشت را هم ببند.
**گارد:** بازمانده‌ای که به survivors-pending نوشته شود باید به jobِ pendingِ type=debate با دو دکمه بدل شود. **جهش:** بستنِ خواننده بدونِ نویسنده (یا برعکس) → صفر کارت باوجودِ بازمانده.
**کلاس/هزینه/پیش‌نیاز:** P2 · ۴h · رأیِ مالک + restart (هر دو پروسه)؛ ترجیحاً بالابردنِ کیفیت اول.

## B18 — قاعدهٔ اقتصادِ مغز روی «نوعِ کار» کلید می‌زند نه «ارزش-به-هدف»؛ داورِ ارزش ساخته ولی خاموش · P1 · ۱۰h
**وضع:** قاعدهٔ فعلی سه‌تکه: (۱) نگاشتِ ایستایِ `TASK_TIERS` (`model_router.py:56-67`)؛ (۲) `CORTEX_LOCAL_FIRST=1` که فقط secondary را اول محلی می‌زند — primary **هرگز** محلی-اول نمی‌شود («کارِ بزرگ = API»، `:296-297`)؛ (۳) fugu_quota سقفِ ۶۰. داورِ پویا `route_scorer` وجود دارد ولی `CORTEX_ROUTE_SCORER` **خاموش** (`flags.cmd:227`).
**شکاف:** مسیریابی بر اساسِ **نوعِ کار** است، نه ارزشِ سؤال یا اینکه ورودی عوض شده. پیامد: governor چون task=orchestrate است بی‌قید primary می‌شود حتی وقتی تلمتری ~همان است → مغزِ گران روی مُهرِ مکانیکی می‌سوزد (B11). هیچ مکانیزمی نمی‌گوید «این سؤال ارزشِ مغزِ گران دارد چون هدفِ ماه را جلو می‌برد». route_scorer که می‌توانست ارزش‌محور مسیریابی کند ساخته-ولی-خاموش است.
**پیشنهاد:** قاعدهٔ صریح: مغزِ گران فقط برای سؤالی که (الف) ورودی‌اش مادّتاً عوض شده **و** (ب) به تصمیمِ عملیاتی/هدفِ ماه بند است. گام: (۱) governor را change-gate کن (B11)؛ (۲) `CORTEX_ROUTE_SCORER` را اول در حالتِ **سایه** روشن کن (`OCTOPUS_WIRE_ROUTE_SHADOW` موجود، `:289`) تا ۲۴h ببینی داور چه می‌گرفت؛ (۳) meterِ ارزش را به route_scorer وصل کن.
**گارد:** route_scorer باید taskِ ورودیِ-بدونِ-تغییر را به local و task متصل-به-هدف را به primary ببرد. **جهش:** پین governor به primary صرفِ‌نظر از snapshot → داور بی‌اثر؛ یا حذفِ `_local_quality_ok` → جوابِ طوطی‌وار پاس می‌شود.
**کلاس/هزینه/پیش‌نیاز:** P1 · ۱۰h · B11 پیش‌نیازِ طبیعی + رأیِ مالک برای آرمِ ROUTE_SCORER پس از سایه.
