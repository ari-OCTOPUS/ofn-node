## C19 — بازبینیِ متخاصمِ قفلِ تک‌نمونهٔ center.py (پیاده‌شده `8cad399`) · P0 · ۱٫۵h انجام‌شده
> تنها موردِ محورِ ج که **کد دارد** — پس کار «شکستن» است نه «ساختن». فرضِ پیش‌فرض: قفل ناقص است تا خلافش دیده شود. **صفر ویرایشِ دیسک — پچ‌ها فقط در سند.**

**تصحیحِ کهنگی:** ایجنتِ پژوهش «قفل ندارد» گزارش کرد (worktreeِ عقب‌مانده، پیش از `8cad399`). راستی‌آزماییِ زنده: قفل هست، تابعِ واقعی `acquire_singleton(port=None)` در `center.py:2401` (نه `_acquire_singleton_lock`ِ نگاشتِ ایجنت). **قفل روی شاخه است ولی merge/restart نشده** — تا `RESTART-PROCESS.ps1 center`، پروسهٔ زندهٔ فعلی هنوز بی‌قفل است.

**کدِ واقعی (خلاصه):** `CENTER_LOCK_PORT` پیش‌فرض ۸۷۷۶، env `TG_CENTER_LOCK_PORT` (`:2397`)؛ `SO_EXCLUSIVEADDRUSE` بدونِ `SO_REUSEADDR` (`:2416-2417`)؛ تشخیصِ in-use = `errno in (48,98,10048)` **یا** `"use" in str(exc).lower()` (`:2422`)؛ شاخهٔ سومِ `error:` **fail-open** (بی‌قفل ادامه می‌دهد + alert، `:2459-2465`)؛ `_SINGLETON_SOCK` فقط وقتی `port is None` سراسری می‌شود (`:2425-2426`). در `__main__` قفل **اول** گرفته می‌شود (`:2440`) پیش از `Center()`/`wired()`/`stopped()`/`snapshot_boot`/`run_forever`؛ روی in-use اگر pulse >180s کهنه باشد alert بعد `sys.exit(0)` (`:2441-2458`). تست: `test_tg_center.py:629-659` (پورتِ ۸۹۰۱، رفتار + callsite + نبودِ رشتهٔ REUSEADDR).

**هشت سؤالِ متخاصم — یافتم: پنج نقصِ واقعی، هیچ‌کدام بلاکر، همه hardening.**

**پچِ hardening (در-سند، دیسک را لمس نکن) — سؤال ۳:**
```
# center.py:2422 — fallback فقط وقتی errno غایب است:
-        if getattr(exc, "errno", None) in (48, 98, 10048) or "use" in str(exc).lower():
+        _errno = getattr(exc, "errno", None)
+        if _errno in (48, 98, 10048) or (_errno is None and "use" in str(exc).lower()):
             return None, "in-use"
```
**گاردِ تقویت‌شده (رفعِ M1/M2/M3):** به `t_center_has_a_real_singleton_lock` سه assert اضافه شود: (۱) بلوکِ in-use در `__main__` شاملِ `sys.exit` است (نه فقط ترتیب)؛ (۲) مسیرِ `port is None` واقعاً `_SINGLETON_SOCK` را ست می‌کند (acquireِ واقعی روی پورتِ آزاد، غیر-None، بعد close)؛ (۳) گرپِ optvalِ عددیِ REUSEADDR (`SO_REUSEADDR` **و** الگوی `setsockopt(1, 2,`). **جهشی که هرکدام را قرمز می‌کند = دقیقاً M1/M2/M3.**
**کلاس/هزینه/پیش‌نیاز:** P0 · ۱٫۵h (قفل انجام‌شده) + ~۰٫۵h گاردِ تقویت‌شده · restart center + رأیِ merge؛ **هشت سؤال، پنج نقصِ hardening — صفر بلاکر.**

## C21 — run_all اسکورینگ: پاسِ اول capture نمی‌شود → exit-120 تستِ سالم را «قرمز» و capability را بی‌جهت revoke می‌کند · P1 · ۰٫۵h
**وضع:** `run_all.py:620` پاسِ اول را با `subprocess.run` **بدونِ** `capture_output` می‌دواند → هر ~۳۶۶ ساب‌پروسه کنسولِ مشترکِ والد را inherit می‌کند؛ فقط پاسِ دومِ لرزش‌سنج (`:634`) capture می‌کند. `:621-622` قبل از retry به failed اضافه می‌کند و چیزی حتی با retryِ سبز برش نمی‌دارد؛ `:663-665` روی هر failed غیرخالی capability را revoke می‌کند.
**شکاف:** exit code 120 (شکستِ flushِ stdout مفسر هنگام خروج زیرِ فشارِ کنسولِ مشترک) با AssertionError یکسان شمرده می‌شود. شاهد: `_ops/tests/_flaky` از ۴۱ رکورد **۳۳** تا `exit(1)=120 exit(2)=0` (سبزِ پاسِ دوم) — یعنی ۳۳ تستِ سالم در یک اجرا «قرمز» شدند. جهتِ خطا امن است (money بسته می‌ماند، CAPABILITY-OK/LIVE-ENABLED هر دو غایب)، ولی go-liveِ مشروع را می‌تواند بی‌دلیل مسدود و «ارگانیسم خراب است» را دروغ اعلام کند. **کالیبراسیون:** سه گاردِ نمونه (test_orphan_scan، test_leg_parity، test_command_discoverability) واقعاً دندان دارند — مشکل «گاردِ بی‌دندان» نیست، «اسکورِ لرزانِ رانر» است.
**پیشنهاد:** پاسِ اول را هم capture کن تا هر بچه روی pipeِ اختصاصی flush کند و به دستهٔ مشترکِ کنسول نخورد (همان چیزی که پاسِ دوم را سبز می‌کند). هم false-red را می‌بندد هم revokeِ بی‌جهت را.
**پچِ پیشنهادی (`run_all.py:620`):**
```
-        r = subprocess.run(cmd, cwd=str(p.parent), timeout=300)
-        if r.returncode != 0:
+        r = subprocess.run(cmd, cwd=str(p.parent), timeout=300,
+                           capture_output=True, text=True,
+                           encoding="utf-8", errors="replace")
+        sys.stdout.write(r.stdout or "")
+        if r.returncode != 0:
+            sys.stderr.write(r.stderr or "")
             failed.append(label)
```
**گارد:** تستی که تأیید کند رانر روی exit≠0 که در retry سبز شود مارکر را revoke نمی‌کند؛ یا بچه‌ای که >64KB روی stdout بنویسد و exit 0 دهد باید pass شمرده شود. **جهش:** حذفِ `capture_output` از خط ۶۲۰ → بچه زیرِ بار 120 می‌دهد، pass→fail.
**کلاس/هزینه/پیش‌نیاز:** P1 · ۰٫۵h · هیچ — تغییرِ محلیِ رانر، درختِ زنده را لمس نمی‌کند.

## C25 — بهداشتِ مخزن: ۵۰۰ فایلِ untracked-not-ignored، هیچ سیاستِ خطِ پایان در .gitattributes، .zcode گیت‌نشده · P1 · ۱h
**وضع:** `git status --others --exclude-standard` = **۵۰۰** فایل نه tracked نه ignored. `.gitattributes` فقط «*.md merge=union» دارد — هیچ eol policy. خطِ پایان مخلوط: `organism.py`=CRLF، `cortex.py`/`server.py`=LF، همهٔ .bat/.cmd/.ps1=CRLF. `.zcode/` در .gitignore نیست.
**شکاف:** سه خطر: (۱) روی این درختِ مشترک (دو جلسهٔ موازی) یک `git add -A` هر ۵۰۰ را stage می‌کند — اسکرچِ ایجنت، حالتِ رانتایم، آشغالِ تستِ Ziman، سورسِ untracked؛ بزرگ‌شدهٔ همان تلهٔ tokens.md. (۲) بدونِ `*.bat/*.cmd text eol=crlf`، هر ابزاری که فایل را LF کند (تلهٔ ثبت‌شدهٔ Edit) بی‌صدا cmd را خراب می‌کند و git محافظت نمی‌کند. (۳) آرتیفکت‌های کهنه (مثل `_flaky` ۰۷-۲۸) به‌عنوان «حقیقتِ فعلی» غلط‌خوانی می‌شوند — نمونهٔ همین جلسه: `_flaky/command_discoverability` قرمز ولی سورسِ ۰۷-۲۹ سبز.
**پیشنهاد:** چک‌لیست: (الف) هرگز `git add -A` روی درختِ مشترک — فقط `git add <path>` یا `-p`؛ قبل از commit همیشه `git ls-files --others --exclude-standard | wc -l` و `git check-ignore`. (ب) `.gitattributes`: `*.bat/*.cmd/*.ps1 → text eol=crlf`. (ج) `.zcode/` و دایرکتوری‌های اسکرچ/state به `.gitignore`. (د) آشغالِ تست به `_Archive` (طبق «حذف نکن، منتقل کن»).
