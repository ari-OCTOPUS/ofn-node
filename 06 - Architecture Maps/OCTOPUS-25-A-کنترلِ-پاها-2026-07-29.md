**کلاس/هزینه/پیش‌نیاز:** P2 · ۶h · A2 (outbox_bridge) + منبعِ حقیقتِ واحدِ برچسبِ پا.

## A9 — باگ‌های نهفتهٔ tg_api (دکمه‌های رأی) · P1 · مجموعاً ~۱h
- **A9-1 — `_scrub_keyboard` کیبوردِ dict-شکلِ bridged را بی‌صدا حذف می‌کند (دکمه‌ها ناپدید):** `center._bridge_to_organism` کلِ markup dict (`{"inline_keyboard": [[...]]}`) را verbatim به `keyboard=kb` می‌دهد (`center.py:954-957`)، ولی `_scrub_keyboard` (`tg_api.py:84-91`) `list[list[dict]]` فرض می‌کند؛ روی dict حلقه کلیدهای رشته‌ای→کاراکترها→`dict('i')`→ValueError→`except`→`[]`. نتیجه: `reply_markup={"inline_keyboard": []}` — هر دکمه حذف، بی‌خطا. **تنها گارد** (`test_bridge_buttons.py`) یک fake client تزریق می‌کند که `_scrub_keyboard`ِ واقعی را هرگز نمی‌دواند، پس سبزِ کاذب. آسیب به سطحِ `/queue، /doctor، /money` (approve/reject/vote، ~۲۹ ردیفِ دکمه). **تأییدِ زنده ۰۷-۲۹: هنوز باز است** (`tg_api.py:84-91` هیچ unwrap ندارد). `doctor_link._keyboard:103` کارِ درست را می‌کند (extract `["inline_keyboard"]`) — پل صرفاً همان unwrap را ندارد.
  **پچِ پیشنهادی:**
  ```
   def _scrub_keyboard(keyboard) -> list:
  +    if isinstance(keyboard, dict):
  +        keyboard = keyboard.get("inline_keyboard")
       try:
           return [[{**dict(b), "text": _scrub(str(dict(b).get("text", "")))}
  -                 for b in row] for row in keyboard]
  +                 for b in row] for row in (keyboard or [])]
  ```

  **گارد:** تستی که `_scrub_keyboard`ِ **واقعی** را با `{"inline_keyboard":[[{...}]]}` بدواند و assert کند ۱ ردیف (نه []). **جهش:** حذفِ خطِ isinstance → دوباره []. P1·۰٫۵h · additive، byte-identical برای callerهای rows-list.
- **A9-2 — `callback_data` از سقفِ ۶۴-بایتِ تلگرام سرریز می‌کند به‌محضِ آرمِ `OCTOPUS_WIRE_CB_TOKEN`:** بدترین حالت `ap:ok:`(6)+jid[:48]+`:`(1)+token(20) = ۷۵B > ۶۴؛ تلگرام کلِ sendMessage را با ۴۰۰ رد می‌کند (کلِ کارت گم، نه یک دکمه). jid قابلِ‌کوتاه‌شدن نیست چون handler دقیقاً `aps_mod.get(jid)` را lookup می‌کند (`center.py:2040`). فلگ امروز خاموش → نهفته. **پیشنهاد:** `_TOKEN_LEN` را از ۲۰ به ۹ کاهش بده: 6+48+1+9=64 (lookup-safe؛ token خودش defense-in-depth است — is_owner + single-use گاردهای اصلی‌اند). جایگزینِ امن‌ترِ owner-choice: تولیدِ job-id را به ≤۳۷ کاراکتر cap کن. **گارد:** تست با `CB_TOKEN=1` + secret + id ۴۸-کاراکتری، assert هر callback_data ≤۶۴B (امروز ۷۵B). **جهش:** بازگرداندنِ `_TOKEN_LEN=20`. P1·۰٫۵h · فقط وقتی فلگ آرم شود؛ رأیِ مالک روی trade-offِ امنیتی.
