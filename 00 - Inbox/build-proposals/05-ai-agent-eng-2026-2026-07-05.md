## ۱. یافته‌های کلیدی (۵ محور، هرکدام منبع‌دار)

### محور ۱ — توپولوژیِ ارکستراسیون (Orchestration)
- سه توپولوژیِ غالبِ ۲۰۲۶: **supervisor/hierarchical** (روترِ مرکزی؛ ~۷۰٪ استقرارهایِ production)، **orchestrator-worker**، و **swarm/mesh** (peer، بدونِ مرکز). توصیهٔ عملی: «با supervisor شروع کن؛ فقط وقتی داده نشان داد latency گلوگاه است و misroute کم است به swarm برو». [1][2]
- **اقتصادِ توکن (صریح):** multi-agentِ مستقل ~**۵۸٪** سربارِ توکن، متمرکز ~**۲۸۵٪** — پس multi-agent فقط وقتی صرف می‌کند که کار واقعاً از specialization/parallelism/critique سود ببرد، نه به‌عنوان پیش‌فرض. [2]
- **گپِ نو (در spec نیست):** دقتِ routing در supervisor بعد از **۸–۱۲ round-trip** افت می‌کند چون تاریخِ پیامِ زیرایجنت‌ها، state جاری را از context بیرون می‌راند. [2]

### محور ۲ — Context Engineering و حافظه
- گذارِ رشته‌ای: در ۲۰۲۶ مهارتِ هستهٔ AI-eng از «نوشتنِ prompt بهتر» به **«طراحیِ معماریِ اطلاعات»** منتقل شده؛ به‌گفتهٔ Cognition ریشهٔ اکثرِ شکست‌ها **معماریِ context** است نه واژه‌بندیِ دستور. [3][4]
- **چهار failure-mode تشخیصی:** Poisoning · Distraction · Confusion · Clash. **چهار اهرمِ طراحی:** Write · Select · Compress · Isolate. [3][4]
- **اهرمِ بودجه (مستقیماً به AU$30 مربوط):** دادهٔ production آنتروپیک — context-editing مصرفِ توکن را **۸۴٪** کم و کارایی را **۲۹٪** بهتر کرد؛ با memory-tool تا **۳۹٪**. [3]
- **ریسکِ نوِ غیرِ adversarial:** «safety-constraint loss در حینِ compaction» — خلاصه‌سازیِ روتین می‌تواند بی‌صدا دستورِ ایمنیِ حیاتی را دور بیندازد. [3]

### محور ۳ — Eval و Observability
- **LLM-as-judge** سوگیریِ length/position/self-preference دارد، non-deterministic است، و یک call کامل per-turn **بیش‌ازحد کند/گران** است. راهِ production: eval آنلاین با **classifierِ سریع (میلی‌ثانیه)** + judgeِ گران فقط روی **نمونهٔ trace‌ها** (offline/sampled). [5]
- Observabilityِ ایجنتی ≠ مانیتورینگِ سنتی: باید حلقه‌هایِ چندگامیِ استدلال، tool-callها و گذارهایِ state را در کلِ session رهگیری کند؛ استانداردِ عملی = tracing سازگار با **OpenTelemetry** (span/generation/retrieval/tool-call) + judgeِ نمونه‌ای برای گرفتنِ semantic drift هفته‌ها قبل از شکایتِ کاربر. [5][6]

### محور ۴ — امنیت / opsec
- **prompt injection** ریسکِ شمارهٔ‌یکِ ۲۰۲۶ است و **دفاعِ کاملاً قابل‌اتکایی وجود ندارد**. تهدیدِ خطرناک‌تر: **indirect/delayed injection** — منبعِ دادهٔ مسموم، context ذخیره‌شده را آلوده می‌کند و ایجنت **روزها/هفته‌ها بعد** دستورِ مخرب را اجرا می‌کند. [7]
- چون دفاعِ کامل نیست، مهارِ بادوام = «ایجنتِ compromiseشده اصلاً نتواند اقدامِ high-impact کند»: دسترسیِ ابزار **default-deny**، اعتبارنامه‌هایِ **کوتاه‌عمر و scoped**، و **human-in-the-loop روی اقداماتِ برگشت‌ناپذیر**. [7]
- ۷۸٪ استقرارها **enforcementِ سیاستِ قطعی** روی tool-callهایِ پرخطر ندارند؛ least-privilege باید نه‌فقط به‌ازای role بلکه به‌ازای **task و کوتاه‌ترین پنجرهٔ زمانی** scope شود. [7]

### محور ۵ — حاکمیت و قابلیت‌اطمینان (Governance / Reliability)
- **حاکمیتِ ریسک‌محور:** low-risk با نظارتِ حداقلی · medium-risk با logging + چکِ خودکار · high-risk با **تأییدِ انسانی** (هم‌راستا با EU AI Act مادهٔ ۱۴: رابطِ نظارتِ انسانی برای سیستم‌هایِ پرخطر). [1]
- ایجنت را **مؤلفهٔ سیستمِ توزیع‌شده** بدان: جداسازیِ لایه‌هایِ reasoning / action / validation به‌جای hard-code کردنِ منطق داخلِ prompt → شکنندگیِ کمتر، iterationِ مستقل. [1][8]
- واقعیتِ میدانی: **۶۸٪** ایجنت‌هایِ production حداکثر **۱۰ گام** پیش از دخالتِ انسانی اجرا می‌کنند؛ تیم‌ها عامدانه autonomy را محدود می‌کنند تا پایداری بماند. [1][8]

## ۳. Cross-domain

> **مرزِ اعتمادِ حافظه** مستقیماً به **Crypto** (اندامِ ۳ — تنها نامزدِ bounded-auto SELL؛ یک digestِ مسموم می‌تواند قاعدهٔ exit را بایاس کند) و **Project-F** (بهداشتِ حافظه = حریمِ خصوصی؛ ماسکِ نام/پلتفرم نباید در ردیف‌های auto نشت کند) وصل می‌شود؛ اندامِ افقیِ مسئولِ هر دو = **EffectorGate + Anchor Ledger** (§۳). یعنی یک مهارِ واحدِ حافظه، هم‌زمان دو دامنه را پوشش می‌دهد — همان «یک رشته، چند node»یِ *Armillaria* [J].

## ۴. پیشنهادِ عملیِ بهبودِ معماری (P-05) — «مرزِ اعتماد + بلوکِ ثابتِ نامتراکم‌پذیر»

**چرا این یکی (نه بقیه):** بالاترین blast-radius برای سیستمی که تنها کارِ فعلی‌اش **ماندن در propose-only** است. هر دو گپِ نوِ محورِ ۲/۴ روی یک مسیرند: **حافظه → دستور**. یک مهارِ واحد هر دو را می‌بندد. کم‌هزینه (فقط سند + یک re-read)، برگشت‌پذیر، بدونِ فعال‌سازیِ کد.

**این diff پیشنهاد است — اعمال نشد. spec دست‌نخورده.**

### diff الف — §۶ (Memory strategy): افزودنِ زیربخشِ «Trust & Provenance»
- **قبل:** «durable = append-only EXPERIENCE-LEDGER + Anchor Ledger؛ volatile = scout-digestهایِ تبخیرشونده. مسیرِ بازیابی: FTS5 اول، بعد وکتور.»
- **بعد (افزوده):** «هر محتوایِ **تولیدشده توسطِ ناوگان/حلقهٔ خودکار** (scout-digest، ردیفِ auto در ledger، خودِ build-proposals) هنگامِ مصرف در بخشِ **data** قرار می‌گیرد نه **instruction** — به‌عنوان untrusted داده می‌شود، هرگز به‌عنوان دستورِ قابلِ‌اجرا. هر رکورد یک `provenance` (human / fleet-auto) دارد؛ فقط رکوردِ human می‌تواند رفتار را تغییر دهد. مهارِ **indirect/delayed prompt injection** [7].»

### diff ب — §۰.۳ (invariants) + §۷: بلوکِ ثابتِ نامتراکم‌پذیر (constitution block)
- **قبل:** invariantها به‌صورتِ متنِ عادیِ §۰.۳ فهرست شده‌اند.
- **بعد (افزوده):** «چهار invariant — (۱) Security Gate=propose-only تا rotation · (۲) CHARTER immutable · (۳) در شک read-only · (۴) هیچ اقدامِ برگشت‌ناپذیرِ بی‌verdict — یک **constitution block** هستند که در هر اجرا **دوباره تزریق** می‌شود و از compaction/summarization **معاف** است؛ + یک **startup-check** که گیت را از منبع ([[ROTATION_CHECKLIST]]) دوباره می‌خواند. مهارِ **safety-constraint loss در حینِ compaction** [3].»

### diffهایِ ثانویه (کاندیدا؛ برای verdict، این اجرا اعمال/بسته نشد)
- **§۶ Eval → دولایه:** classifierِ سریعِ آنلاین (per-turn، میلی‌ثانیه) + LLM-as-judgeِ گران فقط روی نمونهٔ trace‌ها؛ سازگار با سقفِ AU$30. پالایشِ «rubric ≥۱۲/۱۶ blind». [5]
- **§۲ ریسکِ نو:** «routing decay بعد از ۸–۱۲ hop» → سقفِ hop یا فشردهٔ تاریخِ زیرایجنت. [2]
- **§۶ Model selection:** ذکرِ عددِ صریحِ سربار (~۵۸٪/۲۸۵٪) و اهرمِ context-editing (۸۴٪↓) به‌عنوان شواهدِ کمّیِ موجود. [2][3]

## ۵. Trade-off پیشنهادِ P-05 (نمرهٔ ۱–۱۰)

| بعد | نمره | توضیح |
|---|---|---|
| Cost | ۹ | فقط متنِ spec + یک re-read در بوت؛ صفر هزینهٔ API افزوده |
| Complexity | ۳ | کم — یک قاعدهٔ provenance + یک بلوکِ ثابت |
| Scalability | ۸ | با رشدِ ناوگان اهمیتش بیشتر می‌شود (سطحِ حمله بزرگ‌تر) |
| Maintainability | ۸ | سند-محور، هم‌راستا با SDD همین vault |
| Security | ۹ | مستقیماً دو گپِ high-blast-radius را می‌بندد |
| Time-to-Impl | ۹ | یک ویرایشِ §۶/§۰ (با verdict) + یک خطِ startup-check |

**ROI: بالا** — کم‌ترین هزینه، بیشترین کاهشِ ریسکِ escalationِ خاموش. هم‌راستا با «در شک read-only» (P8).
