# Self-improvement proposal — 2026-07-04 (live kickoff)

## Backlog item picked

**R-08 — Link/consolidate the two audit chains** (from `REFACTOR_PLAN.md`, finding P5-01).

Why this one, over the higher-ranked approved items (R-01…R-05): those five are *code fixes with a fixed, obvious answer* — fail-closed, add a timeout, wire or delete a call. They need engineering, not research. R-08 is different: it is a genuine *design* question — "how do you weld two independent append-only logs (the unsigned main `AuditLog`/tracing chain and the signed kernel HMAC chain) into a single end-to-end-authenticated timeline?" — and it is exactly the kind of question where comparable systems (Certificate Transparency, agent-OS audit trails) have already converged on a known-good pattern. It is also the *keystone of the whole "signed ledger" cluster*: the sequencing note in the plan says R-02 and R-08/R-15 should be reviewed together, and R-08 is what makes R-02's signed human verdict actually provable against the main timeline rather than an island. Getting the shape of R-08 right de-risks four other items (R-02, R-09, R-15, and the P5-01 gap itself) for the price of one design decision.

## Prior art / findings

- **The target shape is a "graph of signed, linked events," not a bigger log.** The clearest statement of the goal: a useful audit trail is *"a graph of signed, timestamped, linked events where every node can be verified independently of the party that generated it"* — precisely so overseers can trace an outcome back through the chain to the root decision. That is the acceptance test R-08 should aim at. [nono.sh — tamper-evident audit trail for AI agents](https://nono.sh/blog/secure-agent-audit) · [Sakura Sky — verifiable audit logs](https://www.sakurasky.com/blog/missing-primitives-for-trustworthy-ai-part-5/)
- **The canonical two-log linking primitive is the *consistency proof* / cross-reference, borrowed from Certificate Transparency.** In RFC 6962, a log's authenticity is not just per-entry — it is a signed tree head (STH) plus a *consistency proof* showing the new head is an append-only extension of a prior one; parties gossip STHs so no log can present a "split view." The direct analogue for us: each record in the unsigned main chain should carry the *kernel seq + signature* for the same event (this is verbatim the fix P5-01 suggests), so the two chains become mutually referential and a split between them is detectable. [RFC 6962 — Certificate Transparency](https://datatracker.ietf.org/doc/html/rfc6962)
- **A cheap, self-hostable "witness" already fits the vault's plan and closes the trust gap without the public network.** A witness cosigns a checkpoint *only after verifying the consistency proof* against checkpoints it previously signed — turning "trust the log operator" into "trust an independent second signer." For a small private ledger the realistic path is a self-run witness (the vault's own SCOUT ③ OTS/git-remote anchors already play this role), consistent with the earlier finding that joining the public Witness Network is the wrong fit for a niche private log. [transparency.dev — Can I Get A Witness (Network)?](https://blog.transparency.dev/can-i-get-a-witness-network)
- **Agent-OS implementations show the concrete record format to copy: SHA-256 hash-chain + Merkle proofs per action.** OpenFang / the Hermes-agent proposal implement a Merkle hash-chain audit trail where each entry chains to the previous via SHA-256, and any single action can be proven present via a Merkle proof without replaying the whole log. This is the record schema R-08 (and R-15's "widen the hash to full SHA-256") should adopt for the *linked* records. [NousResearch/hermes-agent #487 — Cryptographic Audit Trail](https://github.com/NousResearch/hermes-agent/issues/487)
- **The specific weak spot this fixes is the industry-recognized failure mode of agent frameworks.** The shared flaw across agentic frameworks is that inter-agent events "live in volatile memory, are persisted as unsigned text, and can be rewritten by the administrator at any time." The vault already *has* a signed kernel chain — R-08 is simply the step that makes the *unsigned* main timeline inherit that guarantee by binding to it, instead of leaving two logs that can silently disagree. [Sakura Sky — missing primitives, part 5](https://www.sakurasky.com/blog/missing-primitives-for-trustworthy-ai-part-5/)

## Proposal (needs Ari's verdict)

**PROPOSAL — not applied. This is a design sketch for R-08; do not implement without approval, and treat it as audit-ledger surface (`HUMAN-APPROVAL-REQUIRED`).**

Adopt the Certificate-Transparency-style **cross-reference + consistency** model to link the two chains, in three small, reviewable steps:

1. **Cross-stamp, don't merge.** Keep both chains as-is (do not collapse them — that would risk the frozen-invariant property of the kernel). Instead, when an event is written to the kernel's signed HMAC chain (`igk/kernel.py`), have it return `(seq, sig)`; the corresponding main-chain record in `src/tracing.py` embeds that `kernel_seq` + `kernel_sig`. Result: every safety-relevant main-log record is now *anchored* to a signed kernel record for the same event — the "graph of linked, signed events" shape from the prior art.
2. **Verifier checks both directions.** The dashboard/verifier (`dashboard.py`) recomputes the main hash-chain **and** re-verifies each embedded `kernel_sig` against the kernel chain, and flags any main record whose referenced kernel seq is missing/inconsistent (a "split view" between the two logs). This is the concrete P5-01 "authenticated end to end" check.
3. **Pairs with R-15 for free.** Because the linked records now carry a real cryptographic reference, widen the main chain's 64-bit hash to the full SHA-256 digest (R-15) *in the same design*, so the linked field isn't the weakest part of the chain.

This is deliberately the *minimum* that satisfies the goal and stays inside the plan's guardrails: no new kernel verb, no key/invariant mutation, no change to the frozen red-team surface. It also front-loads the exact structure R-02 needs (the signed human verdict just becomes another cross-stamped event), which is why the plan already says to review R-02 and R-08 together.

## Risks / trade-offs

- **Ordering / partial-write skew.** If the process crashes between writing the kernel record and the main record, the two chains disagree by one entry. Honest mitigation: the verifier must treat a *dangling* kernel record (signed, but no main reference yet) as benign-pending, and only a *contradicting* reference as tampering — otherwise normal crashes look like attacks. This overlaps R-13 (crash-reconcilable state); flag the dependency.
- **Kernel-adjacent surface.** Even though the proposal adds no new verb, it changes what `kernel.audit` returns and touches `tracing.py` + `dashboard.py` — the plan's rule "each approval-flagged item lands in its own reviewed change" applies. Do **not** batch with hygiene items.
- **Sequencing discipline.** R-08 should not start until R-01…R-05 land and are re-audited (explicit plan rule). This note is a *design pre-stage* only, so it can be reviewed now without violating that.
- **Over-engineering risk.** Full CT (gossip network, external witnesses, STH publication) is more than a single-owner private vault needs. The proposal intentionally takes only the *cross-reference + consistency-check* idea and reuses the already-planned OTS/git-remote anchors as the "witness," rather than standing up new infrastructure.
