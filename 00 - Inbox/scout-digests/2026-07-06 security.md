# Security Scout — 2026-07-06

## سؤال امروز

اولین دیجست این اسکات (no prior digest to dedup against). سؤال: در معماری MCP که همین ناوگانِ اسکات‌ها روی آن اجرا می‌شود، حملات «tool poisoning»، «rug pull» و «tool shadowing» چطور کار می‌کنند و OWASP/Anthropic چه دفاع مشخصی توصیه می‌کنند؟ — این مستقیماً به خودِ زیرساختی که این اسکات را اجرا می‌کند برمی‌گردد (اسکات با ده‌ها ابزار MCP متصل کار می‌کند).

## یافته‌ها

**۱. Tool Poisoning — دستور مخرب داخل schema، نه فقط description.**
دستورهای مخرب می‌توانند در description، نام پارامتر، type، یا حتی return schema ابزار پنهان شوند — نه فقط در متن description. OWASP توصیه می‌کند کل schema به‌عنوان سطح حملهٔ injection دیده شود، نه فقط فیلد description.
[OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)
**برای vault یعنی چه:** هر MCP جدید که برای ناوگان اسکات‌ها وصل می‌شود (fleet در حال گسترش با کانکتورهای تخصصی) باید کل تعریف tool را بازبینی کند، نه فقط توضیح یک‌خطی — بازبینی سطحی کافی نیست.

**۲. Rug Pull — تغییر بی‌صدای ابزار بعد از تأیید اولیه (CVE-2025-54136 / MCPoison).**
یک MCP server می‌تواند بعد از تأیید اولیهٔ کاربر و اجرای تمیز چند هفته‌ای، آپدیتی بفرستد که description/دستور را عوض می‌کند؛ چون spec نیازی به re-approval روی تغییرِ description ندارد، host بی‌صدا لود می‌کند. مورد واقعی: Cursor کلید config تأییدشده را دوباره اجرا می‌کرد حتی بعد از عوض‌شدنِ دستورِ پشتِ آن کلید.
[Rug Pull Attack Explainer — CVE-2025-54136](https://www.practical-devsecops.com/glossary/rug-pull-attack-in-mcp/)
**برای vault یعنی چه:** هیچ تضمینی نیست که کانکتوری که هفتهٔ پیش امن بود امروز هم همان است. دفاع مشخص: hash-pin تعریف هر tool (SHA-256 روی name+description+schema)، و re-hash قبل از هر اجرا؛ mismatch = alert و block تا بازبینی.

**۳. مقیاس مسئله در ۲۰۲۶ — از خطر تئوریک به واقعیت آماری.**
بین ژانویه و فوریهٔ ۲۰۲۶، محققان بیش از ۳۰ CVE علیه MCP serverها/clientها ثبت کردند (۴۳٪ shell injection). Unit 42 (Palo Alto) نشان داد با ۵ MCP server متصل، یک سرورِ compromised به نرخ موفقیت حملهٔ ۷۸.۳٪ می‌رسد — یعنی **تعداد کانکتور بالا خودش ریسک را ضرب می‌کند**، نه فقط کیفیت تک‌تک آن‌ها.
[OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/)
**برای vault یعنی چه:** این جلسهٔ Cowork با ده‌ها MCP وصل کار می‌کند (base44، buildkite، cockroachdb، fastly، monday، tavily، …). سطح حمله با تعداد کانکتور رشد می‌کند؛ یک کانکتور کم‌استفاده و بی‌بازبینی می‌تواند دروازهٔ کل ست شود.

**۴. Tool Shadowing / Confused Deputy — یک سرور مخرب می‌تواند رفتار ابزارهای سرورهای دیگر را دستکاری کند.**
چون LLM همهٔ tool descriptionهای همهٔ سرورهای متصل را در یک context می‌بیند، یک description مخرب در سرور A می‌تواند نحوهٔ استفادهٔ agent از ابزار سرور B (حتی معتبر) را عوض کند. علاوه بر آن، سرور معمولاً با پرمیشن گسترده‌ی خودش اجرا می‌کند، نه پرمیشن واقعی کاربر (confused deputy).
[OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)
**برای vault یعنی چه:** هر سرور MCP باید domain امنیتی مستقل فرض شود؛ جریان داده بین سرورها (مثلاً credential سرور A که در فراخوانی سرور B ظاهر شود) باید مانیتور شود.

**۵. دفاع مشخص و عملی برای اپراتور تک‌نفره — least privilege + human-in-the-loop + عدم اعتماد به return value.**
پیشنهاد مشخص: (الف) least privilege در سطح *tool*، نه فقط سرور (توکن read-only جدا از توکن نوشتن). (ب) هرگز tool call حساس/مالی/destructive را auto-approve نکن — پارامترهای کامل را نشان بده. (پ) خروجی هر ابزار را «ورودی نامعتبر» فرض کن — الگوهای امری مثل «ignore»/«forget»/«send to» در خروجی را log و alert کن، پیش از تزریق به context مدل. (ت) ابزار `mcp-scan` (Invariant Labs) برای تشخیص خودکار poisoning/shadowing.
[MCP Spec — Security Best Practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices)
**برای vault یعنی چه:** این دقیقاً همان الگویی است که Security Gate این vault («autonomy = read-only تا CRITICALهای rotation بسته شود» + استثنای نوشتن-فقط-در-Inbox برای اسکات‌ها) از قبل پیاده کرده — تأیید مستقل بیرونی که مسیر فعلی درست است، نه صرفاً یک ادعای داخلی.
