# Scout: tools — 2026-07-06

## سؤال امروز

(ادامهٔ اسپور دیروز) امن‌ترین و کامل‌ترین راه برای دسترسی read/write ایجنت‌های AI به یک vault ابسیدین در ۲۰۲۶ چیست — Local REST API + MCP رسمی، MCP-serverهای community با scoping پوشه‌ای، یا دسترسی مستقیم فایل‌سیستم (روش فعلی خودمان)؛ و چه ریسک امنیتی/prompt-injection مشخصی دارد؟

## یافته‌ها

### ۱. `obsidian-local-rest-api` — اکنون MCP رسمی توکار دارد

پلاگین community کاددینگتون‌بیر یک MCP server توکار روی `https://127.0.0.1:27124/mcp/` سرو می‌کند؛ auth با bearer token (`Authorization: Bearer <api-key>`) روی HTTPS با گواهی self-signed؛ پورت HTTP (27123) پیش‌فرض خاموش است. رایگان/متن‌باز؛ چون فرمت داده فقط Markdown است، **lock-in عملاً صفر** — حذف پلاگین چیزی را قفل نمی‌کند. منبع: [coddingtonbear/obsidian-local-rest-api](https://github.com/coddingtonbear/obsidian-local-rest-api)

**برای ما:** جایگزین بالقوهٔ فایل‌سیستم مستقیم فعلی برای دسترسی ایجنت‌های خارج از Claude (مثلاً یک بات تلگرام مستقل) — ولی رفتار پیش‌فرض آن (طبق منابع MCP.Directory/راهنماهای کامیونیتی) **read/write/delete کامل و بدون‌محدودیت** است مگر صریحاً scope شود؛ برای یک vault تک‌کاربره با کیف‌پول/کلید داخلش، این پیش‌فرض خطرناک است.

### ۲. `mcp-fs-obsidian` (bitbonsai) — همان الگویی که خودمان دستی پیاده کرده‌ایم، ولی enforced در کد

Server سبک با **`OBSIDIAN_READ_PATHS` / `OBSIDIAN_WRITE_PATHS`** (allowlist پوشه‌ای comma-separated، prefix-based با recursion ضمنی) + کلید سراسری `OBSIDIAN_READ_ONLY`؛ رد دسترسی با خطای تایپ‌شدهٔ `path_forbidden`. جلوگیری از path traversal، resolve کردن symlink، whitelist پسوند (`.md/.markdown/.txt/.base/.canvas`)، محافظت فایل مخفی/`​.obsidian`، و validation فرانت‌متر YAML (جلوگیری از خراب‌شدن frontmatter). رایگان/متن‌باز، بدون lock-in. منبع: [bitbonsai/mcp-fs-obsidian](https://github.com/bitbonsai/mcp-fs-obsidian) + [mcpvault.org](https://mcpvault.org/)

**برای ما:** این دقیقاً معادلِ کدشدهٔ قاعدهٔ فعلی «فقط بنویس در scout-digests/» است که الان صرفاً در پرامپت اعمال می‌شود (soft guard). اگر روزی یک ایجنت خارجی (نه Claude خودمان) به vault وصل شود، این پروژه enforcement فنی واقعی می‌دهد نه فقط قول در پرامپت.

### ۳. حادثهٔ واقعی: PHANTOMPULSE RAT از طریق پلاگین‌های Obsidian (آوریل ۲۰۲۶) — نه MCP، ولی هشدار سطح پلاگین

مهاجمان از پلاگین‌های community مثل **Shell Commands** و **Hider** برای اجرای خودکار کد هنگام باز شدن یک vault مشترکِ cloud سوءاستفاده کردند؛ RAT ویندوزی با resolve شدنِ C2 از طریق تراکنش‌های Ethereum. این حمله مسیر REST API/MCP نیست، ولی نشان می‌دهد **سطح حملهٔ واقعی همین امسال، خودِ اکوسیستم پلاگین ابسیدین بوده**، نه فرضی. منبع: [The Hacker News](https://thehackernews.com/2026/04/obsidian-plugin-abuse-delivers.html) + [Elastic Security Labs](https://www.elastic.co/security-labs/phantom-in-the-vault)

**برای ما:** گاردِ عملی — پلاگین `Shell Commands` هرگز روی vault آری نصب/فعال نشود؛ فهرست پلاگین‌های نصب‌شده دوره‌ای ممیزی شود (این خودش یک آیتم برای `security` scout).

### ۴. گزارش OWASP 2026 (از طریق Help Net Security) — اولین MCP server مخرب «در طبیعت» شکار شد

Prompt injection همچنان غالب‌ترین شکست امنیتی عامل‌های agentic در production است؛ در لایهٔ پروتکل، پژوهشگران اولین MCP server مخربِ واقعی را شکار کردند. پیام عملی: **نصب کورکورانهٔ هر MCP server کامیونیتی (حتی برای ابسیدین) خطر تأمین‌زنجیره (supply-chain) دارد**، نه فقط ریسک نظری prompt injection از محتوای نوت. منبع: [Help Net Security](https://www.helpnetsecurity.com/2026/06/11/owasp-prompt-injection-ai-security-failures/)

**برای ما:** هر MCP server ابسیدینی که در آینده نصب شود باید از سورس pin شود (کامیت هش مشخص)، نه `latest`؛ همان قاعده‌ای که برای `_code` architect داریم.

### ۵. permission manifest هنوز استاندارد بالغی ندارد

ایشوی باز روی `smithery-ai/mcp-obsidian` («Review auto-generated MCP permission manifest») نشان می‌دهد حتی manifestِ خودکار مجوزها هنوز در حال بررسی/بلوغ است — یعنی در ۲۰۲۶ نمی‌توان به یک استاندارد permission پخته برای MCP-obsidian تکیه کرد؛ scoping دستی (مثل `mcp-fs-obsidian`) هنوز قابل‌اتکاترین راه است. منبع: [GitHub issue #33](https://github.com/smithery-ai/mcp-obsidian/issues/33)

## ضمیمهٔ عصر (اجرای دوم اسکات، همان روز) — پاسخ اسپور ۲: بله، advisory واقعی وجود دارد

### ۶. GHSA-62gx-5q78-wrvx — path traversal در `obsidian-local-rest-api` (High، ژوئن ۲۰۲۶)

اسپور ۲ صبح دقیقاً هدف خورد: پلاگین Local REST API (همان که یافتهٔ ۱ به‌عنوان جایگزین بررسی کرد) در **۴ ژوئن ۲۰۲۶** یک advisory با شدت High منتشر کرد. مکانیزم: endpointهای `/vault/{path}` مسیر را **بعد از routing** با `decodeURIComponent` باز می‌کنند؛ `../` خام در لایهٔ routing رد می‌شود (404) ولی `..%2F..%2F` (اسلش percent-encoded) از routing عبور می‌کند و تازه در handler به `../` واقعی تبدیل می‌شود — بدون هیچ چک confinement به ریشهٔ vault. نتیجه: کلاینتِ **احرازشده** می‌تواند هر فایلی روی هاست را با سطح دسترسی پروسهٔ Obsidian **بخواند/بنویسد/حذف کند** — یعنی خارج از vault، کل دیسک. نسخه‌های آسیب‌پذیر: `<= 4.1.2`؛ پچ: **4.1.3** (همان روز، 2026-06-04). منابع: [advisory رسمی](https://github.com/coddingtonbear/obsidian-local-rest-api/security/advisories/GHSA-62gx-5q78-wrvx) + [release 4.1.3](https://github.com/coddingtonbear/obsidian-local-rest-api/releases)

**برای ما — سه درس مشخص:**
- **یافتهٔ ۱ صبح باید تعدیل شود:** «lock-in صفر» درست ماند، ولی «امن‌تر چون Obsidian واسطه است» نه — واسطه‌بودن Obsidian خودش surface جدید ساخت. یک باگ decode-after-routing کلاسیک، API «فقط-vault» را به دسترسی کل دیسک تبدیل کرد. اگر روزی این پلاگین نصب شد: حداقل 4.1.3، و ترجیحاً auto-update پلاگین‌ها روشن.
- **مقیاس اکوسیستم:** کاتالوگ community-driven «Vulnerable MCP Project» تا می ۲۰۲۶ بیش از **۵۰ آسیب‌پذیری MCP (۱۳ critical)** ثبت کرده؛ سه‌ماههٔ اول ۲۰۲۶ CVEهای critical در Atlassian MCP (RCE بدون احراز)، AWS MCP (command injection، CVSS 9.8) و FastMCP (SSRF/traversal، CVSS 9.9) داشت؛ ~۴۳٪ کلاس shell-injection. این تأیید کمّیِ درس یافتهٔ ۴ صبح (pin از سورس، نه `latest`) است. منبع: [Obsidian Security — MCP threat inventory](https://www.obsidiansecurity.com/academy/mcp-security-vulnerabilities)
- **اعتبار مجدد وضع فعلی:** دسترسی مستقیم فایل‌سیستم از داخل Cowork (روش فعلی ما) این کلاس باگ شبکه‌ای/HTTP-decode را کلاً ندارد — سؤال باز همچنان فقط سخت‌کردن گاردِ write-scope است (اسپور ۱)، نه افزودن لایهٔ REST.

### اسپور جایگزین برای فردا

آیا مکانیزم auto-update پلاگین‌های community در Obsidian خودش vector امنی است (امضا/integrity check دارد؟) یا پچ‌گرفتن سریع را باید دستی مدیریت کرد — به‌خصوص روی vaultی که ایجنت‌ها رویش کار می‌کنند؟
