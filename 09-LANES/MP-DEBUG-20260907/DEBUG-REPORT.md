## عیب‌ها و وضعیت اصلاح

### D1 — پذیرش EX1 بیش از شواهد گزارش شده بود — باز / مانع ادامهٔ همان دستور

بخش EX1 در v3، تطبیق فیلدهای خام، ابزار from-zero و provenance هر رکورد را می‌خواهد و صریحاً `on_fail: کل lane متوقف` دارد. رسید قبلی خودش سه مغایرت را ثبت کرده، ولی ادامه داده است. بازخوانی مستقل همین فقدان‌ها را تأیید کرد. رکوردها `reason` دارند؛ کلید دقیق `reason_code` در آن‌ها هم موجود نیست.

فقط با روشن‌کردن معیار آینده و تصویب اصلاح صریح work order می‌توان این محدودیت legacy را تعیین تکلیف کرد. وجود receipt-level source/hash جای per-record loaded-source یا خوانندهٔ تصمیم را نمی‌گیرد. **هیچ معیار پذیرشی در این lane شل یا تغییر داده نشد و EX3 آغاز نشد.**

### D2 — seq-monotonic با hash-chain یکی نیست — دامنه تصحیح شد

دو تابع audit_append بررسی‌شده sequence/locking/flush/fsync دارند؛ hash-chain در آن‌ها دیده نشد. تغییر payload قدیمی با حفظ seq می‌تواند از آزمون seq عبور کند. هش snapshot اثرانگشت بایت‌هاست، نه امضای مستقل یا اثبات دست‌نخوردگی تمام تاریخ. تطبیق prefix تازه، نتیجهٔ خوب و محدودِ قبلی را تقویت می‌کند؛ آن را به ادعای قوی‌تر تبدیل نمی‌کند.

### D3 — ارجاع جعلی، عدد را از UNKNOWN خارج می‌کرد — اصلاح candidate

تابع `metric_value_or_unknown` هر مقدار registry غیر None، حتی `{}`، `False`، رشتهٔ خالی یا claim_id ناموجود را می‌پذیرفت. تست مثبت اولیه خودش از ID ناموجود `C-1` استفاده می‌کرد. candidate شکل دقیق ارجاع، ID واقعاً موجود و نوع عددی معتبر را کنترل می‌کند؛ bool، NaN، infinity و غیرعدد UNKNOWN می‌شوند.

این تابع **فقط انسجام registry و شکل عدد را می‌سنجد**. داشتن شرح truth_source، outcome را حل نمی‌کند و finite بودن عدد صحت اندازه‌گیری را ثابت نمی‌کند. calibration_error همچنان مرجع ثبت‌شده ندارد. هیچ reader زنده‌ای به این helper وصل نشده است.

### D4 — YAML متنِ معتبرِ قرارداد را خراب می‌کرد — اصلاح candidate + بازبینی مستقل

ID عددنما/booleanنما به نوع دیگری تبدیل می‌شد؛ colon/newline خطای parser ایجاد می‌کرد؛ CR/LF و فاصله‌های معنادار در شرح‌ها حفظ نمی‌شد. تست‌های منفی این موارد را بازتولید کردند. بازبین مستقل در اصلاح اولیه یک مورد Unicode غیر BMP (مانند ایموجی اختاپوس) نیز یافت؛ مجموعهٔ Unicode جدا اضافه شد. خروجی نهایی باید هم UTF-8-پذیر و هم round-trip دقیق همهٔ رشته‌های پذیرفته‌شده باشد؛ تعداد و نتیجهٔ نهایی در TEST-RECEIPT.json مرجع است.

### D5 — قفل‌ها parity مولد را آزمایش نمی‌کردند — تست اضافه شد

در baseline واقعی، فایل YAML، خروجی مولد و pinها **همین حالا برابر بودند**؛ drift موجود ادعا نمی‌شود. ضعف این بود که تغییر CLAIMS همراه با refresh فقط قفل Python می‌توانست registry کهنه را سبز نگه دارد. تست مستقیم generator bytes == canonical stored bytes اکنون اضافه شده و باید بدون deselect در اجرای نهایی سبز باشد. خط اول FROZEN.lock و runtime_truth_v1 تغییر نکرده‌اند.

### D6 — جهت مولد با v3 متفاوت است — باز، بدون تغییر خودسرانهٔ طراحی

دستور `ops/verifiable_claims.yaml → contracts/claim_v1.py` می‌خواهد؛ پیاده‌سازی Python را منبع و YAML را خروجی گرفته است. نبود PyYAML روی برد الزاماً مانع code generation روی لپ‌تاپ نیست. این deviation مستقل از سه اصلاح محلی است و در این lane پنهان یا پذیرفته فرض نشده. برای EX2 مطابق v3، جهت مقرر باید پیاده شود یا تغییر طراحی صریحاً تصویب شود.

### D7 — قراردادِ شرح حقیقت هنوز verifier و outcome نیست — باز

سه claim شرح مرجع دارند، ولی هیچ verifier واقعی از آن‌ها اجرا نشده و هیچ outcome حل‌شده/مصرف‌کنندهٔ بعدی در این lane اثبات نشده است. C3 برای داوری دربارهٔ cap/lock در لحظهٔ تصمیم به snapshot مقید به همان تصمیم نیاز دارد؛ خواندن lock فعلی برای تصمیم قدیمی کافی نیست. نتیجهٔ آزمون واحد را به بهبود علمی، اثر تجاری یا سلامت شاهد ۱۸۲ تبدیل نکن.

### D8 — ضعف قدیمی RuntimeTruthRow خارج از تغییر EX2 — باز / lane جدا

در قرارداد frozen قبلی، `readers=("",)` می‌تواند LIVE را رد نکند؛ رشتهٔ تنها به حروف serialize می‌شود؛ list ورودی قابل‌تغییر پس از ساخت، شرط no-readers-no-LIVE را دور می‌زند. بعضی provenanceهای خالی هم پذیرفته می‌شوند. بازتولید مستقل انجام شد، اما این قرارداد و pin قبلی دست‌نخورده‌اند. تغییر آن نیازمند مرور schema/caller و regression مستقل است، نه refresh خاموش قفل ضمن EX2.

## دانش معماری که باید حفظ شود

اختاپوس یک repo یا daemon نیست. مسیر معنادار آن: **signal → producer → state/event → consumer → policy/authority → effect → receipt → outcome → تصمیم بعدی**. این بررسی در سه مرز عیب یافت: «مشاهده به ادعا»، «قرارداد به شاهد واقعی» و «کد merge‌شده به کدِ اجراشده». افزوده‌شدن متن/تست/پروسس، این مرزها را خودبه‌خود نمی‌بندد.

نقش تاریخی قلب/مغز/شاهد راهنمای فهم است، نه آدرس‌دهی زنده. برای ۱۸۲ فرض retired یا active از atlas قدیمی استخراج نکن. دادهٔ زندهٔ ۱۳۸ و ۱۸۰ این lane محدود است؛ همهٔ business legها، تاب‌آوری، حلقه‌های کامل و production migration از ابتدا بازآزمون نشده‌اند. دریل A→B قبلی را هم برای پرکردن گزارش دوباره اجرا نکن.
