# U-WORK — مکانیزمِ «کارِ پیش‌بینی‌نشده را بفهم و (با تأیید من) انجام بده»

> پاسخ به سؤال مالک (2026-09-18): «چیکار کنیم در تسک‌های مختلف با تأیید من، کارهای پیش‌بینی‌نشده را تشخیص بده و انجام بده؟»
> وضعیت: قطعات ۱..۴ **الان زنده‌اند** (V1، امشب deploy + تست شد)؛ قطعات ۵..۶ اسپک دارند.

## چرا قبلاً نمی‌شد (علتِ ریشه‌ای)
سیستم فقط **کارت‌های از پیش تعریف‌شده** را می‌شناخت: `CARD_CHANNEL`/`FA_TITLE`/typed tools در `money_tools`.
هر چیز خارج از آن دیکشنری → `approved-no-typed-tool` → «تأیید ثبت شد» و **هیچ اتفاقی**. یعنی:
تشخیصِ کار ناشناخته وجود نداشت و اجرای آن هم. مالک می‌توانست تأیید کند، ولی دستی برای اجرا نبود.

## مکانیزم U-WORK — شش قطعه

### ۱. Proposal Intake — «هر چیزی که دیده شد، یک پیشنهاد می‌شود» ✅ LIVE
`state/revenue-drive/proposal_intake.py` + `proposals.jsonl`
اسکیمای اجباری: `{title, why, action:{type,args}, risk, reversible, evidence}`
هر حلقه/ایجنت/دیپ‌اسکن می‌تواند submit کند: `python3 proposal_intake.py submit p.json`

### ۲. Classifier — مرز سرخ یا سبز-داخلی ✅ LIVE
`risk=internal_green` → **خودکار** (بر اساس GOV-FREEDOM-V2: کار داخلیِ برگشت‌پذیر = PROCEED)
`risk=red_external|money|public|customer` → **کارت + تپ مالک** (هیچ اثر بیرونی بدون رأی)

### ۳. Bounded Executor — دستِ اجرا با allowlist ✅ LIVE
`state/revenue-drive/action_executor.py` — پنج نوع کار مجاز:
| type | کار | قید |
|---|---|---|
| `write_file` | نوشتن فایل | فقط داخل `state/**`، ≤۲۰۰KB، pre-image + sha256 + rollback |
| `append_jsonl` | افزودن ردیف | append-only، همان قید مسیر |
| `run_script` | اجرای اسکریپت پایتون | فقط داخل `state/**`، timeout ۶۰s، خروجی در رسید |
| `send_email_batch` | ارسال دستهٔ ایمیل | فقط با تپ مالک (`via=owner_card` + `email_authorized`) |
| `none` | فقط ثبت | — |
خارج از allowlist → `ACTION_NOT_ALLOWED` + پیام «کلاس جدید لازم است» (نه اجرا، نه سکوت).
مسیر خارج از ریشه‌های مجاز → `PATH_OUTSIDE_ALLOWED_ROOTS` (تست: `/etc/passwd` رد شد).

### ۴. کارتِ کارِ ناشناخته — با دکمهٔ هر گزینه ✅ LIVE
پیشنهاد سرخ → یک آیتم در `owner-review.json` با `action` → `owner_ask` کارت می‌سازد (fa + دکمه) →
تپ در `owner_reply` → `action_executor.execute(...)` (سیم‌کشی امشب) → رسید + rollback + پیام نتیجه در چت.
**این همان حلقهٔ گمشده بود:** تأیید مالک حالا واقعاً اجرا می‌شود، هر type که در allowlist باشد.

### ۵. Capability Learning — allowlist خودش رشد می‌کند ⏳ V2
وقتی `ACTION_NOT_ALLOWED` برگشت: کارت «کلاس جدید» با شرح دقیق نوع کار + دامنهٔ اثر + نمونهٔ dry-run
→ تأیید مالک = کلاس به allowlist اضافه می‌شود (یک‌بار برای همیشه برای همان کلاس).
یعنی قابلیت‌های ناشناخته با اجازهٔ مالک خودکار می‌شوند، نه با هر بار کدنویسی ایجنت.

### ۶. Detection Sources — «خودش ببیند» ⏳ V2
هر حلقه در پایان چرخه یک **surprise log** بنویسد: «چه چیزی پیش‌بینی نشده بود ولی لازم شد؟»
+ deep-scan findings خودکار به proposal تبدیل شوند (اگر action مشخص دارند).
+ session debrief هر لین: ۳ کار ناشناخته‌ای که وسط راه لازم شد.

## تست پذیرش V1 (اجرا شد، 4/4)
| تست | نتیجه |
|---|---|
| T1 پیشنهاد سبز-داخلی (write_file) | ✅ خودکار اجرا + رسید + rollback |
| T2 پیشنهاد مرز سرخ (نصب پکیج روی نود) | ✅ اجرا نشد؛ کارت با action ساخت |
| T3 تپ مالک روی همان کارت | ✅ اجرای عمومی (و برای type ناشناخته: `ACTION_NOT_ALLOWED`) |
| T4 فرار از مسیر (`/etc/passwd`) | ✅ رد شد: `PATH_OUTSIDE_ALLOWED_ROOTS` |

## تصمیم‌هایی که فقط مالک می‌تواند بگیرد (کارت‌ها)
1. **مجوز ایستاده برای کلاس‌های کم‌ریسک بیرونی**: مثلاً «ارسال ≤۱۰ ایمیل/روز از قالب‌های مصوب بدون رأی هر دسته» —
   این تنها اهرمی است که سیستم را واقعاً خودگردان می‌کند (الان هر دسته رأی می‌خواهد).
2. **دورهٔ اعتبار و سقف**: چند روز؟ چند دلار؟ چند گیرنده؟ (پیش‌فرض پیشنهادی: ۱۴ روز، سقف بودجهٔ فعلی، فقط سرنخ‌های موجود)
3. **کلاس‌های اقدام که هرگز خودکار نشوند** (لیست سیاه صریح): خرید، ارتباط عمومی، انتشار، تغییر زیرساخت.

## قیدهای امنیتی (غیرقابل بازگشایی)
pre-image پیش از هر نوشتن · رسید برای هر اثر · rollback همیشه · مسیر محصور در `state/**` · secrets هرگز چاپ نمی‌شود ·
مرز سرخ فقط با تپ مالک · سقف بودجه و HALT دست‌نخورده · شکست‌ها حفظ می‌شوند (ATTEMPTED_FAILED، نه سکوت).
