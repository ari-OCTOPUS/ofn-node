## A1 — حذف کامل استک ماینینگ از `.100` و `.160`
**تأیید مالک:** «همه‌چیز را کامل پاک کن»

**چرا:** ماینینگ **صفر** بوده. شواهد:
- `grep -icE "block.*(success|found|mined|mint)"` روی کل `fullnode.log` ⇒ **۰ بلوک**
- نود از ۱۶ آپریل هیچ peer عمومی نگرفته: کنسول `P2P peers:` خالی، تیپ زنجیره `height 738143 time 2026-04-16`
- ۱۱۸۳۷ تلاش اتصال، همیشه `total 1 public 0 subnet`
- ماینر تخمین می‌زند **۰.۰۲ HAC در روز** با احتمال موفقیت ۰.۰۸۶٪
- **هیچ کیف پولی روی بردها نیست** (`/opt/hacash/data` خالی، `find / -iname "*wallet*"` چیزی نیافت) ⇒ فقط یک آدرس reward، بدون کلید خصوصی. پس حذف هیچ پولی را از بین نمی‌برد.
- `tdc_miner` (Tidecoin) هم از قبل شکسته بود: `status=203/EXEC` چون باینری `xmrig` قبلاً حذف شده بود.

**انجام‌شده:**
| برد | stop+disable | حذف‌شده | فضای آزادشده |
| :--- | :--- | :--- | :--- |
| `.100` | `hacash-fullnode`, `tdc_miner` | `/opt/hacash` (822M)، unitها، `hacash-health.sh`، کرون | ۸۲۲ مگ |
| `.160` | `hacash-miner` | `/opt/hacash` (126M)، unitها، `wait-for-master.sh` | ۱۲۶ مگ |

**تأیید شد:** `/opt/hacash` دیگر وجود ندارد؛ `systemctl list-unit-files | grep hacash` خالی؛ helperها رفته‌اند.
**ثبت:** کانفیگ‌ها، unitها و اسکریپت‌ها در `removed-hacash-record/` همین پوشه نگه داشته شدند.

**ROLLBACK:** غیرممکن برای باینری‌ها — ولی همه‌چیز از سورس قابل ساخت مجدد است و کانفیگ‌ها/unitها ضبط شده‌اند.
اگر لازم شد: کانفیگ‌ها را از `removed-hacash-record/` برگردان، سپس بر اساس
`03 - Projects/Mining/03 - Rigs/Mining-1/Hcash/` دوباره build کن.

## A2 — ساخت swap روی `182` برای قطع حلقهٔ OOM
**تأیید مالک:** «swap بساز تا حلقه قطع شود»

**چرا:** سرویس `octopus-sensorium` هر ~۱۵ ثانیه OOM می‌خورد و ری‌استارت می‌شد.
خط پایه قبل از تغییر: **`NRestarts=98`** و هیچ‌وقت به `READY` نمی‌رسید.
علت: برد ۳.۹ گیگ رم، **swap صفر**، سرویس سقف `MemoryMax=2G` و `MemorySwapMax=infinity`.

**انجام‌شده:**
- `fallocate -l 2G /swapfile` + `mkswap` + `swapon`
- یک خط `nofail` به `/etc/fstab`: `/swapfile none swap sw,nofail 0 0`
- از `/etc/fstab` نسخهٔ پشتیبان گرفته شد: `/etc/fstab.pre-swap-<timestamp>`
- `findmnt --verify` تمیز است (فقط هشدار `daemon-reload`)

**نتیجهٔ اندازه‌گیری‌شده (۱۵۰ ثانیه پایش):**
```
خط پایه:            NRestarts=98
t+ 30s  active     NRestarts=0   swap_used=826MB
t+ 60s  active     NRestarts=0   swap_used=340MB
t+ 90s  active     NRestarts=0   swap_used=751MB
t+120s  active     NRestarts=0   swap_used=930MB
t+150s  active     NRestarts=0   swap_used=701MB
Status: runtime=ACTIVE readiness=READY/WAVE0_OBSERVE_ONLY bus=CONNECTED
```
**هیچ OOM و هیچ ری‌استارتی رخ نداد و سرویس به `READY` و `bus=CONNECTED` رسید.**

**ROLLBACK:** `swapoff /swapfile && rm /swapfile` و حذف خط از `/etc/fstab`
(یا بازگرداندن `cp /etc/fstab.pre-swap-* /etc/fstab`).

## A3 — نوشتن ایمیج Pro روی کارت ۱۲۸ گیگِ داخل ۱۳۸
**چرا:** مالک کارت ۱۲۸ را در ۱۳۸ گذاشت تا برای برد Pro آماده شود.

**دو نکتهٔ مهمی که حین کار پیدا شد:**
1. **کارت ۱۲۸ خراب بود.** `e2fsck -fn` گفت `Directory inode 15745 ... directory corrupted`
   و abort کرد؛ `/etc/fstab` کاملاً صفر شده بود و `/opt` خالی. پس محتوایش آشغال بود

**تأیید بوت‌لودر روی کارت:**

sector 16384 : d0 0d fe ed ...   <- FIT / u-boot    ✓

**ROLLBACK:** کارت را دوباره فرمت/نوشتن کن؛ محتوای قبلی‌اش خراب بود و ارزشی نداشت.

## A5 — 🔴 کارت ۱۲۸ حین کار **مرد**. باید فیزیکی از ۱۳۸ بیرون بیاید.

نوشتن **موفق بود** (`WROTE_BYTES 817701376` — دقیقاً اندازهٔ درست)، ولی بلافاصله بعدش کارت از کار افتاد:

```
mmc1: tried to HW reset card, got error -110
mmcblk1: recovery failed!
I/O error, dev mmcblk1, sector 0 op 0x0:(READ)
mmc_host mmc1: Timeout sending command (cmd 0x202000 ...)
mmc1: card never left busy state
```
- خواندن ۴ مگابایت **۲۸.۷ ثانیه** طول کشید (کارت سالم این را در چند صدم ثانیه می‌خواند)
- `blkid /dev/mmcblk1p1` دیگر هیچ خروجی نمی‌دهد ⇒ فایل‌سیستم ناخواناست
- چند پروسه از دستورهای من در حالت **D** گیر کردند: `sed`، `partprobe`، و `udev-worker`
  (kill -9 هم آنها را آزاد نکرد — تا کارت فیزیکی برداشته نشود آزاد نمی‌شوند)

**وضعیت ۱۳۸:** سالم است. `dd` روی eMMC با **۲۹۷ MB/s** خواند، هیچ ری‌استارتی نداده
(uptime پیوسته)، و **هر ۸ سرویس ارگانیسم بالاست** (bridge, control-router, cycle-settler,
router, supervisor, verify-dispatcher, …). کارت unmount شده و هیچ پروسه‌ای رویش نمی‌نویسد.

**پس این کارت دور انداختنی است.** کارت اول هم فایل‌سیستش خراب بود (`directory corrupted`)،
حالا هم فیزیکی مرد ⇒ **این کارت هرگز نباید روی برد جدید برود.**

## A8 — ⚠️ برد Plus **eMMC ندارد** — درخواست «فلش روی eMMC» فعلاً ممکن نیست

مالک گفت سیستم Plus به eMMC منتقل شود تا کارت SD آزاد شود. اندازه‌گیری روی خود برد:

```
lsblk            -> mmcblk1 (29.7G) = کارت SD  ·  mtdblock0 (16M) = SPI NOR
                    هیچ mmcblk0 وجود ندارد
dmesg            -> mmc0: SDHCI controller on fe2e0000.mmc   (کنترلر ثبت شد)
                    ولی هیچ chipی وصل نیست ⇒ هیچ دستگاه بلوکی ساخته نشد
/dev/nvme*       -> وجود ندارد (اسلات M.2 خالی است)
/proc/mtd        -> mtd0: 01000000 "loader"   (SPI NOR هست)
```
**یعنی:** کنترلر eMMC هست ولی **ماژول eMMC نصب نیست**؛ M.2 هم خالی است.
تنها حافظهٔ پایدارِ در دسترس، همان کارت SD است (به‌علاوهٔ ۱۶ مگابایت SPI که فقط برای
u-boot کافی است، نه برای rootfs).

⇒ برای آزاد کردن کارت SD باید یا **ماژول eMMC** روی برد نصب شود یا **SSD NVMe M.2**.
تا آن موقع، Plus روی SD می‌ماند (که کار می‌کند).

## A9 — پژوهش عمیق eMMC روی Plus: نرم‌افزار سالم است، مشکل سخت‌افزاری است

مالک تأیید کرد ماژول eMMC **فیزیکی روی Plus نصب است** و خودش چک کرده.
پس چهار آزمون مستقل انجام شد تا نرم‌افزار از سخت‌افزار جدا شود:

| آزمون | نتیجه |
| :--- | :--- |
| وضعیت نود در Device Tree | `mmc@fe2e0000` = **`okay`** (فعال)، با `non-removable`، `no-sd`، `no-sdio`، `supports-cqe` |
| راه‌اندازی مجدد دایرِ کنترلر (unbind/bind) | کنترلر بالا آمد (`mmc0: CQHCI version 5.10` + `SDHCI controller ... using ADMA`) ولی **هیچ چیپی جواب نداد** |
| بازراه‌اندازی سرد (reboot کامل) | باز هم هیچ `mmcblk0` ساخته نشد |
| **مقایسهٔ کلمه‌به‌کلمهٔ نود DT با برد سالم** | **کاملاً یکسان**: `bus-width=8`، `max-frequency=0x0bc2eb00`، `mmc-hs400-1_8v`، `mmc-hs400-enhanced-strobe`، `supports-cqe`، `no-sd`، `no-sdio`، `non-removable`، `resets`/`reset-names` — هیچ تفاوتی نیست |

`sysfs` هم تأیید می‌کند باس در حالتی مانده که هیچ کارتی نشناخته:
`/sys/kernel/debug/mmc0/ios -> clock: 0 Hz ; vdd: 0 (invalid) ; power mode: 0 (off)`

**نتیجه‌گیری:** پیکربندی نرم‌افزاری روی Plus **دقیقاً همان** پیکربندی پنج برد سالم است،
پس علت نرم‌افزاری نیست ⇒ **تماس فیزیکی یا سلامت خودِ ماژول/سوکت**.
گام بعدی مالک: **قطع کامل برق (نه reboot — ریبوت ریل eMMC را قطع نمی‌کند)، درآوردن ماژول و جا زدن محکم مجدد.**

## A10 — ✅ eMMC برد Plus **سالم است** — نتیجه‌گیری A9 **غلط بود**

مالک کارت SD را درآورد و برد روشن شد. برد از **eMMC** بالا آمد:

```
mmcblk0      179:0    0 58.3G  0 disk
└─mmcblk0p1  179:1    0 58.3G  0 part /     ← ریشهٔ سیستم روی eMMC
mmcblk0boot0 179:32   0    4M  1 disk
mmcblk0boot1 179:64   0    4M  1 disk
findmnt /  ->  /dev/mmcblk0p1  ext4
model: Orange Pi 5 Plus      OS: Debian 13 trixie (DietPi)
eMMC size: 62.579 GB
```

**پس ماژول eMMC و سوکت هر دو سالم‌اند.** اشتباه من در A9 این بود که از
«نرم‌افزار یکسان است» نتیجه گرفتم «سخت‌افزار خراب است» — ولی متغیر سومی هم بود که
تست نکرده بودم: **مسیر بوت**.

**علت واقعی:** وقتی برد از **SD** بوت می‌شود، کرنل آرمبیان eMMC را بالا نمی‌آورد
(کنترلر init می‌شود، ساعت‌ها می‌چرخند، ولی هیچ کارتی پیدا نمی‌شود). وقتی از **eMMC** بوت
می‌شود، همه‌چیز درست کار می‌کند. یعنی مشکل در مسیر بوت از SD است، نه در سخت‌افزار.

**درس ثبت‌شده:** «نرم‌افزار یکسان ⇒ سخت‌افزار خراب» یک استنتاج ناقص است؛ باید **مسیر بوت**
هم متغیر در نظر گرفته شود. آزمون درآوردن SD (که مالک پیشنهاد داد) همان چیزی بود که
حقیقت را روشن کرد.

**دستاورد:** هدف مالک محقق شد — Plus روی eMMC است و **کارت SD آزاد شد**.

**ثبت:** نود مِش از `194` به `193` تغییر نام یافت (کامیت `1e1d33a6e`)، نام میزبان
`octopus-model-plus-193` شد، کلیدها نصب و دسترسی از هر دو طرف تأیید شد.

## A11 — کارت ۳۲ گیگ با ایمیج **Pro** آماده شد (فلش از داخل برد Plus)

مالک کارت را **در حالت روشن** داخل Plus گذاشت (نه ۱۳۸). نتیجه:
```
mmc1: new ultra high speed SDR104 SDHC card
mmcblk1: mmc1:aaaa SD32G 29.7 GiB
```
**هیچ کرشی نشد** و جالب اینکه **eMMC (`mmcblk0`) و SD (`mmcblk1`) همزمان کار کردند**.
(۱۳۸ هم امروز یک hot-plug را بدون کرش تحمل کرد؛ پس قانون «هرگز hot-plug نکن» احتمالاً
بیشتر دربارهٔ کارتِ معیوب ۱۸۲ بود تا یک قانون عمومی برد.)

سلامت کارت قبل از نوشتن: `e2fsck -fn` فقط یک ناسازگاری جزئی شمارش inode داشت
(طبیعی بعد از درآوردن کارت) — **برخلاف کارت مرده که «directory corrupted» داد**.

مسیر فلش: تصویر از ۱۳۸ با `scp` نرفت (DietPi سرور SFTP ندارد) ⇒ با استریم روی SSH منتقل شد،
سپس SHA-256 دو طرف مقایسه شد و **مطابقت کرد**. روی Plus نه `python3` بود نه `xz`،
پس `xz-utils` با apt نصب شد.

نتیجهٔ فلش:
```
817701376 bytes (818 MB, 780 MiB) copied, 36.5 s, 22.4 MB/s
DD_EXIT=0
```
تأیید بوت‌لودر و تزریق:
- `RKNS` در سکتور ۶۴ و u-boot FIT در ۱۶۳۸۴ ✓
- `mmcblk1p1` ext4 با `PARTLABEL="root"` + `mmcblk1p2` vfat با برچسب `DIETPISETUP`
- سیستم: **Debian 12 (bookworm)** — ایمیج DietPi Pro
- **۳ کلید تزریق شد** (mesh، لپ‌تاپ، piggybank)، بدون CR
- نام میزبان: `opi5pro-new` · کارت تمیز unmount شد

> ⚠️ **هشدار:** کارت الان بوت‌لودر **Pro** دارد. اگر برد **Plus** با این کارت ری‌استارت شود،
> تلاش می‌کند ایمیج Pro (RK3588S) را روی سخت‌افزار RK3588 بالا بیاورد و **بوت نمی‌شود**.
> پس کارت باید **پیش از هر ری‌استارت از Plus بیرون بیاید**.

## A12 — ✅ هدف نهایی محقق شد: **۷ برد، همه روی eMMC**

مالک کارت آماده‌شده را در برد ششم گذاشت و برد روی `192.168.0.114` بالا آمد:
`Xunlong Orange Pi 5 Pro`, سیستم از کارت (`/dev/mmcblk1p1`), کلیدهای ما کار کردند.

**کشف مهم:** eMMC این برد **از قبل یک نصب کامل و بوت‌شدنی** داشت — لازم نبود چیزی کپی شود:
```
بوت‌لودر eMMC: RKNS در سکتور ۶۴ ✓ + u-boot در ۱۶۳۸۴ ✓
سیستم: Debian 13 (DietPi) با ریشهٔ کامل (sbin/init موجود)
fstab و dietpiEnv: هر دو به UUID خودِ eMMC (1597e95c…) اشاره داشتند ✓
e2fsck: پاک ✓
```
تنها کمبودش **کلید SSH** بود (فقط `known_hosts` قدیمی). پس: کلیدها تزریق شد، نام میزبان
`octopus-pro-114` گذاشته شد، و کارت SD با دستور مالک درآورده شد (اول برق قطع — چون ریشه روی
خودِ کارت بود).

**تأیید نهایی — ۷ از ۷:**
```
138   DietPi                  Orange Pi 5 Pro    eMMC
180   octopus-continuity-180  Orange Pi 5 Pro    eMMC
182   sensorium-opi5pro       Orange Pi 5 Pro    eMMC
100   octopus-compute-100     Orange Pi 5 Pro    eMMC
160   octopus-compute-160     Orange Pi 5 Pro    eMMC
193   octopus-model-plus-193  Orange Pi 5 Plus   eMMC
114   octopus-pro-114         Orange Pi 5 Pro    eMMC
```
همه: ریشه روی `/dev/mmcblk0p1` و **هیچ `mmcblk1` وجود ندارد** (هیچ کارتی نمانده).

**نکتهٔ فنی:** مثل Plus، این برد هم هنگام بوت از eMMC یک **MAC متفاوت** گرفت
(`c0:74:2b:f9:72:f1`، همان بلوک `f9` بقیهٔ Proها) — پس MAC تابع رسانهٔ بوت است، نه شناسهٔ ثابت برد.

**رفع یک ایراد رجیستری:** کلید مِش به `authorized_keys` خودِ ۱۳۸ هم اضافه شد تا نود ۱۳۸ مثل
بقیه قابل تأیید باشد (قبلش `ari@138` رد می‌کرد).
