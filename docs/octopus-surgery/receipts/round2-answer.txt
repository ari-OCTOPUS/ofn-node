# مدل حقیقت وضعیت (Ground-Truth Model)

**آنچه واقعاً می‌دانیم (شواهد ضمنی از صورت مسئله):**
- سه ماه توسعه انجام شده — UNKNOWN: تعداد ساعت واقعی کار
- چند repository، چند node، تعداد زیاد تست وجود دارد
- چند کسب‌وکار نیمه‌کاره — UNKNOWN: کدام‌ها، درصد تکمیل هرکدام
- مالک «نتیجهٔ قابل‌مشاهده» نمی‌بیند

**آنچه نمی‌دانیم (باید علامت UNKNOWN بخورد):**
- آیا حتی یک جریان end-to-end کامل کار می‌کند؟ **UNKNOWN**
- آیا کاربر واقعی وجود دارد؟ **UNKNOWN**
- تعریف مالک از «نتیجه» چیست (درآمد؟ محصول قابل‌استفاده؟ دمو؟) **UNKNOWN**
- آیا تست‌ها مسیرهای ارزش‌آفرین را پوشش می‌دهند یا فقط کد داخلی؟ **UNKNOWN**

# ۲) تفکیک سه‌گانهٔ مشکل

| نوع | نشانهٔ تشخیص | وضعیت فعلی |
|---|---|---|
| **فنی** | کد کار نمی‌کند / یکپارچه نمی‌شود / deploy نمی‌شود | UNKNOWN — تست زیاد لزوماً یعنی کد کار می‌کند نیست |
| **هماهنگی** | قطعات جدا کار می‌کنند ولی به‌هم وصل نشده‌اند؛ چند node/repo بدون یکپارچگی | **مظنون قوی** — «چند repo، چند node، چند کار نیمه‌کاره» الگوی کلاسیک پراکندگی است |
| **انتخاب بازار** | همه‌چیز کار می‌کند ولی کسی نمی‌خواهد | UNKNOWN — چون هنوز چیز قابل‌عرضه‌ای نیست، این را نمی‌توان رد یا تأیید کرد |

**نکتهٔ کلیدی:** تا وقتی یک خروجی end-to-end وجود نداشته باشد، مشکل بازار قابل‌آزمون نیست. پس اولویت بین فنی و هماهنگی است.

# ۳) سه فرضیهٔ رقیب + روش ابطال

**فرضیه A — مشکل هماهنگی/یکپارچگی:**
قطعات جدا ساخته شده‌اند ولی هیچ مسیر کاملی از ورودی تا خروجی وجود ندارد.
→ *ابطال:* اگر بتوان یک جریان کامل end-to-end را در ۴ ساعت اجرا کرد، این فرضیه رد می‌شود.

**فرضیه B — مشکل فنی پایه‌ای:**
اجزا به‌تنهایی هم درست کار نمی‌کنند (تست‌ها سطحی‌اند/کد شکننده است).
→ *ابطال:* اگر هستهٔ اصلی روی داده واقعی بدون خطا اجرا شود، این فرضیه رد می‌شود.

**فرضیه C — مشکل تعریف نتیجه (انتظار مالک):**
سیستم عملاً کار می‌کند ولی هیچ‌کس «نتیجه» را به شکل قابل‌نمایش تعریف نکرده.
→ *ابطال:* اگر پس از نوشتن تعریف صریح «نتیجه»، معلوم شود آن خروجی از قبل موجود بوده، این فرضیه تأیید (و بقیه رد) می‌شود.

# ۴) اقدام داخلی کم‌ریسک (۴ ساعته)

**اقدام: «کاوش مسیر باریک» (Thin-Slice Trace)**

در ۴ ساعت، تلاش برای اجرای **یک** جریان کامل واقعی از ورودی تا یک خروجی قابل‌مشاهده، و مستندسازی هر جایی که می‌شکند.

**Artifact قابل‌بررسی (خروجی):**
- یک سند یک‌صفحه‌ای شامل:
  1. نقشهٔ repository‌ها و node‌ها و اینکه هرکدام چه کاری می‌کنند
  2. جدول کسب‌وکارهای نیمه‌کاره با درصد تخمینی تکمیل
  3. نتیجهٔ تلاش برای یک جریان end-to-end: کجا کار کرد، کجا شکست
  4. تعریف صریح مالک از «نتیجه» (یک جمله)

**چرا کم‌ریسک:** فقط خواندن/اجرا داخلی — هیچ deploy، هیچ تماس خارجی، هیچ تغییر معماری.

---

# ۵) ادعاهای UNKNOWN (صریح)
- ارزش‌آفرین بودن تست‌ها → **UNKNOWN**
- کار کردن هر جریان کامل → **UNKNOWN**
- وجود کاربر/تقاضای بازار → **UNKNOWN**
- تعریف مالک از «نتیجه» → **UNKNOWN**
- درصد واقعی تکمیل هر کسب‌وکار → **UNKNOWN**
