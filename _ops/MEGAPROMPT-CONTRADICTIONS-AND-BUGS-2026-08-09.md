## بخش الف — یافته‌های تازهٔ ۲۰۲۶-۰۸-۰۹ (کنترل‌پنل)

زمینه: مالک گزارش داد کنترل‌پنل بالا نمی‌آید. ریشه پیدا شد (۶ ساعت خوابِ لپ‌تاپ، خودِ watchdog قبل از رسیدنِ من احیا کرده بود — کدی خراب نبود). در حینِ تأیید + soak-testِ ۱۶۰ دقیقه‌ای (۱۵٬۲۶۴ پروب، ۹۹.۹۷٪ موفق، PID بدونِ تغییر)، این موارد کشف شد. جزئیاتِ کامل: [[../01 - Dashboard/HANDOFF|HANDOFF]] (ورودیِ ۲۰۲۶-۰۸-۰۹).

### الف-۱. miniapp-watchdog زمان‌محور است نه رویداد-محور — تناقضِ قصد/پیاده‌سازی
کامنتِ بالایِ `_ops/miniapp-watchdog.ps1` می‌گوید هدفش این است: «keeps the Mini App reachable **while the owner is away**». پیاده‌سازی فقط هر ۱۰ دقیقه چک می‌کند، نه در لحظهٔ واقعیِ wake/logon. شاهدِ زنده امروز: لپ‌تاپ ۰۸:۴۱ بیدار شد، gateway تا ۰۸:۴۸ (~۷ دقیقه) پایین ماند — یعنی دقیقاً همان لحظه‌ای که مالک احتمالاً اول‌بار امتحان کرد.
**سؤال:** (الف) یک trigger اضافه (`AtLogOn`) به تسک‌های `OCTOPUS-MiniApp-Watchdog`/`Cortex-Watchdog`/`Live-Watchdog`/`TG-Center-Watchdog`/`organism-watchdog` اضافه شود — پنجرهٔ خرابی از ۱۰ دقیقه به چند ثانیه می‌رسد. (ب) همین‌طور بماند — ۱۰ دقیقه قابلِ قبول است.
**توصیه:** (الف). دستورِ آماده (فقط مالک اجرا کند):
```powershell
foreach ($name in "OCTOPUS-MiniApp-Watchdog","OCTOPUS-Cortex-Watchdog","OCTOPUS-Live-Watchdog","OCTOPUS-TG-Center-Watchdog","organism-watchdog") {
    $t = Get-ScheduledTask -TaskName $name -ErrorAction SilentlyContinue
    if ($t) {
        $newTriggers = @($t.Triggers) + (New-ScheduledTaskTrigger -AtLogOn)
        Set-ScheduledTask -TaskName $name -Trigger $newTriggers
        Write-Host "OK: $name"
    } else { Write-Host "SKIP (not found): $name" }
}
```

### الف-۲. Owner-Cockpit (fugu_proxy:8787 + owner_api:8788): ساخته‌شده، تست‌شده، ولی بدونِ launcher/watchdog — همان بیماریِ آیتمِ ب-۶ زیر
دیشب (۲۰۲۶-۰۸-۰۸) کاملاً ساخته شد، ۶۴ تست سبز، ۶/۷ چک‌لیست verify. امروز چک شد: هیچ پروسه‌ای روی ۸۷۸۷/۸۷۸۸ گوش نمی‌دهد، هیچ `.bat`/scheduled-task ای برایِ راه‌اندازی‌اش نیست. الگویِ تکراری با `control_plane/supervisor.py` (آیتمِ ب-۶): ساخته می‌شود، تست می‌شود، ولی هرگز به چرخهٔ launch وصل نمی‌شود.
**سؤال:** (الف) launcher+watchdog واقعی مثلِ ۵ لیمبِ دیگر ساخته شود، (ب) عمداً manual-start بماند، (ج) تا معلوم‌شدنِ نیازِ واقعی دست نخورد.
**توصیه:** (ج) — قبل از هزینهٔ زیرساخت (launcher+watchdog+DNS/tunnel جدا برایِ یک پنلِ دوم)، بسنجیم آیا مالک اصلاً از پنلِ دوم استفاده می‌کند یا کنترل‌پنلِ فعلی (تلگرام مینی‌اپ، همین که امروز تست شد) کافی است.

### الف-۳. soak-test مسیرِ نوشتن را عمداً تست نمی‌کند — دقیقاً همان کلاسِ باگی که 91acaf6 فیکس کرد
کامنتِ خودِ `_ops/tests/soak_gateway.py`: «POST … فقط `/api/ask` برای جلوگیری از side-effect». یعنی فیکسِ حیاتیِ دیشب (`check_same_thread=False` — بدونش هیچ نوشتنی از gateway کار نمی‌کرد) هرگز زیرِ بارِ مداوم دیده نشد، فقط unit-test. درسِ خودِ کامیتِ `91acaf6`: «soak test ۱۰۰٪ سبز بود ولی write‌ها شکست می‌خوردند — تست روی اتفاقات واقعی».
**سؤال:** (الف) یک probe نوشتنیِ کاملاً بی‌اثر (یک `action kind` از نوعِ `noop` که فقط DB را لمس می‌کند، صفر اثرِ بیرونی) به soak_gateway.py اضافه شود تا مسیرِ نوشتن هم زیرِ بارِ طولانی دیده شود. (ب) همین‌طور بماند — ریسکِ side-effect بر خطرِ نبودِ پوشش می‌چربد.
**توصیه:** (الف) — یک noop-action ایمن، ریسکِ صفر با پوششِ واقعی.

### الف-۴. حافظهٔ gateway در بازهٔ ۳ ساعته رشدِ آرام داشت — نیازِ رصدِ افق‌بلندتر (نه تصمیم، فقط watch-item)
۲.۲←۳۳.۵MB در ~۳ ساعت. HandleCount بینِ دو چک‌پوینتِ آخر (۳۰ و ۱۲۰ دقیقه) دقیقاً ثابت ماند (۱۴۴=۱۴۴) — نشانهٔ خوب، ولی فقط ۳ ساعت است. جلسهٔ بعدی که PID را چک می‌کند: اگر بعدِ چند روزِ uptime، MemMB پیوسته (نه warm-up یک‌باره) بالا برود، آن‌وقت واقعاً نشتِ آرام هست.
